# Drex Max в замкнутом контуре

Первый прототип ведёт машину по одной полосе от старта до остановки у цели. По умолчанию решения принимает `nace-ai/drex-max-v1` через штатный Python runtime. DriveSuprim, NAVSIM и их данные для запуска не требуются.

Каждые 0,5 секунды симуляции Drex получает текущую и предыдущую скорость, прошлую команду, расстояние до цели, состояние видимого светофора и скорость и дистанцию до ведущей машины. Модель выбирает `proceed`, `maintain`, `slow`, `stop` или `wait`. Симулятор исполняет команду шагами по 0,1 секунды и передаёт новое состояние на следующий запрос. Аварийное торможение отслеживает дистанцию до ведущего автомобиля. Ошибка ответа вызывает остановку и записывается в журнал. Соблюдение светофора и остановка у цели зависят от решений водителя.

В `route` есть ведущая машина и светофор. `red_light` проверяет светофор на свободной дороге. В `lead_brakes` ведущая машина останавливается и снова трогается.

## Локальная проверка

Из корня репозитория, Python 3.10 или новее. Этот режим использует правила, чтобы проверить сценарий и исполнение команд.

```bash
python -m unittest scripts.drex_drive.test_drive -v
python -m scripts.drex_drive --driver reference --scenario route --out output/drex-drive-reference
```

## Прогон с Drex Max на msu270

Команда использует подготовленные на кластере Python-окружение, официальный runtime и веса. Выполнять из корня репозитория на `msu270`.

```bash
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
drex_run_dir="$DREX_RUNTIME_ROOT/runs/drive-route-$(date -u +%Y%m%dT%H%M%S%NZ)"

srun --partition="${DREX_PARTITION:-batch}" --gres=gpu:1 --cpus-per-task=4 --mem=96G --time=00:30:00 \
  env PYTHONPATH="$DREX_RUNTIME_ROOT/upstream" \
  "$DREX_RUNTIME_ROOT/venv/bin/python" -m scripts.drex_drive \
  --scenario route --model "$DREX_RUNTIME_ROOT/models/drex-max-v1" --out "$drex_run_dir"
```

`trace.jsonl` содержит запросы и ответы модели, состояние автомобиля на каждом шаге и источник каждой команды. `report.json` содержит исход поездки, нарушения, вмешательства, долю шагов под управлением водителя и время вызовов. Код выхода `0` означает финиш с остановкой без нарушений, аварийного торможения и ошибок ответа. Для повторного прогона укажите новую папку.

## Прогон с движением во время инференса

В режиме `--mode realtime` симулятор выполняет шаг каждые 0,1 секунды по настенным часам, а отдельный поток обращается к Drex. Запросы отправляются каждые 0,5 секунды, если предыдущий вызов завершён. Ответ должен быть принят за 0,5 секунды после отправки. Пока результат в пути, действует предыдущая команда сроком до 0,5 секунды с момента её применения. По истечении срока команды или запроса симулятор тормозит. Запоздалый ответ записывается в журнал, а следующий запрос использует свежее наблюдение.

На msu270 из корня репозитория запусти `bash scripts/drex_drive/submit.sh warm route`. Один запрос до начала поездки прогревает GPU и учитывается отдельно в `warmup_wall_s`. Для замера холодного старта используй `bash scripts/drex_drive/submit.sh cold route`. После `Submitted batch job` можно отключиться от SSH.

Для номера задания `JOB_ID` лог находится в `$DREX_RUNTIME_ROOT/logs/drive-rt-JOB_ID.log`, а отчёт и события — в `$DREX_RUNTIME_ROOT/runs/drive-rt-JOB_ID/`. Если `DREX_RUNTIME_ROOT` не задан, скрипт берёт `/scratch/pr0201/drex_runtime`.

В отчёте `decision_applied` считает принятые ответы, `decision_deadline_misses` — просроченные запросы, а `decision_slots_busy` — пропущенные моменты отправки из-за занятого потока. `decision_applied_p95_wall_s` измеряет возраст наблюдения при применении команды. `tick_lag_max_wall_s` показывает максимальное опоздание шага симулятора относительно расписания. Ожидание первого ответа и аварийные вмешательства учитываются отдельно от остановок по таймауту.

## Проверка просроченных ответов

`--inject-timeout SIM_MS:EXTRA_WALL_MS` задерживает выдачу ответа после инференса. Первый параметр задаёт время запроса в симуляции и должен быть кратен 500 мс. Второй задаёт дополнительное ожидание в миллисекундах реального времени и должен превышать дедлайн 500 мс. Повтор флага задаёт несколько задержек в одной поездке.

```bash
bash scripts/drex_drive/submit.sh warm lead_brakes --inject-timeout 3500:650 --inject-timeout 12000:650
bash scripts/drex_drive/submit.sh warm red_light --inject-timeout 5000:650 --inject-timeout 11000:650
```

`injected_timeouts` показывает судьбу каждого запланированного ответа. `fallback_recoveries_wall_s` показывает время от начала торможения до следующей применённой команды водителя. `latency_stress_pass: true` означает, что каждая запланированная задержка вызвала один переход к торможению с последующим возвратом управления, просроченные ответы отброшены, а маршрут завершён без нарушений и аварийного торможения. Для прогона с задержками код выхода определяется этим полем. Обычный `clean_finish` при переходе к торможению по таймауту остаётся `false`.

## Камера и серия поездок

Команда `bash scripts/drex_drive/submit.sh suite` запускает девять последовательных поездок в одном задании Slurm и загружает Drex Max один раз. Каждый эпизод начинается с прогревочного вызова своего режима наблюдений. Сценарии `route`, `red_light` и `lead_brakes` выполняются в трёх режимах.

| Режим | Что получает Drex |
| --- | --- |
| `state` | Телеметрия, расстояние до цели, структурированные данные о светофоре и ведущей машине |
| `state-camera` | Те же данные и кадр фронтальной камеры |
| `camera` | Кадр, телеметрия и расстояние до цели. Светофор и ведущая машина представлены только в кадре |

Кадр 512 × 320 рисуется по состоянию текущего одномерного симулятора. Он показывает перспективу полосы, стоп-линию, сигналы светофора и стоп-сигналы ведущей машины. Режим оценивает способность Drex работать с синтетическим видеовходом. Аварийное торможение использует ту же дистанцию из симулятора во всех режимах.

Для отдельного прогона можно указать `bash scripts/drex_drive/submit.sh warm red_light --observation camera`. В пакетном запуске `suite.json` обновляется после каждой поездки и содержит исход, нарушения, число просрочек и p95 задержки применения команды. Полные отчёты лежат в папках вида `red_light-camera/`. В `trace.jsonl` записаны имена входных изображений относительно папки поездки. Метрика `capture_p95_wall_s` учитывает подготовку наблюдения и рендеринг кадра. Дедлайн отсчитывается от начала этой подготовки. Для локального тестирования рендерера нужен Pillow из окружения Drex.

## Один кадр и два кадра при торможении

```bash
bash scripts/drex_drive/submit.sh suite braking
```

Одна загрузка Drex Max, 12 поездок. На каждом из четырёх вариантов `lead_brakes` запускаются `camera`, `camera-pair` и `state-camera`. Начальный зазор составляет 7,5 или 10,5 м. Ведущая машина начинает тормозить на 2-й или 4-й секунде, а через 5 секунд после начала торможения снова трогается. Первый `lead_brakes` совпадает с прежним сценарием.

`camera-pair` передаёт кадры в порядке «предыдущий, текущий», с интервалом 0,5 секунды симуляции. При первом запросе доступен один кадр. Если запрос пропущен из-за занятого инференса, его кадр всё равно сохраняется в истории, чтобы интервал следующей пары остался равен 0,5 секунды. Прогрев проверяет формы с одним и двумя изображениями. Числовых данных о ведущей машине в `camera` и `camera-pair` нет.

В итоговом `suite.json` сравнивай зазор, аварийное торможение, финиш, просрочки и p95 до команды. `lead_braking_phase` содержит зазор и аварийные вмешательства за всё время от начала торможения лидера до его повторного старта. `first_driver_brake_offset_s` — время от начала этого окна до первого физического замедления по команде модели внутри окна. `paired_decisions_applied` показывает, сколько применённых команд получили два кадра, а `frame_ticks` в трассе связывает изображения с тиками симулятора.

## Камера с имитацией радара

```bash
bash scripts/drex_drive/submit.sh suite radar
```

Одна загрузка Drex Max, 16 поездок в реальном времени. Каждый из четырёх вариантов `lead_brakes` проходит в четырёх режимах с одним фронтальным кадром. Дедлайн остаётся равен 500 мс.

| Режим | Дополнительные данные о ведущей машине |
| --- | --- |
| `camera` | Ведущая машина видна в кадре |
| `camera-range` | Зазор между бамперами в метрах |
| `camera-radar` | Зазор и скорость сближения в м/с. Положительное значение означает уменьшение зазора |
| `state-camera` | Прежние структурированные данные, включая зазор и абсолютную скорость лидера |

Радарные значения берутся из текущего состояния симулятора без шума. При отсутствии лидера передаётся `lead_radar: null`. Drex Max выбирает все обычные действия. В `suite.json` сравнивай финиш без вмешательств, первый момент самостоятельного замедления, минимальный зазор, число аварийных шагов и p95 до применения команды.

## Пилот на прямых участках NAVSIM

На `msu270` из корня ветки `codex/drex-drive`:

```bash
bash scripts/drex_drive/straight.sh connect
bash scripts/drex_drive/straight.sh prepare
bash scripts/drex_drive/straight.sh submit
```

`connect` использует прежний SSH-туннель к Astra и при необходимости просит авторизацию в терминале. `prepare` извлекает до восьми TRAIN-сцен из прежнего аудита `pool64_v1`, по одной на сессию. Сцены выбираются по текущей скорости, геометрии маршрута и статическому контуру машины. Проверяем достижимый за 4 с участок длиной до 40 м, без пересечения карты перекрёстка, с отклонением от исходной оси до 0,8 м и изменением направления до 5°. Результаты DriveSuprim при выборе сцен не используются.

Drex получает только текущие начальные наблюдения и последующие прогнозные измерения при постоянной скорости лидеров. Вместо камеры в первом пилоте используется структурированный зазор и скорость сближения. На каждом шаге 0,5 с Drex выбирает действие, из которого получается часть собственной траектории. Горизонт — 4 с, 40 поз в системе начальной задней оси. Проверяется продольное управление с фиксированным курсом и экспериментальным пределом 10 м/с.

После завершения GPU-задания из лога `logs/straight-НОМЕР.log`:

```bash
bash scripts/drex_drive/straight.sh score
```

Astra пересчитывает исходную траекторию DS по архивному протоколу с нереактивным трафиком и проверяет совпадение всех исходных raw-компонентов. После этого тот же PDM-скорер оценивает траекторию Drex для того же токена и кеша. В `/scratch/pr0201/drex_runtime/runs/navsim-straight-train-v1/report.json` будут парные оценки, средние дельты, ухудшения компонентов и отдельный учёт ошибок инференса. `DREX_STRAIGHT_NAME` задаёт имя нового прогона, а `DREX_STRAIGHT_SCENES` меняет целевое число сцен на этапе `prepare`.

Для повторного теста с уточнённой инструкцией выбора `slow` и `maintain` запусти `bash scripts/drex_drive/straight.sh progress-test`. Он копирует исходный `observations.json` байт в байт, ждёт GPU-задание и запускает тот же скорер Astra. Результат сохраняется в `runs/navsim-straight-progress-v1/`. Веса, действия, предел скорости и прогноз лидера совпадают с первым пилотом. В отчёте сохраняется `prompt_variant`, чтобы сравнивать варианты по исходным триплетам «токен, кеш, оценка DS».

`bash scripts/drex_drive/straight.sh forecast-test` повторяет те же сцены с исходной инструкцией. К радару добавляются два прогноза зазора в метрах через 1 и 2 секунды при удержании текущей скорости. Расчёт использует текущий зазор и скорость сближения. Отрицательный прогноз соответствует продольному перекрытию в этой модели. При отсутствии лидера `lead_radar` остаётся `null`. Отчёт в `runs/navsim-straight-gap-forecast-v1/` помечается `observation_variant: gap-forecast`.

### История лидера и последствия команд

```bash
bash scripts/drex_drive/straight.sh next-tests
```

Один GPU-прогон загружает веса один раз и выполняет два варианта на исходных восьми сценах. Оба используют исходную инструкцию и два поля `gap-forecast`.

- `leader-history` добавляет продольные скорости того же лидера из двух последних кадров перед началом сцены. Оба возраста считаются по временным меткам. При отсутствии соответствующего трека список пуст. Прогноз движения в контуре по-прежнему предполагает постоянную скорость лидера.
- `action-effects` добавляет ожидаемое продвижение и минимальный зазор на горизонте 2 с для каждой команды. Команда действует первые 0,5 с, затем удерживается достигнутая скорость. Drex выбирает команду, после чего симулятор продвигается на 0,5 с.

Для истории используется только `past_detections_tracks`. Во время оценки Astra проверяет совпадение с кешем. `suite.json` в `runs/navsim-straight-extra-inputs-v1/` содержит покрытие истории, сравнение с DrSu и `gap-forecast`, ошибки инференса и ухудшения компонентов безопасности. В `leader-history/` и `action-effects/` сохраняются отдельные отчёты и действия. Для сравнения используется готовый `runs/navsim-straight-gap-forecast-v1/report.json`.

### Зарезервированные поездки NAVSIM

```bash
bash scripts/drex_drive/straight.sh fresh-test
```

Тест фиксирует исходную инструкцию и `action-effects` из TRAIN-пилота. Astra берёт зарезервированные поездки из манифеста `selector_data_expansion_v2`, проверяет отсутствие пересечений с прежним TRAIN, строит отдельные кеши и применяет исходный геометрический фильтр ко всем 64 зарезервированным сценам. Drex на MSU получает только начальное наблюдение для каждой прошедшей фильтр сцены. Astra запускает исходный чекпойнт DrSu на камерах тех же сцен. Воспроизведение траектории и raw-компонентов DrSu проверяется на одной исходной TRAIN-сцене. Оба прогноза оцениваются одним нереактивным PDM-скорером на одном кеше для каждой пары.

В `runs/navsim-straight-fresh-v1/report.json` сохраняются средний PDM, парные дельты по компонентам, число побед, равенств и поражений, ухудшения безопасности и результаты по поездкам с равным весом. Если строгий фильтр исключит все сцены, отчёт зафиксирует причины. По умолчанию DrSu использует GPU 0 в контейнере Astra. `DREX_ASTRA_DS_GPU` меняет номер устройства, а `DREX_ASTRA_ACQUISITION` и `DREX_ASTRA_FRESH_CACHE` задают каталоги входов и изолированных кешей Astra.

Если прогнозы Drex уже сохранены, `fresh-score` запускает только получение траекторий DrSu и оценку. При недоступной CUDA на Astra укажи CPU:

```bash
DREX_ASTRA_DS_DEVICE=cpu bash scripts/drex_drive/straight.sh fresh-score
```

Отчёт указывает устройство в `ds_inference_device`. Проверки исходного чекпойнта, архивной траектории и её метрик действуют также на CPU.

### Мягкий разгон и торможение

```bash
bash scripts/drex_drive/straight.sh gentle-test
```

Диагностический прогон использует те же сцены, что завершённый `fresh-test`, и добавляет две команды к пяти исходным. `gentle_proceed` задаёт +1 м/с², а `gentle_slow` задаёт −0,75 м/с². Drex оценивает все семь команд. Для каждой команды рассчитываются продвижение и минимальный зазор по тому же правилу `action-effects`. Период решения остаётся 0,5 с, горизонт траектории 4 с, предел скорости 10 м/с.

В `runs/navsim-straight-gentle-v1/comparison.json` сохраняются парные дельты к прежнему Drex и DrSu, ухудшения компонентов безопасности и частоты двух новых команд. Сравнение проверяет идентичность наблюдений и оценок DrSu. DrSu по умолчанию считается на CPU, как в исходном прогоне. Отдельные файлы `report.json` и `predictions.json` содержат оценки и траектории нового варианта.

### Пересчёт отдельных решений на Astra

```bash
bash scripts/drex_drive/straight.sh action-probes
```

Скрипт берёт пять сохранённых траекторий стандартного `action-effects` из `runs/navsim-straight-fresh-v1/` и воспроизводит команды с прежним шагом 0,5 с. В сцене `98ad6d2817355b99` заменяет `maintain` на `proceed` в 0,5 с, в `9f64bdb900585e9c` и `3643e0160ea75932` заменяет первый `slow` на `maintain` в 1,5 и 0 с соответственно. Остальные команды берутся из архива.

Astra воспроизводит метрики всех пяти исходных траекторий и оценивает три изменённые на тех же кешах. Сравнение с DrSu использует его архивные оценки. GPU и инференс моделей для этого прогона не требуются. В `runs/navsim-straight-action-probes-v1/report.json` сохраняются парные дельты по сценам, нарушения безопасности и комфорта и средние по трём изменённым и всем пяти сценам. Это диагностика заранее выбранных замен на уже разобранных сценах.
