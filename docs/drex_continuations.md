# Проверенная конечная цепочка продолжений

`schedule_replacement.py` — отдельная служебная программа на стандартном Python.
Она не изменяет `replacement.py`, `run_replacement.sh` и замороженные входы.
Новые файлы не входят в списки source hashes работающего эксперимента.

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
export DREX_REPLACEMENT_NAME=replacement_gpu2_v1

python3 -B -m unittest discover -s scripts/drex -p test_schedule_replacement.py -v &&
python3 scripts/drex/schedule_replacement.py submit --after 288789 --passes 2 --gpus 2
```

Исходное состояние: первый проход закончился по семичасовому лимиту; второй,
288789, работает; других отложенных продолжений нет. `--passes 2` означает ещё
два GPU-прохода **после** текущего, не две GPU и не два часа.
Программа проверяет текущую очередь: predecessor должен быть вашей работающей
GPU-задачей, другой старой цепочки не должно быть. Если задача уже завершилась,
сначала проверьте её логи, а затем используйте обычный `resume 2` либо выберите
актуальный работающий predecessor. Не меняйте predecessor на ID CPU-отчёта.

Первая маленькая CPU-задача ждёт `afterany:288789`. После его завершения она:

1. Остановится, если все worker commits уже существуют: следующий GPU-проход не нужен.
2. Проверит логи всех рангов именно этого GPU Job ID. Нужна штатная ошибка
   `Worker time budget reached`; другой traceback, CUDA OOM, отсутствие логов,
   системный OOM или внешний TIME LIMIT блокируют автоматическое продолжение.
3. Вызовет неизменённый `run_replacement.sh resume 2`, который создаёт GPU-задачу
   и зависимый CPU-отчёт.
4. Запишет фактические новые GPU/report Job ID и поставит следующий CPU callback
   с `afterany:<новый GPU Job ID>`. Поэтому callback не зависит от краткоживущего
   предыдущего callback и не запускает конкурирующее продолжение.

Максимум два новых GPU-прохода. Автоматической бесконечной цепочки нет, и успех
за четыре прохода не гарантируется: скорость и очередь меняются. После полного
завершения worker-ов очередной callback ничего не запускает.

CPU callbacks запрашивают 1 CPU, 512M RAM, 5 минут на ранее проверенном узле
из `setup_node.txt`, без GPU. Между callbacks нет постоянно работающего процесса.
После постановки можно отключиться от SSH. Ручной `resume` параллельно цепочке
не запускайте.

```bash
squeue -u "$USER" -o "%.18i %.35j %.10T %R"
python3 "$HOME/drivesuprim/scripts/drex/schedule_replacement.py" status --gpus 2
```

Метаданные: `runs/replacement_gpu2_v1/scheduler/after-<GPU ID>.json`.
Логи: `$DREX_RUNTIME_ROOT/logs/resume-chain-<callback ID>.log`.
В метаданных фиксируются hashes плана, launcher и самой служебной программы.
После её обновления существующая цепочка остановится для проверки, а не изменит
поведение незаметно. Повторный `submit` того же predecessor и того же числа
проходов возвращает уже сохранённый callback Job ID.

Запись намерения делается до sbatch/resume. Если процесс прервётся между отправкой
заявки и сохранением ответа, программа блокирует слепую повторную отправку.
Такие состояния `submitting`/`resuming` требуют просмотра очереди и логов.
Состояние `gpu_submitted` можно дообработать без повторения GPU-заявки.

Локальные тесты подставляют sbatch/squeue/resume и проверяют конечную цепочку,
ошибки обеих GPU, раннее завершение, повторные вызовы, повреждение привязок,
реальную передачу callback через stdin и синтаксис его Bash-обёртки.
Они не являются реальным выполнением Slurm на сервере. Для данного сервера
дополнительно подтверждены Bash 5.2.21, Slurm 23.02.4, доступные на cn29 sbatch,
Python и launcher; окончательное выделение ресурсов зависит от кластера.
