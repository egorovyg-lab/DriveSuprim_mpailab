# Таблица, фотография и итоговый рейтинг DriveSuprim

Два независимых запуска: CPU-аудит двух известных случаев на Astra и GPU-эксперимент
на всех 651 сцене / 32 сессиях исходного `table_topk_night_gpu8_v1`.
Новые результаты сохраняются отдельно; код и результаты старого эксперимента не меняются.

## Что проверяется

Фиксированный top64, одинаковые анонимные ID и три исходные перестановки.
Изображение: отсутствует / пустая доска / настоящая доска камер.
Рейтинг: `ds_score_gap` присутствует / удалён вместе с его пояснением.
Прогнозы отдельных метрик DS, imitation log probability, кинематика и геометрия
сохраняются. Это проверка влияния **итогового рейтинга**, а не удаления всех
подсказок DS. Состав top64 также по-прежнему определяет DS.

Пустая доска сохраняет размер 1536×640 и точные заголовки камер/времени,
заменяя области фотографий белым фоном. Текст запроса и кандидаты внутри каждой
пары real/blank совпадают; изображение остаётся настоящим визуальным входом модели.

Все шесть условий считаются заново: 651 × 6 × 3 = **11 718 запросов**.
Два full-условия имеют точно такие же входы, как старый запуск на top64,
но старые вероятности не подставляются. При изменении числа GPU вычислительное
окружение может повлиять на численную повторяемость; это новый запуск.

Главное сравнение, заранее записанное в новом плане:
`road_minus_blank/full/mean3` — полезна ли информация настоящей фотографии при
сохранении формата ввода. Также считаются real−none, blank−none, hidden−full
и взаимодействие `(road−blank)_hidden − (road−blank)_full`.
Вероятности сначала сопоставляются физическим кандидатам, затем усредняются по
трём порядкам. При точном равенстве сохраняется DS, как в исходном протоколе.

Это исследовательское повторное использование train-данных после просмотра
результатов. Интервалы кластерного bootstrap по сессиям не превращают его в
независимую проверку. Holdout не открывается. Измеряется raw local PDM, не EPDMS.

## Обновление и ночной запуск на msu270

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime

# Одна GPU allocation. Выбрать 1, 2, 4 или 8.
bash scripts/drex/run_table_factorial.sh submit-night 4
```

Последовательность: CPU-тесты → замороженный CPU-план → **одна задача на N GPU** →
CPU-отчёт. Внутри GPU-задачи сначала на каждом GPU выполняются все 18 условий/порядков
одной сцены. Только после успеха всех рангов запускается полный проход. При ошибке
любого ранга останавливается весь srun, следующий этап не запускается.
Каждый процесс загружает отдельную копию Drex на один A100; уникальность физических
GPU проверяется UUID-барьером. Модель не делится между GPU.

Для 4 GPU запрашиваются 16 CPU и 384G RAM; для 8 — 32 CPU и 768G.
Allocation ждёт одновременного освобождения всех запрошенных GPU. Это не обещание
немедленного старта в общей очереди. После `Submitted` можно отключиться от SSH.
Лимит GPU-задачи по умолчанию 8 часов. На 1 GPU разумно выполнить полный проход
несколькими `resume`: отдельный worker сохраняет частичные результаты и останавливается
после 7 часов; неполный проход не считается успешным и не формирует отчёт.

Отдельный короткий запуск:

```bash
bash scripts/drex/run_table_factorial.sh submit-pilot 4
# После успеха — тот же план/имя/число GPU, без повторения готовых запросов:
bash scripts/drex/run_table_factorial.sh resume 4
```

Если уже использовали `submit-night`, дополнительный `resume` нужен только после
остановки неполного прохода. Не запускайте два задания на один и тот же shard.
Изменение числа GPU требует нового имени:

```bash
export DREX_FACTORIAL_NAME=table_factorial_gpu8_v2
bash scripts/drex/run_table_factorial.sh submit-night 8
```

## CPU-аудит на Astra

```bash
# На msu270: CPU-подготовка проверяет все исходные commitments и labels.
bash scripts/drex/run_table_pair_audit.sh prepare
bash scripts/drex/run_table_pair_audit.sh connect
bash scripts/drex/run_table_pair_audit.sh start
```

`prepare` выполняет те же мини-тесты и формирует SHA-связанный запрос из реально
сохранённых решений. `connect` использует прежнее SSH-подключение к Astra; пароль
вводится только интерактивно. `start` запускает мост через nohup, можно выйти из SSH.
На Astra обновлять репозиторий не требуется: инструменты передаются автоматически
в `/workspace/exp_v2/drex_rollout_audit/rollout_audit_table_pairs_v1`.

Сравниваются:

* `case01`: `d6e7f58f94d458b4`, DS/камера против таблицы, фокус NC;
* `case02`: `df1898fb8e6953ee`, DS/камера против таблицы, фокус lane keeping.

`member0` всегда DS/камера, `member1` — таблица. Получаем четыре воспроизведения,
восемь компонентов и PDM должны совпасть с исходными top16 labels. Только при
`geometry_interpretation_ready=true` и `metric_parity_passed=4` интерпретируем
геометрию. Если возникнет `No bound cache index`, это ошибка разрешения исходного
cache, а не признак того, что нужно ждать GPU или ещё один результат.

Результат содержит `camera.png` (синий nominal, оранжевый simulated), `map.png`,
`trace.csv`, `traces.npz`, `summary.json` для каждого кандидата, а также парные
сравнения в `report.json`. В первом случае сохраняются время первого at-fault
контакта и пересекающиеся объекты; во втором — расстояния до scorer centerline,
исключение intersections и окно квалификации lane keeping. Пересечение с объектом
само по себе не является новой классификацией виновности.

Карта, будущие участники движения и истинные события используются только в аудите.
Они не передаются Drex. Проекция на текущую камеру предполагает плоскую дорогу и
не проверяет окклюзии. Эти два случая выбраны по результатам, не являются выборкой
для измерения качества модели.

## Статус и результаты

```bash
squeue -u "$USER"
bash scripts/drex/run_table_factorial.sh status 4
bash scripts/drex/run_table_pair_audit.sh status

cat /scratch/pr0201/drex_runtime/runs/table_factorial_gpu4_v1/report.json
```

Логи Slurm: `/scratch/pr0201/drex_runtime/logs/factorial-*.log`.
В итоговой папке: `plan.json`, `identity.json`, `decisions.json`, `decision_commit.json`,
`per_scene.csv`, `report.json`, commits всех worker-ов. `per_scene.csv` содержит
отдельные порядки и mean3, ранг кандидата, компоненты и изменение PDM.
Пять компонентов relative harm перечислены в отчёте; lane keeping отдельно
учитывается в `component_degradations` и снижениях PDM.
Отчёт читает labels только после проверки commitments всех новых решений.
Технические ошибки сохранены; они не повторяются автоматически до удачного ответа.

Результаты CPU-аудита находятся в каталоге, указанном `latest_result.json`:
`/scratch/pr0201/drex_runtime/runs/rollout_audit_table_pairs_v1/result_<sha>/`.
Сначала пришлите оба `report.json`; затем нужны summary/кадры конкретных событий.

## Локальная проверка

```bash
python -B -m unittest discover -s scripts/drex -p test_table_factorial.py -v
```

Тесты используют маленькие искусственные данные и подставные sbatch/srun, без сети,
весов и CUDA. Проверяют совпадение исходных входов full-условий, чистоту удаления
рейтинга, формат blank, выравнивание ID, возобновление, запрет раннего чтения labels,
контроль порчи результатов, параметры Slurm и остановку после неудачного mini.
Реальный scorer/контакт и работу Drex проверят серверные этапы, не локальный тест.
