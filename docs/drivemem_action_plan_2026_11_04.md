# DriveMem: план после memory-пилота и development oracle

Дата: 4 ноября 2026 года.

Основание: исходный `DriveMem_план_статьи_6_месяцев.pdf`, исследовательская ревизия от 27 октября, текущая реализация и серверные отчёты, переданные пользователем. Серверные CSV/JSON целиком локально не получены; конкретные распределения по сценам ещё предстоит связать с manifests. Календарь ниже — внутренние ориентиры, не сроки конференции. Документ планирует следующие работы, не сообщает о реализации v2.

## 1. Точка принятия решения

| На тех же 24 development-сценах / 3 сессиях | Результат |
|---|---:|
| Baseline Local PDM ×100 | 88,7651 |
| Similarity memory | +0,0000 п.п.; 2 смены выбора; все измеренные компоненты в них без изменений |
| Similarity threshold | Те же 2 решения; порог допускает 20/24 сцен |
| Random memory | +0,0286 п.п.; 3 смены выбора; 1 улучшение |
| No-memory ridge | −0,2614 п.п.; 16 смен; 5 ухудшений PDM; 1 ухудшение safety-компонента |
| Oracle top-8 | +6,5111 п.п. |
| Oracle top-16 | +6,6449 п.п.; 11/24 сцен улучшаются |
| Safe oracle top-16 | Те же +6,6449 п.п. |
| Покрытие донорами | 24/24 сцен; по 5 доноров; использовано 45/48 эпизодов |
| Разнообразие доноров | В среднем 3,29 донорских сессии на запрос |
| Поправки компонентов | Mean absolute 0,035613; mean candidate-wise std 0,000550 |

Top-8 содержит около 98,0% измеренного резерва top-16. Это наблюдение на development, а не гарантия на других данных. Safe oracle ограничен NC/DAC/DDC/TLC/TTC относительно baseline; абсолютная безопасность и остальные компоненты этим не гарантируются. Local PDM не включает two-frame extended comfort и не равен EPDMS.

Ближайшая научная задача: получить полезное предложение памяти и установить, приносит ли именно выбор опыта пользу относительно контроля без памяти. Наличие хороших кандидатов само по себе не показывает, что их качество можно предсказать из доступных входов и имеющегося банка.

Важное ограничение: на этих 24 сценах oracle-gate над фиксированным нынешним similarity proposal имеет нулевой резерв PDM:

`mean(max(Q(baseline), Q(similarity_proposal))) = mean(Q(baseline))`.

Поэтому обучение отказа к нынешнему proposal не может восстановить +6,64 п.п. на данном наборе. Сначала требуется другой механизм предложения. Исходный тезис статьи о utility и risk остаётся исследовательской гипотезой.

## 2. Правила следующей итерации

1. Сохранить неизменными текущие M/F/V/C/T manifests и историю просмотра результатов. Роли: M 48 сцен/6 сессий, F 32/4, V 24/3, C 16/2, T 16/2. V уже исследован многократно; это development, не подтверждающая выборка.
2. Основной пул первой итерации v2 — top-16 исходного DriveSuprim. Все пересчитываемые memory и no-memory варианты выбирают из одного пула; baseline включён, точные ties разрешаются в его пользу. Старые результаты методов с пулом 256 остаются отдельной таблицей.
3. Top-8 — заранее объявленная абляция. Возврат к полным 256 — последующая проверка зафиксированного метода, с теми же правами выбора у контролей. Переход к top-16 мотивирован уже просмотренным V и раскрывается как решение разработки.
4. Заморозить teacher/checkpoint, vocab, исходные head scores, embedding, ego features, simulator/scorer и формулу imitation. На первом этапе менять только перенос остатков.
5. Новая загрузка данных для ближайшего цикла: 0 GB. Использовать имеющиеся features, cache, labels и сохранённые camera archives. Новые параметры и метки хранить отдельными sidecars.
6. H — снижение любого из NC/DAC/DDC/TLC/TTC с текущим допуском 1e-8. Отдельно сообщать ухудшение PDM, lane keeping, history comfort, progress и абсолютные нарушения. В существующем ridge есть H при нулевом ΔPDM; один scalar score недостаточен для анализа вреда.
7. Никакого обучения/подбора по oracle ranks или outcomes текущих V/C/T. V oracle разрешён как post-hoc диагноз и lookup для уже зафиксированных по M/F решений. Не отбирать запросы только по наличию oracle-выигрыша.

## 3. Этап A: собрать полную таблицу решений на M/F/V

### A1. Разобрать резерв по сценам — без новых симуляций

Из `development_oracle/scenes/*.json`, features и исходных evaluation JSON собрать:

- baseline, лучший top-8/top-16, лучший безопасный top-16; vocab ID и model rank;
- Δ всех восьми компонентов и scalar PDM;
- исходный score gap, скорость/манёвр, donor IDs/sessions/distances;
- веса action kernel, entropy и effective sample size `ESS = 1 / sum(w**2)` для baseline и oracle-действия;
- физические различия траекторий: продольное/поперечное смещение, heading, путь/скорость на доступном горизонте;
- тип неудачи: safety-предсказание, progress/comfort, близкие по геометрии альтернативы, большая дистанция до действий памяти.

Таблицы строить для всех 24 сцен, отдельно для 11 с резервом и 13 без улучшения внутри top-16. Показать вклад каждой сессии, долю выигрыша крупнейшей сцены и sensitivity при удалении каждой сессии. Для иллюстраций заранее взять крупнейший выигрыш, типичный средний выигрыш и случай без резерва; эти картинки не заменяют агрегаты.

Проверить гипотезу сглаживания, а не объявлять её доказанной: близость поправок может возникнуть из-за плоских action weights, сходных донорских residuals, одинакового descriptor или взаимного погашения доноров. Нужно различить эти случаи. Почти постоянная компонентная поправка всё ещё может менять ranking через нелинейный score; сравнивать фактические изменения score и относительные margins для каждой сцены.

### A2. Дооценить F top-16

Сейчас каждая M/F-сцена имеет исходные labels top-8 + 8 случайных остальных кандидатов. Top-16 полностью размечен только для V после oracle. Для честной настройки v2:

- на 32 F-сценах добавить только отсутствующие позиции model rank 9–16;
- максимум 32×8 = 256 новых действий; часть уже присутствует среди случайных labels;
- повторить baseline на каждой F-сцене для parity; потолок 288 reference/candidate evaluations, или 576 raw/filtered scorer calls;
- исходные M labels не расширять на первой итерации, чтобы изменение supervision не объясняло результат;
- сохранить F top-16 в sidecar нового experiment, не дописывать в исходную `labels/`: это сломает frozen fit provenance;
- каждый кандидат оценивать отдельно с reference, fresh cache и исходной нормировкой progress. Нельзя совместно нормировать progress по новым 16 кандидатам.

Разметка не требует GPU или новых изображений. До запуска вывести точное число недостающих действий с учётом существующих labels. При возобновлении проверять hashes и повтор baseline; готовые действия использовать повторно.

**Выход A:** полная lookup-таблица top-16 для F и V, полный разбор V, подтверждённая или отвергнутая гипотеза сглаживания. Она пригодна для оценки многих фиксированных reranker-решений без последующих simulator calls.

## 4. Этап B: минимальная action-dependent memory

Сначала оставить текущие geometry descriptors, совместимость по command, visual/velocity retrieval, 5 доноров и их равные веса. Это позволяет проверить перенос действий до одновременной смены представления сцены.

Текущий перенос использует `exp(-distance / 0.25)` по всем размеченным действиям донора. Даже далёкие действия после нормировки получают суммарный вес 1; большой bandwidth может усреднять почти одинаково все кандидаты. Для каждого режима логировать absolute support — nearest distance до размеченных действий; нормированный softmax сам по себе не является уверенностью в наличии поддержки.

### B1. Четыре семейства, один фактор за раз

| Семейство | Action kernel | Перенос |
|---|---|---|
| B0 | Исходный bandwidth 0.25 | Абсолютный residual, воспроизведение v1 в top-16 |
| B1 | Локальный bandwidth, выбранный по M/F | Абсолютный residual |
| B2 | Исходный bandwidth 0.25 | Контраст residual относительно baseline |
| B3 | Локальный bandwidth, выбранный по M/F | Контраст residual относительно baseline |

Определить остаток донора `r_e(b) = y_e(b) - p_e(b)` и его перенос на действие query `m_e(q,a) = sum_b w_h(a,b) r_e(b)`.

Для контрастного варианта:

`c(q,a) = mean_e [m_e(q,a) - m_e(q,a0)]`,

`p_new(q,a) = clip(p(q,a) + beta * c(q,a), 0, 1)`.

Затем сохранить текущую конструкцию:

`S_new(a) = S_original(a) + G(p_new(a)) - G(p(a))`.

Здесь `G` — исходное metric-слагаемое DriveSuprim; imitation остаётся внутри `S_original`. При `a=a0` контраст равен нулю. Это гипотеза, требующая сравнения B1/B2/B3: привязка к baseline может убрать полезную общую калибровку и не обязана улучшать результат.

Структурное ограничение executed-only: если у донора одно действие, нормированные внутри эпизода action weights всегда равны 1. Тогда `m_e(q,a)` одинаков для всех a, и B2/B3 становятся нулевыми. Даже идеальная настройка bandwidth это не исправляет. В текущем цикле B2/B3 проверяются именно как simulator-enriched метод. До утверждения о переносе естественно накопленного опыта нужен отдельный executed-only механизм: например, совместные веса `K_scene(q,e) * K_action(a,b_e)` по действиям разных эпизодов, с контролем абсолютной поддержки, вместо нормировки единственного действия отдельно внутри каждого эпизода. Его нельзя объявить простой абляцией числа labels при сохранённой вырождающейся формуле. Короткую проверку этой конструкции выполнить до масштабирования банка; полноценное сравнение — после работающего enriched proposer.

Нельзя заменить её вычитанием одной константы из scalar score всех кандидатов: такое вычитание не меняет ranking. Нельзя автоматически трактовать скорректированные heads как калиброванные вероятности.

### B2. Ограниченный выбор параметров

- Первый факторный эксперимент: `beta=0.5`, `k=5`, исходные descriptors/scene retrieval зафиксированы.
- Оценить scale `h0` только по M: по очереди считать M-эпизод запросом, исключить всю его сессию из доноров, взять текущие 5 совместимых доноров и для каждого query top-16 действия найти ближайшее строго положительное расстояние до их размеченных действий. `h0` — медиана этих расстояний по всем таким запросам. Нулевые расстояния при совпадении vocab ID учитывать отдельно; если положительных расстояний недостаточно/нет, остановить автоматическую настройку и разобрать descriptor, а не делить на ноль. Единицы h — те же mean squared geometry distances, что в исходном `exp(-d/h)`.
- Для локального kernel проверить только `h ∈ {0.5 h0, h0, 2 h0}` на F. Исходный 0.25 остаётся отдельным контролем.
- Выбрать один h внутри каждого локального семейства по среднему ΔPDM на F, усредняя сначала по сессии. При равенстве — меньше H, затем более простой вариант. Это селектор качества, не процедура контроля риска.
- Сохранить все четыре семейства, выбранные параметры, результаты F и hashes в manifest до чтения V outcomes новым evaluator.
- Основного кандидата v2 также назвать по F до V; остальные семейства заранее объявлены абляциями и сообщаются целиком. Нельзя после просмотра V переименовать удачную абляцию в заранее выбранный основной метод.
- Только после проверки факторов допустима одна отдельная F-абляция beta `{0.25, 0.5, 1.0}`; не запускать одновременно большую сетку k × geometry × bandwidth × beta × representation.

Проверки реализации: нулевая коррекция возвращает настоящий baseline; совпадение vocab/local ID проверяется; no donor возвращает baseline; перестановка кандидатов/доноров с сохранением IDs не меняет физический выбор; history/current ego indexing совпадает с exporter; future fields не входят в признаки. Проверка нулевого beta не заменяет проверки правильности самой коррекции.

## 5. Этап C: сильные контроли и первый decision gate

### C1. Справедливые контроли

Пересчитать в том же top-16:

1. Frozen DriveSuprim.
2. Исходную similarity memory B0.
3. B1/B2/B3 после F-настройки.
4. Победившее семейство со случайными совместимыми донорами — три заранее заданных seed, со средним и разбросом; не выбирать удачный seed.
5. Scene-only residual: одинаковая переносимая поправка для всех действий query. Это контроль необходимости различать действия; нелинейный G может дать ненулевой эффект даже этому контролю.
6. Усиленный no-memory ridge на той же доступной supervision M+F, том же пуле и наблюдаемых query-входах.

Для ridge выбирать регуляризацию из `{1, 10, 100, 1000}` по leave-one-F-session-out: на каждом fold обучать на M + остальных трёх F-сессиях, проверять на исключённой F-сессии. После выбора переобучить на M+F. Все нормировки, обучаемые проекции и настройки строго ограничены обучающей частью fold либо M.

Сейчас memory использует полный visual embedding, а ridge — случайную 12-мерную проекцию. Это возможный confound. Проверить ridge с доступом к полному embedding через подходящий регуляризованный solver либо сравнить оба метода на одной и той же заранее фиксированной проекции. Добавление параметров без контроля числа независимых сессий не делает baseline сильнее.

### C2. Метрики и критерии

Показать macro-session и micro-scene ΔPDM, raw/filtered компоненты, число улучшений/ухудшений, actual intervention coverage, H among interventions и на всех сценах, absolute violations, время решения и размер банка/модели. Retrieval acceptance и actual coverage — разные величины. Сравнение с ridge — paired delta методов, а не вычитание независимых CI.

Дополнительно: top-16 oracle regret, доля покрытого резерва, результаты по baseline failures и oracle-positive сценам (только post-hoc срезы), per-session sensitivity. Долю резерва считать как `sum(Q_method - Q_baseline) / sum(Q_oracle16 - Q_baseline)`, не усреднять отношения с нулевым знаменателем на отдельных сценах; отрицательные gains не обрезать. Не требовать увеличения candidate-wise std или coverage как самостоятельного успеха: они могут вырасти из-за шума.

Инженерная цель для первого кандидата v2 — хотя бы 0.5–1.0 п.п. среднего выигрыша на этом V (примерно 7.5–15% нынешнего oracle-резерва), полезные изменения более чем в одной сессии и отсутствие зависимости всего вывода от одного кадра. Это ориентир для решения о затратах, не статистический порог доказательства и не основание выбрать настройки по V. Отдельно сравнить с усиленным no-memory контролем; положительный gain над baseline ещё не доказывает пользу retrieval.

Нулевой H на малом числе вмешательств не считается доказательством безопасности. Не усиливать память искусственно, чтобы специально получить вредные примеры для статьи.

### C3. Развилки после одного фиксированного прогона V

| Наблюдение | Следующее действие |
|---|---|
| Коррекция остаётся плоской | Проверить action descriptor/weights/остатки. Одна целевая правка, а не новый набор сложных сетей |
| Коррекция различает действия, PDM не растёт | Проверить переносимость донорских residuals и связь доступных признаков с полезными действиями |
| Память растит PDM, но уступает ridge | Продолжить сильный no-memory контроль; оснований для центрального memory claim пока нет |
| Память сравнима со случайными донорами | Выбор опыта не обоснован; проверить scene retrieval, до усложнения gate |
| Полезные предложения есть, также есть harm/разброс | Перейти к utility/gating после подтверждения на дополнительных сессиях |
| Есть gain и мало/нет harm | Оценить неопределённость; не обещать необходимость сложного risk gate |

Бюджет разработки до первой проверки на новых сессиях: не более двух явно описанных циклов изменения механизма. Историю вариантов сохранять. Не повторять бесконечный подбор на трёх V-сессиях.

## 6. Если геометрического переноса недостаточно

Диагностировать достижимый эффект внутри семейства предложений: заранее фиксированные политики «один совместимый donor», B1/B3 и несколько h формируют действия только по доступным query/M-признакам. На уже размеченном V top-16 post-hoc выбрать лучшее из этих предложений для каждой сцены. Это oracle выбора донора/политики, не deployable метод и не основание обучать predictor на V.

- Если даже эта богатая семья не даёт полезных предложений, utility gate над ней проблему не решит. Исследовать представление взаимодействий/динамики или targets переноса.
- Если лучший donor-перенос полезен, а nearest — нет, появляется предмет для обучения релевантности/полезности найденного опыта.

Следующая ограниченная итерация при необходимости — query/donor признаки доступной истории: delta speed/acceleration, направление движения, доступная динамика сцены. У текущего visual embedding не установлена способность описывать взаимодействия; «эпизодическая» память в исходном PDF требует временной информации. Новые поля должны быть доступны всем контролям. Не добавлять ground-truth future tracks, collision checker по истинному будущему или simulator outcomes в query features. Объекты/карта допустимы только при явно объявленной постановке и равных входах baseline.

Сначала использовать уже сохранённые ego/history данные. Новый GPU export temporal visual features — отдельное решение после анализа причины, с новым hash/version и проверкой неизменности базового planner.

## 7. Этап D: расширение без большой загрузки

Перед utility и серьёзными выводами добавить независимые сессии.

1. Проверить наличие четырёх сжатых архивов в общем кэше и перечислить все содержащиеся в них подходящие сессии, используя metadata и архивный mapping.
2. Исключить все сессии, чьи outcomes уже использовались при разработке, и отдельно сохранить резерв существующих C/T. Нельзя перенести их в M/F/V под новым root. Сессия сохраняет историю использования даже при выборе новых кадров.
3. Если есть доступные новые сессии, до оценки сформировать V2 — подтверждение механизма, отдельно M2/F2 при расширении обучения. Выбрать кадры без использования качества. Пожелание: 12–20 новых V2-сессий по 4–8 сцен; фактическая достижимость проверяется metadata inventory.
4. Извлечь дополнительные требуемые камеры из уже скачанных архивов: новый трафик 0 GB, но новые cache/export/labels потребуют вычислений. Если новых сессий в них недостаточно, это явно показать. Дополнительные кадры прежних трёх сессий увеличивают объём данных, но не число независимых сессий.
5. При необходимости новой загрузки сначала представить конкретный план: добавляемые независимые сессии, архивы, bytes и место на диске. Повторно не переходить к 449 GB по умолчанию.
6. На V2 оценивать union действий заранее зафиксированных методов и повтор baseline, а не oracle 256 для каждого запроса. Небольшой заранее выбранный oracle-срез допустим для проверки резерва/регретов.

Новые выборки из тех же дешёвых архивов не устраняют смещение archive-budget отбора. Позже для основного вывода нужна более широкая session-stratified оценка. Географическую/временную близость сессий проверять отдельно от удаления суффикса log_name.

**Условие перехода D:** воспроизводимый полезный эффект на нескольких новых сессиях и понятное сравнение с равным по входам/supervision no-memory методом. Если оно не выполнено, сузить claim или переработать механизм; не маскировать неработающую память теорией отказа.

## 8. Этап E: utility и риск после фиксации proposal

Заморозить версию memory proposer. Предпочтительно собрать новый F_utility по сессиям после выбора proposer на исходном F: разметка union baseline/proposal заметно дешевле полного top-16. Для каждого обучающего запроса сформировать targets ΔPDM, Δ восьми компонентов и H. Если приходится повторно использовать M/F, нужны session-level out-of-fold predictions: вся сессия запроса исключается из donor bank и обучения связанных predictor/representation; гиперпараметры proposer также выбираются только внутри обучающей части fold. Один глобальный выбор h по всем F с последующим объявлением его F-предсказаний out-of-fold недостаточен. Изменение proposer требует новой версии targets. Сам utility predictor также проверяется по сессиям, а не случайному разбиению пар.

Начать с простого регуляризованного predictor по исходным query features, паре действий, score gaps, donor distance, support, ESS и disagreement. Более сложную модель добавлять после проверки групповой обобщаемости. Пары с разными донорами увеличивают число targets, но не число независимых сессий. Если мало полезных/вредных вмешательств, сначала расширить F по сессиям; не выдавать 80 сцен/10 сессий за достаточную обучающую базу большой сети.

Сравнить baseline, ungated proposer, distance gate, utility gate и затем calibrated gate при сопоставимом actual intervention coverage. Пороги для графиков и выбора метода задавать до T. Матрица «distance × измеренная utility», ranking вреда и risk–coverage curves должны показать, что utility добавляет сверх similarity. Если distance gate уже объясняет результат, это ограничивает центральный тезис.

Текущая C — 16 сцен/2 сессии — пригодна для smoke-проверки процедуры, но недостаточна для убедительного ограничения малого риска. Заранее определить estimand: `P(H=1 | intervention)` или session-level loss, целевой α и confidence. Для зависимых кадров нужны групповые предположения/процедуры. Для ориентира: при одном фиксированном пороге, независимых принятых решениях и нуле H односторонняя 95% биномиальная верхняя граница ниже 5% требует 59 принятых решений, ниже 1% — 299. Эти числа не применяются напрямую к соседним кадрам и выбору лучшего из нескольких порогов.

Дополнительную C формировать до выбора по её outcomes и после фиксации модели; T не участвует ни в выборе архитектуры, ни в калибровке. Независимость нового модуля от M/F не доказывает независимость от pretraining DriveSuprim на navtrain. При недостаточном C сообщать эмпирический риск с неопределённостью и ограничивать claim; не приписывать формальную гарантию любой процедуре с названием conformal.

## 9. Этап F: закрыть требования статьи

После работающего и проверенного модуля:

- **Полный NAVSIM EPDMS.** Отдельные непрерывные последовательности, исходная adjacency/агрегация, парное сравнение baseline и выбранного метода. Эффект отдельных sparse actions нельзя просто прибавить к EPDMS: two-frame comfort связывает соседние решения.
- **Executed-only vs enriched.** Нынешние M labels — simulator-enriched. Провести сравнение с реально доступной только меткой выбранного прошлого действия и равными правами no-memory baseline. Если сделать contrastную память только на enriched метках, это надо включить в постановку; у executed-only нет внутриэпизодных контрастов альтернатив, и нельзя тайно использовать их для него.
- **Размер банка.** Два-три вложенных размера при одинаковом query set; правила подвыборки/записи без query outcomes; несколько seed. Сначала frozen bank, затем отдельно prequential growing memory: decide → observe → record, с одинаковыми правами контролей.
- **Второй planner / closed-loop.** Сначала короткий integration spike одного выбранного PDM, затем baseline / similarity / лучший memory / gate на ограниченном публичном протоколе. Смена DriveSuprim/NAVSIM на PDM/nuPlan меняет и planner, и среду — это не чистый zero-shot transfer claim.
- **OOD/stress.** Только заранее объявленные группы/сдвиги и замороженные пороги; calibration не гарантирует безопасность при произвольном shift.
- **Позиционирование.** Обновить обзор первичных работ перед фиксацией novelty, не повторять непроверенные названия/статусы репозиториев из PDF как установленные факты.

Работа над текстом идёт сейчас: мотивация и oracle, формализация вмешательства/H, схема данных, отрицательный v1-результат, методика воспроизведения. Короткую проверку ближайших первичных работ начать параллельно этапу A и обновить позднее перед фиксацией novelty; не откладывать выявление прямого совпадения постановок до финальных прогонов. Центральный вывод «utility лучше similarity» появится только после соответствующего сравнения. При отсутствии роста памяти сузить continual claim; при отсутствии формальной калибровки — формулировку risk-controlled.
