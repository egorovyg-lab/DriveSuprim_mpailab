# Диагностика шести пар: 48 запросов

Запрос пользователя: проверить, помогает ли попарное предъявление и показ
габаритов различить пять известных исправлений DS и одно ухудшение Drex.
Это выборка **по известным исходам**, не независимая оценка качества.

## Состав

- `case01` / `0a3804bea43d5ea8`: DS против oracle top16, исправление DAC.
- `case02` / `a75d642049ef528d`: то же, DAC.
- `case03` / `368c895ca59e5537`: то же, DAC.
- `case04` / `85e8c8e8f6c85157`: то же, DAC.
- `case05` / `6394ed413b685026`: то же, NC.
- `case06` / `5e0b5d47dcb5593c`: DS против выбранной `overlay_mean3`
  альтернативы, ухудшившей удержание полосы; ожидается сохранение DS.

Полный исходный v2-прогон проверяется по плану, обязательствам всех 576
результатов и повторному восстановлению решений. Только после этого
подготовка читает старые метки шести сцен и фиксирует пары. Если ожидаемого
исправления/ухудшения нет, запуск останавливается без замены сцены.

`pair_inputs.json` содержит только индексы двух кандидатов. Ожидаемые ответы,
состав случаев и raw scores — в отдельном `expected.json`. Выбор пар использует
исходы; на GPU этот файл не десериализуется. Модель получает только текущую
фотографию, два кандидата, размеры автомобиля, скорость и ускорение.
Нет названий DS/oracle, рейтингов, PDM, токенов сцен и правильных ответов.

Для каждой пары:

1. `centerline`: линия точки привязки пути;
2. `footprint`: та же линия, прямоугольники автомобиля через 0,5 секунды и
   линии перемещения четырёх углов;
3. для каждого представления — `road` и парный `blank`;
4. для каждого условия — исходный и обратный порядок.

Итого `6 × 2 × 2 × 2 = 48`. ID TA/TB назначаются независимо от роли кандидата
и сохраняются при перестановке. Меняются и порядок картинок, и порядок
вариантов ответа. Голубой цвет одинаков для обоих кандидатов.

## Геометрия и параметры

Пользователь подтвердил на Astra параметры объекта по умолчанию из
`inspect.signature(PDMScorer.__init__).parameters['vehicle_parameters'].default`:

```text
width=2.297 m; front_length=4.049 m; rear_length=1.127 m
rear_axle_to_center=1.461 m
```

Они записаны в `scripts/drex/vehicle_profile_astra.json`, его SHA фиксируется.
Прямоугольник строится от задней оси с учётом heading каждого из 40 poses.
Размеры одинаковы в обоих представлениях. Схемы имеют общий метрический
масштаб по двум кандидатам и их габаритам. Фото полностью помещается в
верхнюю часть картинки; схема и подписи находятся ниже, не закрывая дорогу.
Три изображения по 768×640: исходный кадр и два кандидата.

Используется исправленная проекция v2. Недопустимые лучи не рисуются, сегменты
через них не соединяются. Габариты следуют **предложенной** траектории;
это не точное воспроизведение состояний после PDM-симулятора. Набор контуров
и линий углов — приближение, а не точное непрерывное объединение занятых
областей. Плоскость z=0, неизвестные уклоны и перекрытия сохраняют ограничения
v2. Нет карты с истинной drivable area или будущих позиций участников.
Один кадр особенно ограничивает выводы по будущему столкновению.

## Запуск на msu270

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
export DREX_PAIR_SOURCE=overlay_v2_top4_gpu4_v1
export DREX_PAIR_DIAG_NAME=pair_diag_gpu4_v1

bash scripts/drex/run_pair_diagnostic.sh submit 4
```

CPU-подготовка → GPU-массив → CPU merge/report с зависимостью `afterok` на
весь массив. После получения JobID можно отключаться. Каждая GPU держит одну
полную BF16-копию модели. Поддерживаются 1/2/4/8, по 48/24/12/6 запросов на
работника. Распределяются запросы, не шесть сцен, поэтому восемь работников
также имеют работу. Обычная очередь, без захвата всего узла. Старые v1/v2
файлы, решения и отчёты не меняются.

Только CPU-план и превью:

```bash
bash scripts/drex/run_pair_diagnostic.sh submit-plan 4
```

Локальные CPU-тесты в runtime на compute-узле:

```bash
bash scripts/drex/run_pair_diagnostic.sh check 4
```

Статус и результат:

```bash
bash scripts/drex/run_pair_diagnostic.sh status 4
cat "$DREX_RUNTIME_ROOT/runs/$DREX_PAIR_DIAG_NAME/report.json"
```

Логи: `logs/pair-diag-plan-JOBID.log`,
`logs/pair-diag-worker-ARRAY_TASK.log`, `logs/pair-diag-merge-JOBID.log`.
Превью: `preview-case01-footprint-TA.png`, `...-TB.png` и аналоги для
остальных случаев и центральной линии. `preview-case01-reference.png` —
исходное фото. Это те же пиксели, которые фиксируются в запросах к модели.

Имена по умолчанию включают число GPU. При смене количества с явно заданным
именем использовать новое `pair_diag_*` имя. Повтор `submit` разрешён после
завершения/остановки прежней серии в том же каталоге: готовые запросы
проверяются и не повторяются. Технические ошибки сохраняются, автоматического
перезапуска таких запросов нет. Не отправлять дубли одновременно.

## Чтение результата

`report.json` содержит четыре условия, правильность среднего двух порядков,
строгое совпадение ожидаемого выбора в обоих порядках, смены ответа и точные
ничьи. Ничья разрешается в пользу DS, но не считается строгим подтверждением
предпочтения DS. Дополнительно фиксируется политика смены только при выборе
альтернативы в обоих порядках. После обязательства всех 48 ответов и решений
ожидаемые результаты используются для оценки, а `per_case.json` сохраняет
предпочтения, PDM и все компонентные разницы по каждому случаю/условию.

Простые правила дают 1/6 для «всегда оставить DS» и 5/6 для «всегда выбрать
альтернативу». Это подчёркивает смещение выбранной диагностики; пять успехов
сами по себе не устанавливают качество модели. `always_TA_correct` помогает
увидеть влияние идентификатора. `paired_diagnostic_changes` показывает
переходы правильный/неправильный при добавлении фото или габаритов.

Не публикуется средний выигрыш PDM на этих заранее известных ошибках как
benchmark. Следующий полноценный тест должен включать весь фиксированный
набор сцен и все альтернативы; предпочтения Drex не являются калиброванной
вероятностью безопасности. Нет обучения, новых scorer calls или открытия
holdout.
