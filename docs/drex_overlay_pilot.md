# Отдельная фотография с проекцией для каждого кандидата

Изолированный протокол `overlay_top4_v1`. Исходные `real_train64_v1`,
synthetic night и их код не меняются. GPU replicas: **1, 2, 4 или 8**,
по умолчанию 2. Каждая реплика получает одну GPU >=70 GiB с BF16,
96G CPU RAM и 4 CPU. Реальное число одновременно запущенных workers
определяет доступность ресурсов Slurm. Код не вмешивается в чужие задания.

## Что проверяем

Те же 64 train/development-сцены из 32 сессий, без нового отбора по исходам.
Берём top4 по исходным оценкам DS из прежнего top16; baseline в пуле.
Один исходный снимок текущей передней камеры и четыре отдельных изображения
кандидатов. Для каждого кандидата — стабильный случайно назначенный ID,
независимый от ранга DS. ID сохраняется при смене порядка изображений/ответов.

Режимы, по три порядка в каждом:

- `overlay`: дорога и тонкая голубая линия одного кандидата поверх неё;
- `separate`: исходное фото отдельно, кандидат показан схемой без дорожного
  фона. Это сравнение представлений, а не чистый эффект фотографий;
- `blank`: фотографии заменены белыми полями, проекция линии и схемы остаются.
  Текст/ID/размеры/порядок совпадают с overlay; это парный контроль содержания дороги.

Каждый запрос — **пять изображений 768×432**, четыре варианта, скорость и
ускорение, инструкция выбора. Картинки сохраняют пропорции с полями.
Маленькая схема показывает полный четырёхсекундный путь: часть пути может
быть вне поля зрения камеры или позади неё. Не добавляем отсутствующие
проекции и не исключаем такие сцены молча. Исходный снимок без линий помогает
увидеть детали, которые линия или inset могли закрыть в копии кандидата.

Всего **576 запросов**. Основной метод — `overlay_mean3`; сравниваем с DS,
`separate_mean3`, `blank_mean3`, одиночным overlay и фиксированным random_top4.
Два oracle после фиксации решений — top4 и прежний top16 — показывают цену
сужения пула. Новое качество нельзя напрямую приписывать проекции, сравнивая
с прошлым top16: здесь одновременно другая камера/раскладка и размер пула.
Чистое парное сравнение фотографий: overlay_mean3 минус blank_mean3.

## Геометрия и её ограничения

В [конвертере OpenScene](https://github.com/OpenDriveLab/OpenScene/blob/main/DriveEngine/process_data/helpers/nuplan_cameras_utils.py)
поля `sensor2lidar_rotation/translation` заполняются исходными calibration
rotation/translation камеры nuPlan. Используем camera-to-ego:
`p_camera = R.T @ (p_ego - t)`. Не добавляем ещё один произвольный lidar offset.
Это согласуется с преобразованием в локальном `navsim/visualization/private.py`.

Проекция — intrinsics и [Brown–Conrady distortion OpenCV](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html),
реализованные в NumPy без установки зависимостей в замороженный runtime.
Поддерживаются пустой вектор/0 коэффициентов, 4, 5 и 8 коэффициентов.
Неподдерживаемая модель/форма, неверная rotation, отрицательная высота камеры,
несогласованные principal point/размеры кадра вызывают остановку.

**Принимается плоская поверхность `z=0` в текущем ego frame.** Реальный уклон,
future ego pitch/roll, вертикальный профиль дороги и occlusions не восстановлены.
Проекция центра пути не является swept vehicle footprint или доказательством
отсутствия столкновения. Проверки чисел/оси не заменяют просмотра реальных
preview. На подъёмах и при перекрытиях картинка может быть неточной.

## Запуск на msu270

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime

bash scripts/drex/run_overlay.sh check 2
bash scripts/drex/run_overlay.sh plan 2
```

Обе команды CPU-only на сохранённом setup-узле. Plan проверяет исходный пакет,
cohort, калибровки всех 64 сцен, создаёт:

```text
/scratch/pr0201/drex_runtime/runs/overlay_top4_v1/
  plan.json
  projection_diagnostics.json
  preview-TOKEN-0.png     # исходный снимок
  preview-TOKEN-1.png     # отдельный кандидат
  ...-2.png ...-4.png
```

Превью первых четырёх сцен не выбираются по PDM. `projection_diagnostics.json`
показывает translation, distortion и количество видимых сегментов каждого
top4-кандидата. При ошибке: `calibration_error.json` с token и calibration.
Проверить на preview положение пути относительно дороги и начало/конец;
не подбирать параметры по качеству PDM. Подтверждённая ошибка геометрии требует
нового имени/версии протокола. Данные на локальной машине отсутствуют:
геометрические тесты проверены на аналитических примерах; реальные preview
создаются этой командой на сервере.

Короткий GPU-пилот на двух GPU:

```bash
bash scripts/drex/run_overlay.sh submit-pilot 2
```

CPU plan → GPU array из двух workers. Каждый выполняет 18 новых запросов,
то есть по две сцены. Итого первый пилот — четыре сцены/36 запросов.
Статус **partial** штатный: метки ещё не читаются, merge/report не отправляется.
Пилот поддерживает те же варианты 1/2/4/8 GPU: по две сцены на worker.

```bash
bash scripts/drex/run_overlay.sh status 2
# Логи: logs/overlay-worker-pilot-ARRAY_TASK.log
```

Если короткий запуск и изображения корректны, полная серия:

```bash
bash scripts/drex/run_overlay.sh submit 2
```

Или вместо 2 выбрать **1, 4 либо 8**. 64 сцены распределяются по 64/32/16/8
на worker. Для смены числа replicas требуется отдельное имя, поскольку
распределение фиксируется в plan:

```bash
DREX_OVERLAY_NAME=overlay_top4_gpu4_v1 \
  bash scripts/drex/run_overlay.sh submit 4
```

Не отправляйте одновременно две серии в один output. Полный запуск:
CPU plan → GPU array → CPU merge с `afterok` на весь array. После получения
job IDs можно отключиться. GPU workers ограничены четырьмя часами,
короткие — 30 минутами; нормальная очередь без `--immediate`/`--exclusive`.

Готовые запросы проверяются и пропускаются. Завершённый worker не загружает
модель заново. При технической ошибке результат сохраняется для разбора и
не пересчитывается автоматически. Частичный полный worker возвращает ошибку,
поэтому оценка не идёт до полного восстановления серии.

Только после проверки **всех 576 ответов**, одинакового runtime profile и
точных пикселей/текста всех запросов фиксируются `decisions.json` и
`decision_commit.json`. Затем читаются существующие top16 raw labels из NPZ.
Исходный raw PDM не реконструируется по компонентам; нет новых scorer calls,
обучения, future images, navigation-command decoding или открытия holdout.

```bash
cat "$DREX_RUNTIME_ROOT/runs/overlay_top4_v1/report.json"
```

Отчёт содержит оба oracle, gain/CI, ухудшения PDM/компонентов, а также парные
контрасты overlay-vs-blank и overlay-vs-separate с CI по сессиям.
Полные компонентные разницы — `per_scene.json`. Это повторное исследование
train/development-набора, не независимый benchmark или full EPDMS.
