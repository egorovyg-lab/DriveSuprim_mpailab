# Попарная проверка замены DriveSuprim

## Что переносим из рекомендательных систем

1. **Генератор и ранжировщик решают разные задачи.** DS оставляет широкий набор,
   Drex проверяет замену исходного решения. Это близко к разделению candidate
   generation/ranking в [YouTube Recommendations](https://research.google/pubs/deep-neural-networks-for-youtube-recommendations/).
   Полезный кандидат в пуле ещё не означает, что ранжировщик сумеет его выбрать.
2. **Сравниваем относительную полезность.** [RankNet](https://www.microsoft.com/en-us/research/publication/learning-to-rank-using-gradient-descent/)
   обучает ранжирование на парах, а [Pairwise Ranking Prompting](https://arxiv.org/abs/2306.17563)
   использует сравнения пар в LLM. Наш эксперимент проверяет замороженный Drex без
   обучения: перенос результатов текстового поиска на вождение не предполагается.
3. **Отделяем позицию от качества.** В [Unbiased Learning-to-Rank](https://arxiv.org/abs/1608.04468)
   разбирается смещение наблюдаемых кликов и его коррекция. У нас другая ситуация:
   уже есть scorer-labels всех top64 кандидатов, а позиционное смещение возникает
   внутри модели. Поэтому IPS-веса кликов не применяем. Меняем порядок одной пары,
   сопоставляем ответы физическим кандидатам и отдельно измеряем чувствительность.
   Это также не устраняет смещение отбора архивов/сцен.
4. **При недостатке оснований сохраняем исходную политику.** Идея сравнения с baseline
   близка к [SPIBB](https://proceedings.mlr.press/v97/laroche19a.html). Но наш порог
   вероятности предпочтения не является доверительной границей качества. Мы не
   реализуем теоретические условия SPIBB и не заявляем гарантированного улучшения.

Согласованность ответов проверяет только чувствительность к выбранному возмущению.
Согласованно ошибаться возможно. Для калибровки критерия отказа в дальнейшем нужны
отдельные сессии, реальные labels и проверка редких ухудшений. Не обучаем фильтр и
не выбираем лучший порог по результатам этого запуска.

## Замороженный протокол

Источник: полный исходный `table_topk_night_gpu8_v1`, 651 TRAIN-сцена / 32 сессии.
Свежий holdout не открывается. Новые downloads, labels и GPU DriveSuprim не нужны.

Для каждой сцены:

* reference всегда исходная траектория DS;
* каждый из остальных **63** кандидатов top64 — отдельный challenger;
* одна и та же пара в двух порядках; идентификаторы физически выравниваются;
* три входа: таблица / таблица с blank / таблица с настоящими камерами;
* полные исходные DS score gap, component heads и imitation prior сохранены;
* в таблице только два кандидата и колонка/строка различий challenger−reference.

Различия содержат прогнозы компонентов, относительный рейтинг, номинальные
координаты через 1/2/4 с, конечный угол, длину и максимумы скорости, ускорения и
кривизны. Положительная разница прогноза не является измеренным улучшением.
Ускорение включает переход от текущей скорости к первому номинальному шагу.
Угловая разница приводится к [-180°,180°). Отрицательная разница максимума
ускорения не доказывает улучшения фактического комфорта.
Карта, будущие объекты и simulated rollout не подаются модели.

Итого **41 013 пар и 246 078 запросов**. `per_pair.csv` имеет 123 039 строк:
каждая физическая пара отдельно для трёх входов, оба порядка объединены.

Это сравнение каждой альтернативы с одной опорной траекторией, без адаптивного
турнира. Оно не устанавливает транзитивность предпочтений между альтернативами.

## Как фиксируется решение

Для challenger сохраняются две вероятности его предпочтения, их среднее и минимум.
Основная политика `none/both050`:

1. Допустить замену, только если challenger получает >0,5 в **обоих** порядках.
2. Среди допущенных выбрать максимальный минимум этих двух вероятностей.
3. При точном равенстве предпочесть меньший исходный ранг DS.
4. Если допущенных нет — сохранить DS.

В отчёте отдельно считаются заранее заданные контрольные правила:
`mean050` (среднее >0,5) и `both075` (обе вероятности >0,75). Это эвристики, не
калиброванный риск. Даже значение 0,99 не означает 99% вероятности безопасной замены.
Выбор самого уверенного из 63 сравнений может усиливать ошибки модели; поэтому
измеряются и все pair-level ошибки, и окончательный результат выбора на сцене.

Модельные решения всего набора фиксируются до чтения raw labels. Отчёт показывает
PDM gain micro/macro, bootstrap по сессиям, число вмешательств, потери по всем
компонентам, выборы из рангов 17–64, чувствительность к порядку и real−blank/none.
В `pair_quality` полезная замена определяется как gain >=0,005 raw PDM и отсутствие
ухудшения пяти safety-компонентов и lane keeping; harmful — loss >=0,005 либо любое
такое ухудшение. Это диагностические метки, не целевая вероятность модели.
Остальные случаи не объявляются ни полезными, ни вредными. Строки пар коррелированы;
их количество нельзя трактовать как количество независимых сцен.

## Запуск на msu270

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime

bash "$HOME/drivesuprim/scripts/drex/run_replacement.sh" submit-night 8
```

Поддерживаются 1/2/4/8 GPU. GPU-этап — **одна Slurm allocation**, N параллельных
процессов, одна копия Drex на каждом GPU, уникальность UUID проверяется барьером.
Для 8 GPU запрашиваются 32 CPU/768G RAM, для 4 — 16 CPU/384G.
Задание ждёт одновременной доступности всех запрошенных GPU.

Цепочка: CPU-тесты → CPU-план → одна GPU-задача (mini, затем full) → CPU-отчёт.
Mini каждого ранга выполняет 18 запросов: challenger ранга 2, 64 и 32, все три
режима и оба порядка. Первый сбой останавливает шаг; full после неудачного mini
не запускается. После постановки через sbatch можно выйти из SSH.

Отдельный mini перед ночным запуском:

```bash
bash "$HOME/drivesuprim/scripts/drex/run_replacement.sh" submit-pilot 8
# После его успешного завершения, с тем же именем и числом GPU:
bash "$HOME/drivesuprim/scripts/drex/run_replacement.sh" resume 8
```

`submit-night` уже содержит mini, дополнительно ставить `submit-pilot` не нужно.
Полный объём значительно больше предыдущего; время оценивайте по новым логам.
GPU allocation имеет лимит 8 часов, worker сохраняется и завершает неполный проход
после 7 часов, блокируя отчёт. При необходимости выполняйте `resume` с тем же
именем и числом GPU: успешные запросы не повторяются. Технический сбой сохраняется
и не перезапускается автоматически до удачного ответа. Для изменения протокола или
числа GPU задайте новое `DREX_REPLACEMENT_NAME=replacement_<новое_имя>`.

```bash
squeue -u "$USER"
bash "$HOME/drivesuprim/scripts/drex/run_replacement.sh" status 8

cat /scratch/pr0201/drex_runtime/runs/replacement_gpu8_v1/report.json
```

Прогресс обновляется каждые 25 обработанных запросов. Логи находятся в
`/scratch/pr0201/drex_runtime/logs/replacement-*.log`, worker-логи имеют номер ранга.
Первым для анализа нужен итоговый `report.json`. Затем `per_scene.csv` и при
необходимости `per_pair.csv`. Все исходные эксперименты сохраняются без изменений.

## Мини-тесты

```bash
python -B -m unittest discover -s scripts/drex -p test_replacement.py -v
```

Тесты используют искусственные данные и fake inference/sbatch/srun без сети, CUDA
и весов. Проверяются полный набор 63 альтернатив, знаки различий и углы, смена
порядка без подмены ID, одинаковый текст image-controls, возврат к DS и tie-break,
полный commitment до labels, сохранение и возобновление, повреждённые результаты,
обновление прогресса, параметры 1/2/4/8 GPU и остановка после неудачного mini.
Реальная корректность выбора Drex будет оценена серверным экспериментом.
