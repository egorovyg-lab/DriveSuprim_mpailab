# DriveMem: пересмотр исследовательского плана после оракульных экспериментов

Дата: 27 октября 2026 года.
Основание: исходный шестимесячный PDF, локальный код DriveSuprim/NAVSIM v2 и отчёты серверных запусков, переданные пользователем в чат. Серверные артефакты целиком локально не загружались; приведённые результаты следует связать с их manifests и CSV при подготовке статьи.

## 1. Решение о следующем этапе

Доступный резерв выбора среди финальных кандидатов установлен на диагностической выборке. Следующая обязательная веха — показать полезные и вредные вмешательства реального механизма памяти на независимых поездках и сравнить его с переоценкой без памяти. Повторные большие оракульные прогоны пока имеют меньшую ценность.

Научный вопрос статьи сохраняется: полезность извлечённого опыта не определяется одним сходством; предсказание результата вмешательства и отказ должны улучшать соотношение вреда и охвата. Нынешние эксперименты проверили только предпосылку — наличие лучших альтернатив. Они не проверили саму память, отрицательный перенос, оценку полезности или контроль риска.

## 3. Исправить единицу независимости

В результатах есть несколько log_name с одинаковыми датой, временем и машиной, но разными суффиксами сегмента. Например, `2021.09.29.19.02.14_veh-28_00540_00917` и `2021.09.29.19.02.14_veh-28_02451_02708`. Их следует считать фрагментами одной сессии, пока не показано обратное.

Введём `session_id`: дата/время + vehicle, без последних двух числовых суффиксов; проверить это правило по метаданным. По приведённому списку 32 log_name соответствуют 21 такому префиксу. Это предварительная группировка, а не доказательство полной независимости 21 поездки.

Ближайшая дешёвая проверка: пересчитать CI и распределение вклада по session_id из готовых CSV без новой симуляции. В новом наборе разделять память/обучение/калибровку/тест по session_id; дополнительно проверять пространственно-временную близость и перекрытие сегментов. Разносить два кадра на 10 секунд недостаточно для независимости.

Основные результаты сообщать с групповой оценкой неопределённости по сессиям. Не считать 256 кандидатов независимыми наблюдениями: это альтернативы внутри одной сцены. Отдельно показывать результаты с удалением каждой одной сессии (leave-one-session-out sensitivity), без выдачи такого анализа за новый подтверждающий тест.

## 4. Зафиксировать измеряемые величины и происхождение меток

Существующий benchmark-протокол сохраняется как отдельная версия. Его поведение с фильтром документируется, а не молча исправляется ради более удобного результата.

Новый экспорт меток должен сохранять:

- компоненты до human filter и после него;
- `weighted_metrics`, `weighted_metrics_array`, `multiplicative_metrics_prod`, raw progress, локальные баллы;
- вмешательства фильтра: какое поле и почему изменено;
- simulated states, sampling, map/cache/scorer versions и hashes;
- исходный и выбранный после вмешательства candidate ID, оба полных вектора метрик.

Внутреннее состояние scorer после включённого human filter может уже относиться к оценке human trajectory. Снимок метрик кандидата необходимо делать до этого вызова, с копированием массивов. Нельзя брать `scorer._weighted_metrics` в конце и считать их метриками кандидата.

Основной вектор вреда H: снижение NC, DAC, DDC, TLC или TTC относительно baseline с заранее определёнными допусками. Lane keeping, comfort и progress также сообщаются, но их статус в H задаётся явно. Не заявлять «безопасность по всем критериям», если H включает только пять компонентов.

Наряду с относительным вредом сообщать абсолютные нарушения: обе траектории могут иметь плохую безопасность и одинаковые метрики. Sigmoid-выходы DriveSuprim называть прогнозами голов; их вероятностная калибровка не установлена.

## 5. Разбиения и доступная в момент решения информация

Использовать navtrain для разработки модуля памяти. Создать заранее пять ролей данных:

| Роль | Назначение |
|---|---|
| M — memory | Донорские завершённые эпизоды и их доступные исходы |
| F — fit | Обучение переоценки и модели пользы; при необходимости out-of-fold предсказания |
| V — development | Выбор представления, retrieval, коэффициентов и размеров моделей |
| C — calibration | Только окончательный выбор порога уже зафиксированного метода |
| T — module holdout | Независимая проверка нового модуля после фиксации метода и порогов |

Количество сессий и сцен для каждой роли выбрать после инвентаризации реальных данных и частоты вмешательств, а не по произвольной пропорции кадров. Ни одна сессия не делится между ролями. Для карты/географии нужен дополнительный отдельный OOD-протокол.

Важно: C и T, выделенные внутри navtrain, независимы от обучения нового модуля, но не обязательно от обучения самого опубликованного DriveSuprim. Сначала установить, на каких данных обучался checkpoint. Если C входила в обучение любого компонента, строгую split-calibration гарантию нельзя автоматически обосновать новым именем split: нужен действительно независимый набор либо дополнительное доказательство. При отсутствии такого набора сообщать эмпирический контроль риска без неподтверждённой гарантии.

Публичный navtest уже использован для диагностики и выбора исследовательского направления. Сохранить список просмотренных сессий и историю использования. Не называть весь navtest нетронутым финальным тестом. Можно заранее зарезервировать ещё не изученные группы и продолжать стандартный benchmark как дополнительную оценку с честным описанием. Не обучать память/utility на полученных navtest-метках.

Для retrieval и переоценки разрешены только данные, доступные при принятии решения: изображения до текущего времени, ego status, driving command, исходные candidates и прогнозы модели; карта/маршрут и объекты — только если такие входы явно включены в постановку и доступны сравниваемым методам. Future annotations и scorer outputs текущего запроса используются только как offline targets/evaluation.

## 6. Минимальная проверяемая память

### 6.1. Что хранить

Эпизод: признаки сцены и короткой доступной истории, ego state/command, геометрия прошлого кандидата, прогнозы DriveSuprim, наблюдавшийся или симуляционно полученный исход, время/место, session_id, версия planner/vocab/cache. Память успешных эпизодов и ошибок; не отбирать доноров только под уже увиденные navtest-примеры.

В начале допускается банк из текущих сцен с доступной историей как технический baseline. Для итогового утверждения об эпизодической памяти определить короткое временное окно и показать его отличие от одиночного кадра. Текущий DriveSuprim в проверенном forward использует последнюю camera feature, поэтому его embedding нельзя автоматически считать полноценным представлением динамики.

Различать два режима получения исходов доноров:

1. **Executed-only memory:** исход реально выбранного действия каждого завершённого эпизода. Ближе к заявлению о накоплении опыта.
2. **Simulator-enriched memory:** дополнительные прошлые кандидаты оценены offline в симуляторе. Допустимый эксперимент, но это дополнительный источник supervision и вычислений, который надо раскрыть и предоставить контрольным моделям.

Не выдавать второй режим за память, сформированную только естественным потоком исполненных действий. В пилоте второй режим может ускорить проверку идеи; итоговая статья должна включать executed-only сравнение или сузить соответствующее утверждение.

### 6.2. Retrieval

Сначала фиксированное представление: frozen visual embedding + нормированные ego speed/acceleration/command; временные признаки и уверенно доступная геометрия добавляются по необходимости. Экспортировать embedding отдельным диагностическим выходом, проверить отсутствие будущих данных. Нормировку и проекции обучать только на M/F.

Три первоначальных варианта: случайный совместимый донор, ближайший совместимый донор, несколько соседей. Жёсткие фильтры должны использовать только доступные признаки. FAISS пока необязателен: точный поиск по небольшому банку проще проверить.

Сходство изначально не обучать на utility. Так можно проверить тезис о недостаточности сходства, а не построить utility-модель под названием retrieval.

### 6.3. Как опыт меняет траекторию

Траекторию донора нельзя просто копировать в новую сцену. Первый baseline: перенос ошибки прогноза метрик.

Для прошлого действия a в эпизоде e: `residual_k(e,a) = outcome_k(e,a) - predicted_k(e,a)`. Для кандидата τ новой сцены перенести эти residuals с весом сходства сцены и совместимости геометрии движения (скорость, смещение, кривизна, горизонт). Получить скорректированные ограниченные прогнозы компонентов и ранжирование S_M. Imitation сохраняется отдельным исходным слагаемым, если для него нет сопоставимой метки.

Использовать абсолютный vocab ID как идентификатор можно только внутри того же фактического словаря; для переноса residual нужен анализ геометрии и текущего ego state. Общий ID не означает одинаковую полезность в разных сценах. Для второго planner потребуется представление геометрии, а не ID DriveSuprim.

Формулу коррекции и коэффициент её силы фиксировать на V. Все методы выбирают из того же полного пула 256; отсутствие памяти или отсутствие совместимого донора возвращает baseline. Это baseline для проверки идеи, не заранее объявленный итоговый архитектурный вклад.

## 7. Первый решающий эксперимент: полезность и отрицательный перенос

На независимых F/V/T-запросах измерить:

- τ0 и τM; долю реальных изменений решения, отдельно от доли выполненных retrieval;
- Δ по каждому компоненту, локальному качеству, позже полному EPDMS;
- пользу и вред среди изменённых решений, а также на всех сценах;
- распределение Δ при разных similarity и семействах сценариев;
- чувствительность к случайному донору, nearest retrieval и нескольким соседям.

Повторные запросы с разными донорами дают больше обучающих пар, но не больше независимых сессий. Ошибки и CI группировать по сессиям и запросам. Нельзя избирательно показывать только эпизоды с крупным отрицательным переносом.

Минимальные конкуренты уже на этом этапе:

| Вариант | Что отделяет |
|---|---|
| Frozen DriveSuprim | Исходное качество |
| Переоценка без памяти | Эффект дополнительной модели и supervision |
| Та же коррекция со случайным совместимым донором | Эффект выбранного опыта |
| Similarity memory без отказа | Базовый retrieval и его вред |
| Similarity memory с порогом сходства | Простой selective baseline |

Переоценка без памяти получает те же query-признаки, кандидаты и доступный объём supervision, включая донорские метки, использованные для обучения memory-метода. Сравнивать также latency/model size и доступ к дополнительным входам. Изъятие memory из уже обученной сети не заменяет отдельно обученный сильный baseline без памяти.

Условия продолжения: память иногда даёт воспроизводимую пользу на разных сессиях; есть измеримые полезные и вредные вмешательства; effect не объясняется только дополнительным predictor. Если вреда мало, не усиливать память искусственно ради красивого тезиса: оценить интервал и проверить, нужна ли постановка risk-controlled recall. Если память стабильно уступает модели без неё, остановить усложнение и разобраться в представлении/переносе residuals.

## 8. Модель полезности — только после проверки самого вмешательства

Фиксировать версию retrieval/reranker и формировать цель Δ для конкретного предложенного вмешательства. При смене reranker перегенерировать пары или явно учитывать policy version. Иначе predictor обучается оценивать другое действие.

Входы: query-признаки, параметры исходного и нового кандидатов, исходные scores, сведения о донорах и их прошлых результатах, расстояния, поддержка действия в памяти, конфликт соседей. Недоступны текущие истинные outcomes и offline quality rank.

Сначала простой предиктор Δtotal/события H, затем компонентные Δ и неопределённость. Out-of-fold результаты нужны, если gate обучается на действиях обученной на тех же F-метках переоценки. Оценить дискриминацию вреда при matched coverage, а не только среднюю ошибку регрессии.

Итоговые обязательные строки: baseline; no-memory reranker; similarity memory; similarity threshold; utility gate без калибровки; calibrated gate. Рандомная память и memory-label/neighbor ablations — проверки роли retrieval. Сравнивать gate-методы при одинаковом intervention coverage и в пределах одинакового candidate pool.

## 9. Контроль риска: изменить слишком сильную исходную формулировку

Определить `A=1`, только если выбранный candidate действительно отличается от baseline. Основные величины:

- `coverage = P(A=1)`;
- `selective_harm = P(H=1 | A=1)`;
- `unconditional_harm = P(H=1, A=1)`;
- абсолютная частота нарушений и величина ухудшения, отдельно от бинарного H.

Калибровка unconditional harm не равна калибровке selective harm: уменьшение coverage само уменьшает P(H,A). Статья должна ясно сообщать, какая величина ограничивается.

Оригинальный Conformal Risk Control рассматривает ожидаемый ограниченный monotone loss. Это не автоматическая гарантия условной доли вреда среди вмешательств. При фиксированном ранжировании threshold делает A вложенным, но отношение числа вредных вмешательств к числу всех вмешательств не обязано быть монотонным. Источник: https://arxiv.org/abs/2208.02814 ; официальный код: https://github.com/aangelopoulos/conformal-risk .

Первый честный вариант: заранее определить конечную сетку порогов, зафиксировать predictor на F/V, на независимой C выбирать максимальный coverage при одновременной верхней границе selective harm для этой сетки. Использовать подходящие конечновыборочные границы и учёт выбора порога/множественных проверок. Если независимая единица — сессия, нужна корректная формулировка на уровне сессии либо заранее выбранного случайного решения из каждой сессии; простая биномиальная граница по соседним кадрам неприменима.

Оценить объём C до обещания малых рисков. Даже для одного заранее фиксированного threshold, независимых принятых решений и нуля вредных исходов, односторонняя 95% биномиальная граница ниже 1% требует примерно 299 принятых независимых примеров; для 5% — около 59. Выбор из нескольких порогов и зависимость данных усложняют задачу. Число всех кандидатов и число отказов не заменяют число принятых независимых примеров.

Не обещать per-scene safety из условных lower bounds без обоснованной процедуры. Если доступных данных недостаточно, показать эмпирические risk-coverage curves и CI и честно ограничить claims. Новая теория желательна только если возникает точная, доказуемая постановка, а не как формальное требование к статье.

## 10. Полная метрика, последовательность и второй planner

Нынешние две сцены на лог разнесены на 10 секунд и не подходят для полноценного two-frame comfort. Добавить отдельный набор непрерывных фрагментов. Сравнивать baseline и реально выбранный memory-метод на одном полном множестве кадров с исходным adjacency mapping и агрегацией.

Для обучения utility сначала допустим локальный Δ. Потом проверить согласованность этого proxy с полным EPDMS. Одна замена влияет на свою строку и комфорт следующей; одновременные изменения требуют общей повторной агрегации. Полный DP-oracle по цепочке оставить диагностикой при необходимости: для проверки практического метода он не обязателен. Не тратить на него недели до проверки памяти.

В течение ближайших двух недель выполнить небольшой integration spike PDM-Closed/PDM-Hybrid: воспроизводимость, доступ к кандидатам, место вмешательства, парный прогон nuPlan. Выбрать один второй planner, не сравнивать оба полностью. Важный confound: DriveSuprim/NAVSIM и PDM/nuPlan меняют одновременно planner и среду. Это проверка применимости в двух контурах, а не чистое доказательство zero-shot переноса между planner. Для такого claim нужен общий протокол/сценарии либо более узкая формулировка.

Основные закрытые прогоны выполнять после выбора работающего метода: baseline, similarity memory, similarity gate, full DriveMem; несколько заранее заданных семейств сценариев и повторов. interPlan использовать как ограниченный stress test. Не смешивать локальное действие из фиксированной сцены с истинным эффектом полного replanning rollout.

## 11. Рост памяти и смысл continual

Рост индекса сам по себе не доказывает continual improvement. Использовать временной поток: retrieve/decide → наблюдать исход завершённого эпизода → записать → перейти к следующему. Future query labels не попадают в память до решения этого запроса.

Для чистого сравнения провести два режима: frozen memory и chronological growing memory. Изначально ограничиться 2-3 размерами/политиками записи и проверкой дублей. Test-stream outcomes могут использоваться как прошедший опыт для последующих сцен, если это заранее заданный prequential-протокол и одинаковые права есть у baseline; они не используются для подбора гиперпараметров и не выдаются за обычный статический holdout.

Гарантия калибровки не переносится автоматически на изменяющуюся память. В первой версии фиксировать memory/reranker в пределах этапа оценки; для роста памяти отдельно показать повторную калибровку и эмпирический drift. Если prequential опыт не реализован, сузить название до episodic recall/memory-augmented planning вместо заявления continual motion planning.

## 12. Вычислительный бюджет и размер пилота памяти

Измерено: 3898 секунд на 64 сцены × 256 кандидатов, около 61 секунды на сцену в конкретном последовательном запуске. 1000 таких сцен — ориентировочно 17 часов, 10000 — около 7 суток на одном worker, без учёта изменений нагрузки. Не масштабировать слепо полный oracle на каждую query.

Для ближайшего пилота:

1. Инвентаризация cache/логов и session-level split до тяжёлых запусков.
2. Небольшой M, например 500-1000 донорских сцен из достаточного числа сессий; точное число после проверки доступности.
3. Query-пилот порядка 200-400 сцен по независимым сессиям; это тест работоспособности, не обещание точного low-risk certification.
4. Для каждого query оценивать union уникальных действий baseline и сравниваемых методов, а не все 256. Все методы по-прежнему могут выбирать из полного пула.
5. Для обогащённых доноров оценивать ограниченный заранее выбранный набор: верхние кандидаты по model score плюс случайные кандидаты из более низких рангов. Не выбирать их по query oracle labels.
6. Полную оценку 256 оставить на фиксированной небольшой диагностической подвыборке. top-32/64 дают около 92%/96% резерва текущего пилота, но это не основание запрещать методу выбирать более низкие ранги: первая поездка уже дала полезный rank 51.
7. До пакетного ускорения scorer сохранить pairwise-нормировку progress и проверить численную эквивалентность. CPU parallelism по сессиям проще контролировать, чем менять сам протокол.

## 14. Как должна выглядеть доказательная структура статьи

1. **Мотивация:** резерв кандидатов и примеры ошибочной оптимистичной оценки DriveSuprim; текущие результаты относятся сюда и в приложение.
2. **Постановка:** фиксированный planner, доступные query-входы, memory provenance, конкретное вмешательство, компонентный harm и coverage.
3. **Центральный эмпирический результат:** распределение реальной пользы memory при фиксированном similarity, полезные и вредные вмешательства на разных сессиях.
4. **Метод:** retrieval/reranking → prediction of intervention value → selective gate; каждый элемент проверяется абляцией.
5. **Основная таблица:** baseline, сильный no-memory reranker, similarity memory, similarity threshold, utility gate, calibrated gate; качество и harm при сопоставимом coverage, без спрятанных safety ухудшений.
6. **Перенос и последовательность:** полный NAVSIM протокол, nuPlan/второй planner, ограниченный stress test, frozen/growing memory с честным разделением прав на метки.
7. **Ограничения:** simulator labels, зависимость от candidate pool, модель входов, rare-event uncertainty, distribution shift, повторное использование public test, условность статистических гарантий.

Перед фиксацией новизны отдельно обновить обзор близких работ по memory/retrieval planning, learning to defer и оценке полезности. Названия и доступность всех перечисленных в PDF проектов в этой ревизии систематически не перепроверялись. Нынешний oracle результат сам по себе не является основанием для заявления о достаточной новизне или вероятности принятия NeurIPS.

## 15. Следующее конкретное задание для реализации

Подготовить один пакет для сервера:

- inventory датасета/cache с session_id, временными диапазонами и списками доступных входов;
- детерминированный session-level manifest M/F/V/C/T без обращения к quality labels;
- экспорт query/donor embedding, ego features и геометрии кандидатов с provenance;
- raw/filtered метки с сохранением внутренних агрегатов и проверками benchmark parity;
- минимальный residual-memory reranker и независимый no-memory контроль;
- evaluator union выбранных действий и отчёт similarity/utility/harm по сессиям.

Первым выполнить дешёвую inventory/split проверку. Если train cache отсутствует, построить его сначала только для выбранного пилота. После этого запустить один небольшой memory experiment и оценить научный вопрос до расширения архитектуры.
