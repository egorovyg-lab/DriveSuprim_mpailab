# Локальная модель выбора траектории по мотивам System One

Предложение от 7 ноября 2026 года. Это проект эксперимента, не реализованная
модель и не заявление о приросте качества. Jev API, внешние ключи и языковая
генерация для этого подхода не нужны. Вычислительные затраты остаются локальными.

## Что берём из идеи Jev

Состояние и конечный набор допустимых действий → один forward → структурированные
оценки и решение. Применительно к нам state — визуальные/ego признаки, options —
готовые траектории, результат — ID существующего кандидата и основание для
сохранения baseline при недостаточном свидетельстве улучшения.

Это перенос принципа специализированной decision model, а не воспроизведение
закрытого Jev/RLCD. Набор из 16 ответов позволяет сделать небольшой head,
но сложность понимания сцены и прогнозирования последствий сохраняется.

## Что у нас уже есть и чего не следует переименовывать

DriveSuprim уже кодирует траектории, сопоставляет их с image features через
attention, выдаёт component heads и выбирает действие по заданной формуле.
Идея «нейросеть оценивает варианты» для него не нова.

Предыдущий direct utility использовал линейный ridge на candidate-baseline
признаках. Component/decoder experiments использовали ridge по абсолютным
PDM/components с sigmoid readout; decoder features расширяли признаки,
но не меняли линейный learner. Следовательно, кандидат на следующий тест —
нелинейный, обучаемый непосредственно для выбора из набора модуль. Просто
добавить softmax к старым scores не меняет argmax и ничего не исправляет.

## Архитектурные варианты

### A. Общий нелинейный scorer — обязательный простой контроль

Для каждого кандидата вход включает:

- его frozen decoder vector и разность с decoder vector baseline;
- геометрию траектории и разность с baseline;
- ego state, исходные predicted metric heads и score gap;
- явный флаг baseline, привязанный к кандидату, а не номеру строки.

Один и тот же небольшой MLP применяется ко всем кандидатам и выдаёт ranking
logit. Затем все 16 logits нормируются совместно. Это нелинейный контроль
относительно прежнего ridge. Не использовать trainable vocabulary-ID embeddings,
scene/session IDs или номер кандидата: они могут позволить запоминание shortcuts.

### B. Небольшой set-head — основная проверяемая гипотеза

Те же входы проектируются в векторы, например ширины 64. Один компактный
self-attention блок без embeddings позиции кандидата позволяет сопоставить
альтернативы. Общий readout выдаёт один logit на кандидата.

При перестановке кандидатов outputs должны переставляться тем же образом;
выбранная физическая траектория сохраняется при отсутствии ties. Это
permutation equivariance, а не постоянство вектора probability по позициям.
Padding/masks и tie-breaking проверяются отдельно. Численные допуски тестов
задаются до эксперимента; воспроизводимость всего старого planner из этого
свойства нового head не следует.

Ориентир проектирования — десятки или первые сотни тысяч обучаемых параметров,
не миллиарды. Размер уточняется после фиксации входных признаков. Модель B
сравнивается с A при близком числе параметров: эффект нельзя приписывать
взаимодействию кандидатов, если B просто существенно больше.

Теоретическая основа множеств: [Deep Sets](https://arxiv.org/abs/1703.06114),
[Set Transformer](https://arxiv.org/abs/1810.00825). Открытая работа
[Narrow Decision Models](https://arxiv.org/abs/2610.25553) показывает похожую
организацию bounded decisions и set-head, но исследует другие данные и не
доказывает применимость к autonomous driving.

### C. Локальные визуальные признаки вдоль каждой траектории

Если A/B не различают опасные и хорошие пути, проверить, достаточно ли информации
в frozen decoder vectors. Возможное расширение — признаки изображения в
геометрически связанных с траекторией областях: границы дороги, препятствия,
видимость. Нужны корректная camera projection, masks видимости/occlusion и
разделение наблюдаемого и неизвестного.

Это более существенное изменение perception, чем ещё один MLP. DriveSuprim
уже имеет candidate-conditioned attention; добавление общего cross-attention
само по себе не новое отличие. Проверяемое отличие C — явно локализованное
свидетельство вдоль candidate corridor. Не подавать истинную drivable map из
metric cache на inference. Можно исследовать её как training target для
camera-derived predictions, явно сохраняя camera-only режим проверки.

C не запускается автоматически после любого отрицательного результата A/B:
сначала проверить, указывает ли диагностика именно на нехватку visual evidence.

## Учить качество ВЫБОРА

Для обучающих сцен известны simulator outcomes кандидатов. Поэтому начальный
прототип можно обучать supervised, без онлайн RL. Это labels будущего только
в train loss; в inference features они не попадают.

Не назначать единственный best-ID через argmax: у многих сцен несколько
кандидатов имеют PDM=1, и выбор первого ID создал бы искусственную задачу.

Один фиксируемый вариант listwise loss:

`G_s = {i: Q_i >= max_j Q_j - epsilon}`

`L_rank = -log(sum_{i in G_s} softmax(z)_i)`.

Он поощряет массу на множестве почти лучших траекторий. Если все варианты
равноценны, этот loss не даёт основания навязывать вмешательство. Epsilon
определяется как минимально значимое различие до evaluation; не подбирается
по уже известной сцене f27a618a5c7458ee.

Pairwise loss на различимых парах — разумный контроль, но не ещё одна длинная
серия перебора objectives. В начальной спецификации выбрать одну основную loss
и один контроль. Веса усреднять по сценам/сессиям; число пар не является числом
независимых дорожных ситуаций.

## Отдельный вопрос «есть ли основания менять baseline?»

Второй небольшой выход может учиться на событии: существует ли среди
альтернатив заметное улучшение PDM без ухудшения заданных safety-компонентов
относительно baseline. Это training label, вычисляемая из outcome vectors.
Выбор кандидата и решение вмешиваться должны быть согласованы; наличие одного
плохого candidate не делает весь набор плохим, а высокое относительное
предпочтение не доказывает хорошего абсолютного качества.

Сравнить raw ranker и тот же ranker с gate. Порог/правило выбора настраивать
только на training/tuning sessions. Не переносить старый teacher-Pareto guard
в обязательную часть нового метода без сравнения: ошибочная teacher оценка
может отфильтровать полезную альтернативу. Старый guard полезен как контроль.

Softmax over actions — относительное предпочтение в данном наборе. Его нельзя
объявлять вероятностью безопасности. Добавленная intervention head также не
становится калиброванной от BCE или Brier loss автоматически. Для вероятностей
конкретных safety events нужны достаточная поддержка этих событий, отдельная
проверка calibration и holdout. При отсутствии таких данных не выдавать
неподтверждённые collision probabilities.

Сохранение baseline уменьшает вмешательства, но baseline сам может ошибаться.
Когда все кандидаты плохие, один selector не создаёт новую безопасную траекторию.

## Данные: сначала использовать то, что уже оплачено вычислениями

В functional sidecar сохранены vectors для всех 256 candidates, а не только
top16. Для первой фазы использовать прежние M/F сцены, их labels и frozen
functional features; никакого повторного RGB export или смены numerical profile.
Бывшая M здесь — часть training data, а не память, доступная при inference.

Имеется порядка сотни M/F scenes, а не десятки тысяч независимых примеров.
Даже 112×16 candidate rows дают только 112 scene groups. Следует сначала
сосчитать разнообразие meaningful ranking pairs, improving interventions,
unsafe alternatives и число независимых sessions для каждого случая.

Если supervision бедна, возможен следующий data-only шаг: досчитать outcomes
top32/top64 или geometry-selected negatives на уже имеющихся M/F изображениях.
Дополнительные vectors уже сохранены; основная новая цена — simulator scoring.
Однако rollout labels за пределами deployment top16 не доказывают calibration
внутри top16. Дополнительные кандидаты не увеличивают количество sessions.
Training rank objective и evaluation pool должны явно отражать этот сдвиг.

Ещё один источник — ранее скачанные, но не вошедшие в labels screening-сцены
тех же M/F sessions. Это расширяет train coverage, но не даёт независимого test.
Никаких новых больших image downloads до первых результатов не требуется.

## Первый ограниченный эксперимент

1. Зафиксировать inputs, top16, labels, session roles и primary criterion.
2. Провести read-only аудит supervision без новых models/thresholds.
3. Сравнить teacher, прежний ridge и модели A/B с одной основной ranking loss.
4. Проверить обучение на train, session-separated CV, permutation/padding tests,
   baseline behavior на ties и ошибки на редких meaningful decisions.
5. Зафиксировать intervention rule на M/F tuning. Сохранять все решения перед
   чтением evaluation outcomes, как в прежнем pipeline.
6. Старые 40 development scenes использовать для диагностики и сравнения
   с предыдущей историей, не как fresh confirmation новой архитектуры.
7. Независимые новые sessions/закрытый заранее определённый holdout использовать
   только после freeze. Считать utility, component harm, coverage и bootstrap
   по sessions; делать leave-one-session-out и проверять зависимость от f27.

Не выбирать лучший seed/threshold по development. Нулевые вмешательства не
считать успехом. При отсутствии session-generalized useful signal остановить
этот вариант, а не автоматически увеличивать transformer и открывать C/T.

## Ожидаемое отличие от закрытой ветки памяти

Новый объект — компактный scene-conditioned decision module, обучаемый выбирать
из набора по непосредственной outcome supervision. Нет donor retrieval, cloud
service, свободного текста и задачи воспроизведения Jev. Проверяются отдельно
нелинейность, взаимодействие кандидатов, ranking objective и intervention gate.

Узкий выход и использование cached features делают такой первый опыт
ресурсно доступным; они не гарантируют хорошего обучения на малом числе сцен.
Новизна статьи и прирост качества не следуют из одного названия Set Transformer.
