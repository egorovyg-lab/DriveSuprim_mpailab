# DS + Drex: проверка полезности сохранённых оценок

Новый запуск: `rollout_audit_drex_probe_v1`. Старые исследования, картинки,
решения и метрики не меняются. На первом шаге не обучаем сам Drex: проверяем,
содержат ли его уже вычисленные попарные предпочтения полезную информацию
для небольшого предиктора физических последствий замены DS.

## Что сравниваем

Используем ровно 651 TRAIN-сцену из 32 сессий, по 63 альтернативы исходному
выбору DS: 41 013 пар. Это не 41 013 независимых дорожных ситуаций.

Пять вариантов входа:

| Вариант | Признаки |
|---|---|
| `ds` | Числа исходной таблицы DS, различия с DS, текущее движение ego |
| `ds_drex_text` | Те же числа + сохранённые ответы Drex без изображения |
| `ds_drex_blank` | Те же числа + ответы с пустым изображением |
| `ds_drex_road` | Те же числа + ответы с фотографиями дороги |
| `ds_drex_shuffled` | Контроль: ответы road перемешаны между альтернативами одной сцены |

Добавленные признаки: предпочтение альтернативы в двух порядках подачи,
среднее и абсолютная разница. ID кандидата, token, номер сессии, настоящие
метрики, карты и будущие участники не входят в числовые признаки.
Размер входа одинаков: у `ds` четыре дополнительных нуля.

Две одинаковые для всех входов модели: линейная ridge и ridge с фиксированными
нелинейными случайными признаками. Основная — вторая. Нет поиска параметров:
нормированная по сессиям ridge-регуляризация 0.1, 64 случайных проекции,
фиксированный seed. Четыре группы целых сессий: каждый раз 24 сессии для
обучения и 8 для прогноза. Все нормировки вычисляются только на обучающей части.
Есть дополнительный контроль — средние обучающих целей без признаков.

## Цели и правила замены

Модель предсказывает изменение RMS рывка, RMS бокового ускорения,
продвижения в метрах, PDM в процентных пунктах, максимума рывка, а также
два бинарных обучающих признака: наблюдаемое ухудшение и полезное изменение.
Источники — уже рассчитанные полные четырёхсекундные симуляции top64.

Наблюдаемое ухудшение в этом **новом протоколе** означает хотя бы одно:

- ухудшился NC, DAC, DDC, TLC, TTC, lane keeping или history comfort;
- выросли площадь/интеграл/длительность выхода кузова за дорогу либо длительность контакта;
- потеря продвижения превысила хотя бы один из лимитов: 1 м и 5% продвижения DS;
- доступный минимум расстояния до дороги уменьшился более чем на 0.1 м,
  либо до участников — более чем на 0.25 м;
- неполное временное покрытие участников у DS или альтернативы.

Полезное изменение: RMS рывка снизился хотя бы на 0.2 м/с³ и на 20%, **или**
RMS бокового ускорения снизился хотя бы на 0.05 м/с² и на 20%; второй RMS и
максимум рывка при этом не выросли, перечисленных ухудшений нет.
Пороги абсолютного/относительного выигрыша взяты из предыдущего pool-аудита.
Ограничения здесь отличаются от строгого `geometry_peaks` oracle: это отдельная
обучающая постановка, её результаты нельзя выдавать за результаты того oracle.

Недоступные расстояния сохраняются как NaN, не заменяются нулём. При отсутствии
одного из парных расстояний этот конкретный запас не сравнивается; в отчёте и
CSV есть `road_margin_unavailable` и `actor_margin_unavailable`. Поэтому
`benefit` не доказывает сохранение всех неизвестных запасов безопасности.

Правило замены получает **только прогнозы**, без измеренных целей:
оценка полезности выше порога, оценка ухудшения не более 0.05, прогноз потери
продвижения не больше 1 м, прогноз максимума рывка не растёт, прогнозируется
достаточный выигрыш хотя бы по одному RMS без ухудшения второго.
Это некалиброванные ridge-оценки, не вероятности аварии.
Относительный лимит продвижения и реальные последствия проверяются при оценке;
измеренное будущее продвижение DS не подаётся в правило.

Основной заранее заданный порог полезности — 0.1. Также публикуются все
заданные пороги от 0.01 до 1.01 (последний всегда оставляет DS).
Выбирать лучший порог по этому отчёту и объявлять его независимым результатом нельзя.
Равенство порогу оставляет DS; между допущенными альтернативами выбирается
максимальная оценка полезности, при равенстве — исходный порядок DS.

## Запуск на msu270

На Astra обновлять репозиторий не требуется: небольшой проверенный набор кода
и массивов передаётся автоматически. Обязательные существующие источники:
`replacement_gpu2_v1` и завершённый `rollout_audit_pool64_v1` с `latest_result.json`
и SHA-проверенным архивом. Подготовка перепроверяет все сохранённые ответы Drex,
ID кандидатов и исходные PDM. Она может занимать несколько минут; это CPU,
в Slurm очередь обычная, GPU не запрашиваются.

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
export DREX_PROBE_NAME=rollout_audit_drex_probe_v1

bash scripts/drex/run_consequence_probe.sh prepare &&
bash scripts/drex/run_consequence_probe.sh connect &&
bash scripts/drex/run_consequence_probe.sh start
```

`prepare` сначала выполняет небольшие автоматические тесты, затем собирает
входы. `connect` попросит пароль Astra только если прежнее SSH-соединение
закрыто. После сообщения `launched` можно закрывать терминал: CPU-процесс
запущен внутри контейнера Astra с отдельной сессией, stdin/out/err отвязаны
от SSH. Никакого активного контроллера на msu270 не остаётся.

Сначала выполняется один полный внешний fold (10 моделей), проверяются конечные
прогнозы и привязки входов. Только затем автоматически остальные три fold.
Это проверка исполнения, не требование получить положительный научный результат:
нулевые замены, пустая поддержка редких событий или проигрыш контроля допустимы.
Всего 40 небольших fit, без Torch, новых вызовов Drex или scorer.
Ожидать прежних суток GPU-расчётов здесь не нужно; время зависит от CPU и проверки файлов.

```bash
bash scripts/drex/run_consequence_probe.sh status
# Если SSH-соединение закрыто, сначала снова connect.
bash scripts/drex/run_consequence_probe.sh fetch
```

`start` с тем же именем после прерывания продолжает по SHA-привязанным
чекпойнтам завершённых fold. Менять код, входы или имя для продолжения нельзя.
Повторный `start` во время работы не создаёт второй расчёт.
Пароль Astra в файлах не сохраняется; новые данные из сети не скачиваются.

## Что прислать для анализа

`fetch` выводит каталог `result_<hash>`. Нужны:

- `report.json`: качество прогнозов, AP редких событий, фиксированные правила и
  парные интервалы по целым сессиям;
- `per_scene.csv.gz`: фактически выбранные альтернативы, прогнозы и истинные последствия;
- `per_candidate.csv.gz`: OOF-прогнозы всех пар для подробного разбора.

В первую очередь смотрим `accuracy` относительно `train_mean` и `ds`,
затем `continuous_mae_road_minus_control` (отрицательное значение лучше),
`primary_contrasts` и `overview`. Для выигрышей реальные ухудшения и пропуски
геометрических сравнений должны анализироваться вместе с комфортом и прогрессом.
Интервалы — кластерный bootstrap сессий, не независимых строк кандидатов.

Все эти данные уже многократно просматривались. Результат остаётся исследовательским
OOF, свежий holdout не открывается. Успех этого шага обоснует следующий,
более дорогой эксперимент с адаптацией Drex/новой головой. Неудача покажет
ограничение **текущих сохранённых оценок**, а не невозможность любого подхода с Drex.
