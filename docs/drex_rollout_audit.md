# CPU-аудит исходного пути и движения после симулятора

Проверяем, соответствует ли информация на изображениях шести пар условиям,
по которым вычислены DAC, удержание полосы и NC. Это постфактум-разбор 12
известных кандидатов, а не новый эксперимент Drex.

## Запуск с msu270

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
export DREX_ROLLOUT_PAIR_SOURCE=pair_diag_gpu4_v1
export DREX_ROLLOUT_AUDIT_NAME=rollout_audit_pair6_v1

bash scripts/drex/run_rollout_audit.sh connect
bash scripts/drex/run_rollout_audit.sh start
```

`connect` использует уже знакомое SSH-подключение к Astra. Если соединение
истекло, пароль вводится в терминале; скрипты его не сохраняют. После `start`
можно отключаться от msu270: лёгкий мост работает через `nohup`.

На msu270 используется только стандартная библиотека Python — без запуска
compute-node venv на login-узле. Вычисления выполняются **на CPU Astra** в
существующем `egorov_drivesuprim`, с пустым `CUDA_VISIBLE_DEVICES` и двумя
потоками OMP/BLAS. GPU и очередь Slurm не используются.

Мост проверяет завершение 48 запросов, их SHA и обязательство решений,
пакет данных, кандидатов и ожидаемые метрики. Затем доставляет только
небольшой запрос и девять файлов инструментов в отдельный каталог:

```text
/workspace/exp_v2/drex_rollout_audit/rollout_audit_pair6_v1/
```

Исходный checkout Astra, конфигурации, cache, bundle, результаты v1/v2 и
диагностики пар не меняются. На Astra используется ранее экспортированный
пакет `/workspace/exp_v2/drex_transfer/navsim_train_v1`; новые изображения
или архивы датасета не скачиваются. Полный датасет обратно не переносится.

Статус:

```bash
bash scripts/drex/run_rollout_audit.sh status
```

Команда покажет журнал, итоговый отчёт и **точный локальный каталог артефактов**
на msu270. Путь имеет вид:

```text
/scratch/pr0201/drex_runtime/runs/rollout_audit_pair6_v1/result_HASH/
```

Снимки возвращаются с контрольными суммами; разные снимки сохраняются в
разных каталогах. Лимит возвращаемых артефактов — 90 MiB, архива — 100 MiB.
Ожидаемый объём — несколько/десятки мегабайт, в основном PNG.

## Что воспроизводится

На Astra по исходному bundle ищутся связанные контрольными суммами
`source_config.json`/`identity.json` и `cache_index.json`. Конфигурации scorer,
симулятора, proposal sampling, traffic policy и sampling агента должны
совпадать. Проверяются исходные файлы scorer/simulator, cache SHA и лог сцены.
Если для токена доступны несколько cache, предпочтение имеет корень с
связанным исходным feature-файлом, содержащим те же кандидаты; выбор записан.

Для каждого кандидата один раз вызывается исходный `pdm_score` с
`human_penalty_filter=False`, как при сборе raw labels. Все девять выходных
метрик сопоставляются с сохранёнными: `atol=1e-8`, `rtol=1e-7`.
Это **12 CPU-пересчётов**, без инференса DriveSuprim/Drex, обучения и открытия
holdout. Параметры автомобиля сверяются с подтверждённым на Astra профилем.
Параметры машины симулятора из cache также записываются отдельно.

Отдельно сохраняются исходная траектория, её семплирование на сетке scorer
и состояния после LQR/bicycle simulator. Оба пути преобразуются в текущую
систему координат задней оси. Измеряются среднее/максимальное/конечное
расхождение и разница heading с корректным учётом перехода через ±π.

DAC проверяется по четырём углам и **тем же** cached drivable polygons через
`points_in_polygons`, а не по рисунку дороги. Учитываются исходный момент и
строгая принадлежность полигонам. Для первого нарушения записываются углы,
время, расстояние до drivable polygons и проекция на фото. Точка на границе
может не пройти `contains`, имея нулевое расстояние до полигона.

Удержание полосы использует центр автомобиля и cached scorer centerline.
В точности воспроизводятся строгий порог `distance > limit`, число отсчётов
`ceil(window/dt)` и пропуск перекрёстка **без сброса счётчика**. Ничего в
метрике не исправляется. Время достижения требуемого числа отсчётов не
подменяется интуитивным «прошло ровно две секунды».

Для NC берётся время первого at-fault события, зарегистрированное scorer.
Список пересекающихся объектов в этот момент — контекст: он не выдаётся
за новую классификацию виновности каждого из перечисленных объектов.

## Артефакты и интерпретация

В каждом `case01-member0/`, `case01-member1/` и т. д.:

- `summary.json`: метрики, совпадение с оригиналом, события и проекции;
- `traces.npz`: исходные/симулированные states и локальные poses, углы,
  membership в карте, расстояния до centerline и маски перекрёстков;
- `trace.csv`: покадровая таблица основных величин;
- `camera.png`: синий исходный путь, оранжевый после симулятора, красное
  отмечает место записанного события;
- `map.png`: drivable polygons, scorer centerline, траектории и габариты;
  пурпурным — перекрывающиеся объекты в момент collision, если он есть;
- `commit.json`: SHA готовых файлов, используемые при возобновлении.

`member0` — DS; `member1` — предложенная в диагностике альтернатива.
В `case06` именно member1 соответствует известной потере удержания полосы.
В остальных пяти парах member1 — известное исправление.

Общий `report.json` должен содержать `status=complete`,
`metric_parity_passed=12`, `geometry_interpretation_ready=true`.
`pairs` показывает расстояния между кандидатами и проекции соответствующего
угла/центра в момент первого нарушения плохого кандидата. Дополнительно
считаются расхождения DAC/LK между номинальным и симулированным движением.
Это позволяет отделить различия после контроллера от тех, которые изначально
были показаны модели.

`projects_inside_current_photo` означает только попадание в границы кадра
на допустимой ветви калибровки. Перекрытия объектами не проверяются; все
проекции по-прежнему используют плоскую землю. Карта и будущий traffic
**привилегированный диагностический контекст**, который не подаётся Drex.

При `parity_failed` все результаты сохраняются, но геометрию нельзя
интерпретировать как воспроизведение исходных метрик. Бюджеты не расширяются,
автоповторов для получения удобного результата нет. Готовые кандидаты при
возобновлении проверяются и не пересчитываются. Записанная техническая ошибка
требует разбора и нового `DREX_ROLLOUT_AUDIT_NAME`; старый каталог сохраняется.

Переопределения нестандартных путей: `DREX_ASTRA_PACKAGE`, `DREX_ASTRA_REPO`,
`DREX_ASTRA_CONTAINER`, `DREX_ASTRA_HOST`, `DREX_ASTRA_PORT` и прежний
`DREX_TRANSFER_CONTROL`. Изменённые инструменты/запрос не перезаписываются
в уже начатом аудите; для них также нужно новое имя.
