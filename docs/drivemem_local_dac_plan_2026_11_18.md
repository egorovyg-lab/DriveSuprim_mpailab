# DriveMem: память локальных свидетельств выхода за drivable area

Дата: 18 ноября 2026. Статус: новая проверяемая гипотеза, до реализации опыта.
Ветка `main`; вычисления сначала на Astra (две GTX 1080 по 8 ГБ).

## 1. Узкое утверждение

Проверяем только один механизм: **выход угла footprint автомобиля за статическую
drivable area в интервале 1–2 секунды после текущего наблюдения**.

Это заранее выбранный ближний участок: избегаем требования восстановить всю
четырёхсекундную дорогу и не начинаем с самых близких к кузову точек. Никакой
гарантии его наблюдаемости нет — её проверяет A. Окно не выбрано по времени
уже известных удачных исправлений.

Предполагаемая дополнительная информация памяти — размеченные локальные
визуальные примеры дорожной границы у конкретной проверяемой точки. Их нужно
сопоставлять с аналогичным участком текущего изображения, а не с усреднённой
сценой или общим остатком PDM.

Две отдельные гипотезы:

- **H_spatial:** привязка изображения к углам исполненной траектории позволяет
  распознавать этот локальный выход лучше глобальных/decoder признаков.
- **H_memory:** при том же пространственном представлении, обучающих точках и
  метках обращение к отдельным историческим примерам даёт добавочный выигрыш
  относительно обычного обученного verifier.

H_spatial может подтвердиться без H_memory. В этом случае получен результат
пространственного verifier, а самостоятельная польза DriveMem не установлена.
Эта теория не обещает находить столкновения, TTC, светофоры или поздние выезды
после двух секунд. Итоговый полный четырёхсекундный PDM всё равно обязателен.

## 2. Основания и отрицательные результаты

На 651 сцене / 32 сессиях остаточная память top64 дала −1,8688 п.п. к DS,
C2−C1 = −0,5041 п.п. Все семь новых safety-ошибок сопровождались поправкой
разности действий в неправильную сторону. Из 71 потери относительно C1:
40 — wrong direction, 24 — overshoot, 7 — уменьшение ошибки без верного выбора.
Преимущества над random/shuffled memory нет.

В разобранной сцене `16203587e1f15918` все десять донорских действий имели
нулевые изменения PDM и компонентов. Они переносили ошибки исторической
модели, не предупреждение о текущем DAC. В `53a11dd8c7b158c7` избыточный
исторический пессимизм стал положительной поправкой к TTC-опасному действию.
В `b0b2f29233f15cfb` реальные донорские нарушения DAC/TTC оштрафовали удачный
выбор C1 сильнее неудачной альтернативы. Поэтому скалярный residual больше
не является содержимым нового банка.

Независимый от памяти геометрический контроль уже выполнен в другом этапе:
точная текущая карта + штатный ego rollout + top16 исправили 9 из 11 baseline
DAC failures в шести сессиях; macro local PDM +1,0698 п.п., без сильнейшей
сессии +0,8300. Это привилегированный reference, не результат камерной модели.
Совпадение с raw DAC 10416/10416 ожидается по конструкции геометрии метрики.

Номинальная траектория для этой задачи недостаточна: raw geometry имела
345 расхождений с DAC. Используем фактически рассчитанный ego rollout по
сохранённому контроллеру и начальному состоянию; чужое записанное будущее
для этого не требуется.

## 3. Что действительно имеется в данных

Пересчитано по локальной копии `results/pool64_v1/per_candidate.csv.gz`:
651 уникальная сцена, ровно 64 уникальных кандидата на сцену (41664 строки).

| Пул | Строк | DAC<1 | Сцен с таким кандидатом | Сессий с таким кандидатом |
|---|---:|---:|---:|---:|
| DS baseline | 651 | 11 | 11 | 6 |
| top16 | 10416 | 201 | 41 | 15 |
| top64 | 41664 | 1001 | 97 | 23 |

Это четырёхсекундные raw labels. Поддержка именно интервала 1–2 секунды и
поддержка наблюдаемых камерой выходов ещё не установлены. Их нельзя вывести
из одного минимума clearance по всему горизонту. Кандидаты/углы/кадры внутри
сцены коррелированы; 201 строка не равна 201 независимому случаю.

Таблица `results/astra_cpu256_v1/per_candidate.csv.gz` содержит измеренное
подмножество кандидатов, а не полный пул 651×256. Её наличие не принимаем
за готовый большой обучающий набор. Локальные копии результатов не изменяем;
для запуска привязываем данные к исходным Astra manifests/hashes.

**Основной пул нового опыта — top16.** Он совпадает с выполненным
геометрическим контролем. Top64 не подмешивается в банк только для памяти;
его возможное расширение — отдельный последующий эксперимент.

## 4. Этап A: проверка наблюдаемости и достижимого эффекта, без обучения

Это ближайший конкретный шаг, до экспорта новых признаков и обучения.

1. На тех же 651 training-сцене / top16 взять сохранённые rollout poses,
   размеры автомобиля и sampling. Фиксированное окно: t=1,0..2,0 с шагом
   исходного sampling; четыре угла. Не менять окно по понравившемуся gain.
2. На CPU получить локальные map labels: для каждой точки inside/outside,
   а для кандидата `Y_near=1`, если хотя бы одна точка окна вне drivable area.
   Проверить тот же boundary convention, что у исходного DAC. Это новые
   производные labels из существующей карты, не новые full PDM scorer calls.
3. Спроецировать эти точки в текущие L0/F0/R0 камеры с исходными calibration,
   distortion, crop и resize. Развести причины недоступности: FOV, crop,
   текущий кузов, сомнительная calibration/плоскость, заслонение.
4. Просмотреть overlays 11 baseline DAC failures и сопоставленных контролей.
   Отметить, видна ли граница около проблемных точек. Это ручная диагностика
   наблюдаемости; её аннотации не становятся скрытыми входами query worker.
5. Посчитать для фиксированного окна: baseline failures, кандидаты-замены,
   число поддерживающих сессий, наблюдаемые/непроецируемые участки,
   распределение времени полного DAC failure относительно окна.
6. Привилегированный reference: при истинном `Y_near=1` baseline выбрать
   первый в DS ordering кандидат с `Y_near=0` и требуемым проекционным покрытием.
   Оценить сохранённый полный PDM и все компоненты. Отдельно oracle по исходам
   допустимых кандидатов — только верхняя граница, не policy.

Проецируемость — верхняя граница наблюдаемости. Она не доказывает отсутствия
окклюзии и не превращает закрытую машиной точку в визуально размеченную дорогу.
При приближении плоской земли map-проекции являются weak supervision;
расхождение с реальной поверхностью и семантикой карты проверяется отдельно.

**Переход к B:** минимум пять доступных полезных исправлений в трёх сессиях;
положительный полный PDM у reference, без наблюдавшихся новых ухудшений пяти
safety-компонентов. Числа — инженерный минимум для малого опыта, не оценка
мощности независимого испытания. Если поддержка меньше, текущие данные не
позволяют убедительно проверить именно эту теорию: фиксируем ограничение,
не переносим автоматически +1,07 п.п. прежнего полного геометрического опыта.

Для каждого будущего train fold отдельно проверяется наличие inside/outside
labels в нескольких сессиях; массовое число углов не заменяет это условие.
Не открываем reserved holdout ради увеличения числа положительных примеров.

## 5. Представление и supervision в B

Рамка проверки: текущие камеры → замороженный R34 spatial feature grid →
локальный patch около проекции угла → оценка inside/outside в этой точке.

Input-only worker получает текущие изображения, calibration, ego state,
габариты и вычисленные ego rollout poses. Из прежних признаков можно дать
teacher heads/decoder: они одинаковы во всех matched memory-контролях.
HD-map polygons, point labels, measured clearance, будущие actors и PDM
запроса не передаются inference worker. Подготовка labels — отдельный процесс.

Новый RGB export работает только с frozen backbone и уже сохранёнными
candidate IDs. Не повторяет выбор 8192→256, не меняет старые logits и не
возобновляет неудачные ветки decoder parity. Новый sidecar имеет собственные
identity и repeat checks; все сравниваемые методы используют одну его копию.

Patch descriptor сохраняет пространственную привязку; дополнительные входы —
координата/масштаб проекции, время, направление footprint и наблюдаемый ego state.
Полная scene embedding сама по себе не служит ключом поиска. Номер кандидата,
token и session ID не входят в обучаемые признаки.

Основная метка: `y(point)=1` для выхода за drivable area, иначе 0. Точки под
кузовом и непроецируемые точки не получают фиктивную метку inside. Сомнительные
проекции исключаются по заранее заданному техническому правилу, не по PDM.
Заслонение нельзя исключать через query GT annotations. До обучения нужно
зафиксировать реально доступную обработку unknown; ручной visibility oracle
не допускается. Если такой контракт не получается, сохраняем этап A как
диагностику и не называем последующий опыт проверкой видимой дороги.

Одинаковый supervision manifest для всех вариантов: разрешённые training
сцены, кандидаты, точки, map labels, masks и веса. Ограничить повторяющиеся
почти одинаковые ground anchors и число точек на сцену; при балансировке классов
сохранить одинаковые weights/точки у всех learners и банка. Конкретный лимит
фиксируется по input-only resource pilot, до outer-результатов.

## 6. Этап B: сначала проверить пространственную информацию

Без памяти сравниваются:

| Вариант | Назначение |
|---|---|
| Исходный teacher DAC | Необучаемый ориентир; его score не является локальной point label |
| Decoder/global verifier | Те же локальные labels и геометрия, глобальное представление изображения |
| Aligned spatial verifier A | Patch действительно соответствует проверяемому углу |
| Shuffled-spatial verifier | Та же размерность/архитектура, но пространственная привязка patch разрушена input-only перестановкой |

В сравнении global/spatial входная информация намеренно меняется — это
H_spatial. Для H_memory ниже она уже не меняется. У shuffled-spatial контроля
нужна одинаковая процедура train/query; permutation не использует labels.

Проверяем point errors и candidate-event errors, особенно ложные отклонения
действительно допустимого baseline. Общая accuracy не решает вопрос: 640/651
baseline имеют полный DAC=1. Все оценки агрегируются по сессиям.

Переход к памяти оправдан, если aligned представление даёт полезные решения
в нескольких сессиях и воспроизводимо лучше global/shuffled контролей.
Нулевое вмешательство при высокой accuracy положительным результатом не считается.

## 7. Этап C: память физических примеров вместо остатка модели

Запись памяти:

`(local patch descriptor, projection/footprint context, direct outside label, provenance)`.

Модель, которая когда-то предсказывала для донора PDM gain, для этой записи
не нужна. Метка имеет одну физическую интерпретацию; DAC/TTC/progress не
складываются в один переносимый residual. Это supervised memory с map labels,
а не память только реально исполненных водителем действий.

Простая фиксированная версия: найти до пяти ближайших разрешённых примеров
из разных donor sessions; получить взвешенный outside score `s_K`. Расстояние
считает отдельно нормированные patch и projection/footprint блоки с равным
суммарным весом. Нормировки и bandwidth — только training. Радиус поддержки
`h` фиксируется как 90-й процентиль расстояния до ближайшего примера другой
сессии на training probes; веса `exp(-d/h)`. Учитываются только доноры с d≤h,
минимум из трёх сессий. Иначе память воздерживается и остаётся score A.
Основной memory score: `s_M = 0,5*s_A + 0,5*s_K`; коэффициент не выбирается
по outer-результатам. Значения называем scores: калиброванный риск не обещается.

Контроли при одинаковых patch features, labels и policy:

- **A:** обычный spatial verifier, обученный на всех разрешённых labels.
- **M:** тот же A плюс описанная память.
- **E:** среднее A и второго такого же verifier с другим заранее заданным seed;
  контроль дополнительного параметрического сглаживания/обучения.
- **S:** те же найденные доноры, distances и weights, но labels перемешаны
  внутри training session и заранее заданных projection-range bins. Сохраняем
  class prevalence, разрушаем связь patch с его собственной меткой.

Для S пять фиксированных seed, все результаты и средний эффект сохраняются;
удачный seed не выбирается. Банк не получает top64 labels, если A обучен на
top16. Весь training набор доступен A/E, а не только его бывшая роль F.

Память здесь может оказаться обычным менее удачным классификатором. Наличие
понятного примера у query ещё не является её самостоятельным преимуществом.

## 8. Фиксированная политика вместо свободного reranking

Меняем только решения с диагностированным near-window выходом:

1. Если baseline не классифицирован как bad — сохранить DS.
2. Если baseline bad — взять первый clear кандидат из исходного top16 DS.
3. Если clear кандидата нет — сохранить DS с причиной отказа.

Интервал 1–2 с, критерии bad/clear/unknown, sampling и tie-breaking одинаковы
у A/M/E/S. Первая версия использует фиксированные score cutoffs bad≥0,9,
clear≤0,1. Это инженерные пороги, не вероятностная гарантия. Bad требует
поддержанного свидетельства хотя бы в одной точке; score кандидата — максимум
outside scores по проверяемым точкам. Clear требует прохождения
всех требуемых точек окна и согласованного input-only coverage contract;
недоступные/неопределённые точки дают unknown. Ненаблюдаемость не равна inside.

Clear означает только проверку указанного окна данным модулем. Нарушения
раньше/позже, ошибки восприятия, TTC и остальные риски остаются возможны.
Мы не выдаём near-window verifier за сертификат четырёхсекундного DAC.

Пороги не подбираем по 651 OOF результату. Если фиксированная policy никого
не пропускает или создаёт вред, это исход опыта. Новый набор порогов — новая
гипотеза с отдельной проверкой, а не исправление опубликованного результата.

## 9. Разделение и метрики

Повторно использовать четыре фиксированные группы сессий прежнего опыта:
каждая оценивается один раз, обучение и банк — только остальные 24 сессии.
Собственная query session целиком отсутствует в донорах, нормировках, PCA/
проекциях и fitting. Любой внутренний подбор делается только внутри этих
24 сессий; запросы inner group также не входят в её банк. Direct labels в
банке не требуют восстановления исторических cross-fit PDM residuals.

Основная оценка — полный stored raw local PDM, равный вес сессиям:

- M−DS, M−A, M−E, M−среднее(S), paired bootstrap целых сессий;
- новые DAC/NC/DDC/TLC/TTC ухудшения, LK/progress/comfort отдельно;
- правильные исправления baseline DAC и false baseline rejections;
- missed repairs: отдельно окно, наблюдаемый поддержанный поднабор и все
  11 полных baseline DAC failures. Не выкидывать неизвестные сцены из общего gain;
- все 32 session effects, концентрация, результат без лучшей сессии;
- coverage/abstention и причины unknown. Общий знаменатель policy — все 651
  сцена, а не только случаи, где модулю удобно отвечать;
- ошибки до/внутри/после окна, чтобы не приписать near-window методу решение
  другой задачи. Показывать и исходную частоту, и эффект относительно A.

**Критерий самостоятельной пользы памяти:** положительный PDM относительно
DS; минимум +0,1 п.п. M−A; нижние границы парных exploratory 95% интервалов
M−A, M−E и M−среднее(S) выше нуля; польза минимум в трёх сессиях и положительный
M−A без лучшей сессии. Нет наблюдавшегося нового вреда пяти safety-компонентам
относительно DS; число PDM-потерь и худшая потеря не хуже A.

Порог +0,1 п.п. — инженерный минимум малого DAC-опыта, заранее заданный,
не результат поиска на новой выборке. Если геометрический near-window reference
слишком слаб даже для такого масштаба, стадия A должна остановить затраты.

Когорта уже многократно исследована. OOF/интервалы здесь диагностические,
особенно при небольшом числе baseline failure sessions. Успех даёт право
заморозить метод и спланировать независимое испытание; fresh holdout не
открывается автоматически. Абсолютная безопасность не следует из нулевого harm.

## 10. Порядок работы и ресурсы

1. Сейчас: зафиксировать отрицательный residual-memory результат и этот план.
2. Следующая реализация: CPU-аудит near-window labels/наблюдаемости/reference
   с отдельным root и без обучения. Существующие геометрические packets и
   проекционные helpers переиспользуются только после проверки provenance.
3. При достаточной поддержке: frozen R34 spatial export, batch=1 resource
   smoke на GTX 1080, затем простые matched heads на CPU. Сначала оценить время,
   размер cache и память, не обещать завершение «за ночь».
4. Только после H_spatial: memory comparison на том же cache. A100 можно
   использовать для ускорения или большей модели, когда это обосновано
   результатом и зафиксировано отдельным resource protocol. Новый большой
   encoder/дообучение DS не являются первым шагом.

Новые архивы и платный inference не входят в этот план. Меняются только новые
документы/позднее новые модули в `main`, доставка commit→push→pull пользователем
на Astra. Существующие identities, результаты и файлы других исследований
не переписываются. Отчёт реального projection audit и визуальная проверка
камер пока не подтверждены; это ближайшая неопределённость.

  поддержки выше относятся к четырёхсекундным labels, не к новому окну.

Эта версия не запускает обучение и не утверждает, что доступность визуального

## Запуск двух CPU-аудитов

После обновления `main` запустите из терминала Astra:

```bash
docker exec -w /workspace/DriveSuprim egorov_drivesuprim \
  python -u -m navsim.planning.script.run_drivemem_dac_window

docker exec -w /workspace/DriveSuprim egorov_drivesuprim \
  python -u scripts/drivesuprim/evaluation/audit_drivemem_risk_coverage.py
```

Входы берутся из `corridor_geometry_v2` и `residual_memory_top64_v1`.
Оба выхода находятся в
`/workspace/exp_v2/drivemem_memory/experiments`. Можно указать свой
`--out`, а источник переопределить через `--geometry` для DAC и `--root`
для сравнения правил отказа.

- В `drivemem_dac_window_v2` сохраняются три проверки окна. `map_reference`
  выбирает первый допустимый по карте кандидат. `fov_reference` требует
  хотя бы одну проецируемую точку выхода baseline и проецируемость всех
  нужных углов альтернативы за пределами текущего кузова. Отдельный
  `safe_fov_oracle_gain_macro_pp` отбирает альтернативы по истинным исходам
  среди тех, что исправляют полный DAC и сохраняют safety-компоненты.
  `per_scene.csv` и `window_points.npz` дают покомпонентный gain и маски.
  Счётчики до, внутри и после окна могут пересекаться.
- `full_horizon_projection` показывает для каждого выезда baseline доступность
  камеры, проецируемость первого выхода, любого выхода и выхода после 2 с.
  Панорамы полного горизонта находятся в `preview_full/`. Метрики по полному
  горизонту диагностические. Проверка общей начальной позы использует ту же
  конвенцию yaw, что NAVSIM, а обзор камеры по-прежнему строится с полным
  трёхмерным вращением. Ошибки позиции и угла выводятся отдельно.
- `fov_prescreen_passed` показывает предварительную достижимость по проекциям.
  Для проверки изображения откройте панорамы в `preview/` и заполните
  **копию** `review_template.csv`. Для каждого предложенного переключения
  отметьте, видна ли дорожная граница у выхода baseline
  (`baseline_witness`) и достаточно ли виден проверяемый коридор альтернативы
  (`replacement_corridor`). Допустимы `visible`, `occluded`, `ambiguous`,
  `unknown`. Совпадение с картой само по себе недостаточно. Привязку к сцене,
  обеим траекториям и PNG сохраняют первые пять полей. Затем запустите тот же
  DAC модуль с `--review /path/in/container/review.csv`. В
  `review_report.json` поле `proceed_to_verifier` относится к случаям с двумя
  отметками `visible` и прежним критериям перехода.
- В `drivemem_matched_coverage_v1` файл `risk_coverage.csv` сравнивает правила
  при одинаковом числе замен. Покрываем 10/25/50/75/100% доступных предложений
  с округлением вверх, а охват в отчёте считаем от всех сцен. Сравниваются
  близость донора, сохранённый прогноз выигрыша C2 и оракул с приоритетом
  отсутствия ухудшений safety. Для сравнения с C1 берём худшее из ближайших
  расстояний для двух небазовых действий. Если одно из действий исходное DS,
  используем расстояние для другого. Расстояние нормировано на bandwidth
  соответствующего fold. В `distance_bins.csv` показаны измеренные исходы
  по диапазонам расстояний, рангам и срезам данных. В `summary.json` есть
  парная разность полезности и правила расстояния с бутстрепом по сессиям.
  Это ретроспективные кривые на просмотренной когорте.

## Пространственный пилот на msu270

Проверяем, помогает ли признак R34 в проекции угла будущего положения
кузова отличить выезд за границу дороги от проезда рядом с ней. Когорта
фиксирована по `corridor_geometry_v2` и содержит 651 train-сцену из 32
сессий. Используем все top16 DriveSuprim и четыре внешних разбиения по
целым сессиям. Окно выборки — 0,5–4 с с шагом 0,1 с. В аудите большинство
первых выездов было после 2 с. Итоговый raw DAC оценивается по всем 4 с.
Точки под текущим кузовом и вне кадра считаются неизвестными. Проекция
определяет область обзора. Фактическая видимость может быть хуже из-за
перекрытий.

| Вариант | Визуальный признак |
| --- | --- |
| `aligned` | Билинейная выборка из карты `layer3` R34 в проекции точки, с усреднением окна 3×3 карты признаков |
| `global` | Среднее по той же карте признаков кадра |
| `shuffled` | Те же локальные векторы, переставленные между проецируемыми точками внутри сцены |
| `teacher` | Штатная оценка риска DAC от DriveSuprim для каждой траектории |

Три обучаемых варианта используют один набор точек, одинаковый линейный
классификатор с L2, проекции, геометрию, состояния декодера и DAC-логит
DriveSuprim. Изображения текущего кадра берутся из исходных JPEG. Панорама
собирается с теми же границами кадрирования для трёх камер, размер
приводится билинейным resize Pillow. Координаты хранятся отдельно от
карточек с метками. Карта даёт метки для обучения на чужих сессиях и
проверки замороженных решений. Добавочный срез оценивает ложные
срабатывания на углах в пределах 0,5 м от границы объединённой области
карты у траекторий, которые сохраняют DAC на полном горизонте.

Правило выбора одинаково во всех четырёх вариантах. Пробуем замену, когда
хотя бы одна наблюдаемая точка baseline имеет оценку выезда ≥0,90.
Берём первый по рангу DriveSuprim кандидат, у которого спроецированы
≥60% углов и все позиции `(время, угол)` с высоким риском baseline.
Каждая из его спроецированных точек должна иметь оценку выезда ≤0,10.
В остальных сценах сохраняем baseline. Эти пороги фиксированы для первой
проверки. Баллы модели не интерпретируются как оценка вероятности риска.

Создайте отдельный checkout из `main`, чтобы Drex мог продолжать работать

```bash

  | tar -xzf - -C "$DREX_RUNTIME_ROOT/data"
```

Когда transfer завершится, отправьте две связанные задачи:

```bash
bash "$HOME/drivesuprim-dac/scripts/drivesuprim/evaluation/run_drivemem_spatial_dac_msu.sh" submit
squeue -u "$USER"
```

Первая задача выделяет одну GPU, проверяет загрузку весов и обработку
четырёх сцен, затем завершает полный экспорт. Вторая стартует после её
успешного завершения, на CPU. Снимки моделей, решения и результаты
сохраняются в `$DREX_RUNTIME_ROOT/runs/drivemem_spatial_dac_v1`. Скрипт
по умолчанию использует Python из существующего runtime Drex с NumPy,
Pillow, PyTorch и torchvision. Проверку интерпретатора выполняют
на вычислительном узле. Исходные изображения читаются из пакета Drex
`$DREX_RUNTIME_ROOT/data/navsim_train_v1/package/images`. Если пути
отличаются, задайте `DAC_PYTHON`, `DAC_IMAGES`, `DAC_DATA` или
`DAC_OUT` перед `submit`. Для выбора раздела используется `DAC_PARTITION`
с резервом `DREX_PARTITION`, по умолчанию `batch`. После прерванного
запуска тот же экспорт продолжает проверенный кэш в том же окружении.

```bash
tail -n 30 "$DREX_RUNTIME_ROOT/logs/dac-r34-"*.log
tail -n 30 "$DREX_RUNTIME_ROOT/logs/dac-probe-"*.log
cat "$DREX_RUNTIME_ROOT/runs/drivemem_spatial_dac_v1/report.json"
```

Основной результат — raw local PDM с равным весом сессий и парный
бутстреп по сессиям. Проверяем AP для выхода на наблюдаемой части
траектории, число исправлений и пропусков доступных DAC-исправлений,
ложные тревоги, потери PDM и ухудшения safety-компонентов. В
`per_scene.csv` и `per_session.csv` видны отдельные вмешательства и их
концентрация. Следующий пилот имеет смысл, если выровненные признаки
дают больше AP и PDM, чем оба визуальных контроля, улучшают PDM против
DriveSuprim, исправляют DAC минимум в двух сессиях, сохраняют
положительный PDM без сильнейшей сессии и не добавляют safety-ухудшений.
Даже при выполнении этих условий результат остаётся разведочным на
train-когорте. Память в этом пилоте отсутствует.
