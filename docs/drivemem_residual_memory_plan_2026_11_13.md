# DriveMem: минимальная проверка памяти ошибок обучаемого селектора

Дата: 13 ноября 2026. Статус: план до реализации и получения новых результатов.
Рабочая ветка: `main`. Основная машина: Astra, контейнер `egorov_drivesuprim`.
На Astra две GTX 1080 по 8 ГБ; A100 доступны отдельно, но для этого этапа не нужны.

## 1. Решение, которое должен дать эксперимент

Проверить, помогает ли обращение к исходам похожих исторических действий
выбирать траекторию **сверх обучения на тех же исходах**. Память должна
превзойти обычный селектор и сопоставимый обучаемый корректор, а не только DS.

Это проверка конкретного способа использования памяти на сохранённых данных.
Она не доказывает преимущество памяти над любым возможным селектором.
Обученная модель тоже получает информацию из истории через свои веса;
добавочный механизм DriveMem — локальное обращение к отдельным примерам.

**Гипотеза H1:** остаточные ошибки селектора при оценке замены DS повторяются
у похожих пар «сцена, действие относительно baseline». Их перенос из других
сессий улучшает фактический raw local PDM по сравнению с тем же селектором
без обращения к памяти. Если перестановка исторических ошибок сохраняет
результат, гипотеза о содержательной пользе поиска не подтверждается.

Baseline в этом документе — исходная траектория DS. `C1` ниже — обучаемый
контроль без памяти. Это разные точки сравнения.

## 2. Почему меняем постановку

Проверенные ранее варианты DriveMem уже переносили ошибки прогнозов DS,
разности относительно baseline и непосредственный выигрыш PDM. Их нельзя
представлять как ещё не проверенные идеи. По отчёту от 7 ноября:

- первичный similarity-вариант не дал прироста;
- action-transfer дал положительный результат на первой development-когорте,
  но эффект зависел от одной сцены; на второй когорте B3 дал −0,958 п.п.;
- scalar pair utility на расширенном M/F дала около −8 п.п. на обеих когортах;
- компонентные ограничения уменьшали вмешательства вместе с пользой;
- decoder-memory guarded дала +4,065 п.п. на V1 и 0 на V2. Весь положительный
  эффект был в одной уже известной сессии; `primary=baseline` сохранился.

В текущем коде есть также MLP-селекторы и критики на 651 training-сцене из
32 сессий. По результатам чата «Продолжение работы DriveSuprim» устойчивого
преимущества top16-селекторов не установлено. Компонентный MLP с margin 2 п.п.
давал +0,142 п.п., интервал [−0,703; +0,817], с двумя ухудшениями safety.
Согласие моделей почти устраняло вмешательства. Новую память нужно сравнивать
с обучаемым контролем, а не повторять сравнение только с DS.

Из чата «Drex» и кода `codex/drex-max`, `7c123fb`:

- на тех же 651 train-сцене / 32 сессиях oracle top64 имеет резерв около
  +4,94 п.п., session bootstrap [3,41; 6,65];
- Drex с таблицей / таблицей и фото дал +0,282 / +0,146 п.п.; интервалы
  включают ноль. Дополнительная польза фото не установлена;
- лучший oracle-кандидат находится в рангах 17–64 в 196 сценах;
- DS-рейтинг и порядок показа сильно влияют на Drex; согласие перестановок
  не стало надёжным фильтром правильности;
- raw top64 labels уже собраны. Незавершённые 246 078 Drex-запросов не нужны
  для этого DriveMem-эксперимента. Их не повторяем и не используем как метки.

Новое здесь — **память остаточных ошибок уже обученного селектора**, широкий
пул top64 и строго сопоставимые обучаемые контроли. Новые фотографии,
HD-карта и дополнительные perception-модели в этот этап не входят.

## 3. Данные и проверка готовности на Astra

Используем только существующую training-когорту 651 / 32. Ожидаем:

| Артефакт | Назначение |
|---|---|
| `/workspace/exp_v2/drivemem_memory/selector_training_bundle_v3_30gb` | 256 кандидатов, DS logits/scores, scene/ego context, decoder states; исходные top16 labels и protected sessions |
| Raw labels эксперимента `table_topk_night_gpu8_v1` | Метрики всех top64, привязанные к физическим local/vocabulary IDs |
| `label_request.json`, `label_source.json`, `package_manifest.json` и соответствующие hashes | Проверка происхождения и точного совпадения когорт |

Полный путь к копии top64 labels на Astra нужно установить по существующим
артефактам передачи; не предполагаем, что путь с msu270 существует на Astra.
В `table_labels.py` remote root определяется через hash запроса, поэтому
название нельзя угадывать. Если конечного JSON нет локально, допускается
копирование уже полученных числовых labels и manifests, без повторного scorer
и без переноса фотографий. Объём сначала показывается в инвентаризации.

Перед fitting обязательны:

1. Ровно 651 уникальный token и 32 session ID, все с ролью `train`.
   Нет пересечения с protected sessions, включая четыре fresh holdout;
   старые development-когорты также не добавляются в этот эксперимент.
2. В каждой сцене один и тот же frozen DS baseline и stable top64 из
   сохранённых `selection_scores`; 64 уникальных local/vocabulary ID.
3. Покрытие labels: 41 664 строки, из них 41 013 альтернатив baseline.
   Это не 41 013 независимых наблюдений и не 246 078 Drex-запросов.
4. Для общих top16 совпадают ID и raw labels с bundle по исходным допускам
   Astra/Drex-протокола: `atol=1e-8`, `rtol=1e-7`. Любое несоответствие
   останавливает подготовку; автоматически пересчитывать метки нельзя.
5. Девять raw величин на кандидата: сохранённый scalar PDM и восемь
   компонентов; значения конечны и лежат в [0,1]. Scalar не восстанавливаем
   из filtered-компонентов. Filtered targets в этом этапе не используются.
6. Frozen decoder states `(256, 256)` и heads согласованы с этими IDs.
   Новый GPU export и ослабление parity-допусков не нужны.

Подготовка создаёт отдельный read-only input/label bundle top64. Старый
top16 bundle, identities и завершённые результаты не изменяются. Нельзя
молча перейти к меньшей удобной подвыборке, если аудит не прошёл.

## 4. Общие признаки и supervision

Все обучаемые варианты получают один и тот же полный training-набор,
все его top64 labels, одинаковые веса сессий и один allowlist входов:

- DS probability heads, imitation log-probability по исходным 256 кандидатам,
  selection score и их отличия от baseline;
- номинальная геометрия vocabulary-траектории и её отличие от baseline;
- замороженный decoder vector кандидата и его разность с baseline;
- сохранённый scene embedding и ego context.

Берём исходные числовые массивы, а не округлённые до четырёх знаков таблицы
из LLM-запросов. Геометрия номинальная: результаты controller rollout,
дорожные границы из scorer и будущее других участников не являются входами.
Token, session ID, vocabulary ID и ранг строки не становятся обучаемыми
эмбеддингами. Session ID используется для разделения и исключения доноров;
candidate ID — для проверки соответствия и детерминированных ничьих.

Основной target:

`u(q,c) = raw_PDM(q,c) - raw_PDM(q,baseline)`.

Из raw-компонентов можно получить тот же auxiliary benefit target для
обычного селектора; все варианты наследуют его через один общий checkpoint.
У памяти нет дополнительных размеченных сцен, дополнительных tail-кандидатов
или меток из оцениваемой сессии. Старый отдельный M-bank сверх разрешённого
training fold не подключается.

## 5. Что именно хранит память

Для исторической сцены `d` и альтернативы `a`:

`r(d,a) = u(d,a) - f_without_d_group(x(d,a))`.

`f` — обычный обучаемый селектор, предсказывающий выигрыш относительно DS.
Предсказание для вычисления остатка получено моделью, которая не обучалась
на **всей группе сессий** донора. In-sample training residual не используется.

Запись памяти содержит допустимые признаки пары, этот остаток и provenance
его получения. Baseline не добавляется как искусственный донор с нулевым
остатком. На запросе его предсказанный gain и поправка равны ровно нулю.

Поиск фиксируем до результатов:

- расстояние по четырём блокам общего представления: scene/ego context,
  DS predictions/gaps, geometry/deltas, decoder states/deltas;
- стандартизация только по разрешённому training fold; внутри каждого блока
  mean squared distance, затем среднее четырёх блоков. Большая размерность
  decoder не даёт ему автоматически больший вес;
- в каждой разрешённой donor session выбирается ближайшая пара. Из них
  берём пять ближайших **разных сессий**, а не пять коррелированных строк;
- `h` — медиана положительных расстояний до ближайшего донора другой сессии
  на не более чем 512 training probe-actions. Probes выбираются по hash,
  с равномерной квотой сессий, без меток;
- `w_j = exp(-distance_j / h)`;
  `m(q,c) = sum(w_j * r_j) / (1 + sum(w_j))`;
- итог `f_T(x(q,c)) + m(q,c)`. Множитель памяти фиксирован равным 1.
  При отсутствии поддержки поправка равна нулю, остаётся `f_T`.

Параметры поиска не подбираются по outer-результатам. Выбор ближайшего донора
не смотрит на знак или величину его остатка. Поиск и порядок суммирования
детерминированы; перестановка кандидатных строк не меняет физический выбор.
Нерасшифрованные команды ego не используются как придуманные hard-фильтры.

## 6. Контрольные варианты

| Код | Выбор | Что отделяет |
|---|---|---|
| C0 | Исходный DS | Польза всей замены исходного алгоритма |
| C1 | Обычный обучаемый top64 selector `f_T` | Основной контроль: те же признаки и все training labels, без retrieval |
| C2 | `f_T + m_nearest` | Единственный основной memory-вариант |
| C3 | `f_T + g_T` | Обычный второй MLP, обученный предсказывать те же cross-fitted остатки по тем же входам; контроль дополнительного обучения и коррекции ошибки |
| C4 | `f_T + m_random` | Пять случайных training sessions; внутри них ближайшие действия, та же формула весов/усадки |
| C5 | `f_T + m_shuffled` | Те же найденные доноры, расстояния и веса, но векторы остатков переставлены между training scenes разных сессий |

Для C5 целиком переставляем 63-мерные векторы остатков в DS-rank порядке,
сохраняя внутрисценовую корреляцию и связь с полосой рангов, но разрушая
связь с конкретной сценой/действием. Перестановка использует только training
fold; она не переносит остатки или labels outer-запросов.

Для C4/C5 фиксируем пять seed `20261113..20261117`. Показываем каждый и
средний эффект по seed; удачный seed не выбирается. Это отрицательные
контроли, а не дополнительные независимые датасеты.

Все C1–C5 используют **один и тот же** `f_T`. Общий selection rule: лучший
предсказанный gain должен быть не меньше 0,005 PDM, иначе сохраняется DS.
При численной ничьей baseline предпочтителен, затем минимальный физический
vocabulary ID. Порог не является гарантией истинного выигрыша или риска.
Нет veto «учитель обязан согласиться по всем heads», чтобы заранее не
закрыть исправления его собственных ошибок. Новые ухудшения измеряются явно.

Обычный selector C1: существующий coherent MLP stem width=64, 120 эпох,
AdamW lr=0,001, weight_decay=0,001, session-equal weights, gain/regret loss
из `trajectory_selector_v2`. Единственный seed модели `20261113`.
Новый top64 adapter должен заменить hardcoded top16, не менять остальные
условия. C3 использует такой же stem и отдельный baseline-anchored scalar
head: SmoothL1 по остаткам, beta=0,05, те же optimizer/epochs/weights.
Никакого перебора seed, эпох, h, числа соседей или новых gates в этом запуске.

## 7. Разделение сессий и cross-fitting

1. Один раз делим 32 сессии на четыре группы `G0..G3` по восемь. Сортируем
   по SHA256 от `20261113:session_id`, распределяем round-robin. Outcomes
   при создании `split.json` не читаются.
2. Outer fold: одна группа — запросы (8 сессий), остальные три — training
   `T` (24). Даже другие сцены той же query session запрещены как доноры.
3. Учим `f_T` на всех 24 training sessions. Это C1 для данного outer fold.
4. Для исторических остатков внутри `T` проводим три cross-fit: одну из
   трёх групп исключаем полностью, модель учится на остальных 16 сессиях.
   Ею предсказываем gain исключённой группы и затем вычисляем её остатки.
5. Эти остатки всех 24 training sessions образуют банк C2/C4/C5 и targets C3.
   Нормировки каждой cross-fit модели обучены только на её 16 сессиях.
   Retrieval-нормировка обучена только на outer training `T`.
6. Получаем решения C0–C5 для всех input-only запросов outer fold и сохраняем
   hashes решений. Только evaluator присоединяет их настоящие outcomes.
7. Повторяем четыре outer fold. Для каждой из 651 сцен имеется ровно один
   OOF-выбор каждого варианта.

Группы фиксированы, настройки не выбираются на inner или outer метриках:
внутреннее разбиение нужно для честных остатков, не для поиска параметров.
Модель на 16 сессиях и модель на 24 могут иметь разный уровень ошибки — это
ограничение переноса остатков. C3 и memory получают одни и те же остатки.

Можно переиспользовать шесть моделей на двух группах между outer fold,
если совпадают точный список training sessions, входы, нормировка, код и seed.
Тогда бюджет — **10 базовых fits + 4 residual-MLP fits = 14 fits**, а не
четыре независимых запуска полного старого LOSO-перебора. Полное обучение
финальной модели на всех 32 сессиях и открытие holdout сюда не входят.

Важно: в OOF сессия, оцениваемая в одном fold, закономерно является training
для других fold. Это допустимо. Влияние её labels на её собственные решения
недопустимо. Проверяется provenance по каждому fold, а не утверждение, что
все 651 labels нигде не загружались до завершения обучения.

## 8. Метрики, которые решают вопрос

Основная величина — равновесный по сессиям raw PDM gain относительно DS:

`G(M) = 100 * mean_sessions(mean_scenes(Q(chosen_M) - Q(DS)))`.

Главное парное сравнение — `D = G(C2) - G(C1)`. Также обязательны C2−C3,
C2−mean(C4), C2−mean(C5). Для каждой разности используем одни и те же
10 000 bootstrap-перевыборок **целых сессий**, seed `20261113`; сохраняем
распределения и percentile 95% intervals. Candidate rows и seed не считаются
независимыми наблюдениями. Разбиение и состав групп остаются фиксированными.

В отчёте для каждого метода:

- session macro и scene micro gain; число вмешательств, улучшений,
  равенств и потерь; сумма полученной пользы и сумма потерь отдельно;
- все 32 session means, доля сессий с положительным/отрицательным эффектом,
  худшая сессия/сцена, вклад лучших одной и двух сессий; mean после их
  исключения как чувствительность, без удаления из основного результата;
- фактическое ухудшение каждого NC, DAC, DDC, TLC, TTC относительно DS;
  LK, progress и comfort показываются отдельно. «Относительный harm=0»
  не означает абсолютную безопасность;
- отдельно изменения C2 против **выбора C1**: новые потери, устранённые
  потери и новые safety-degraded сцены. Нельзя скрывать новый вред тем,
  что память исправила другое место;
- oracle regret `max_top64(Q) - Q(chosen)` и доля извлечённого резерва;
- упущенные исправления: сцены с альтернативой, дающей ≥0,005 PDM без
  ухудшения пяти safety-компонентов, где метод такого исправления не сделал.
  Показываем также недобранный безопасный oracle gain;
- отдельная таблица для рангов 17–64: доступный резерв, выборы, полезные
  замены, потери и safety harm. Oracle tie с top16 не объявляется уникальной
  возможностью хвоста; считаем и строгий дополнительный резерв top64−top16;
- uniform/challenge отдельно при наличии provenance, без подмены основного
  результата удачным срезом. Доли срезов и archive-selection bias сохраняются.

Совпадение donor/query, sign accuracy остатка и качество retrieval — только
диагностика. Оракул, использующий истинный outcome запроса, только верхняя
граница и не является policy или источником меток для данного запроса.

## 9. Заранее заданное решение после запуска

**Продолжать именно эту memory-гипотезу** имеет смысл, если одновременно:

1. C2 улучшает DS, а дополнительный эффект C2−C1 составляет хотя бы
   **+0,25 п.п.** и нижняя граница его session-bootstrap interval выше нуля.
   0,25 п.п. — заранее выбранный инженерный минимум для следующего этапа,
   не результат подбора по этому запуску.
2. C2 превосходит C3 и средние C4/C5; нижние границы соответствующих парных
   интервалов также выше нуля. Иначе нельзя отделить пользу поиска от
   обычного корректора, усадки или случайных исторических остатков.
3. C2−C1 остаётся положительным после исключения лучших одной и двух
   сессий. Улучшение C2−C1 хотя бы на 0,5 п.п. есть минимум в трёх сессиях.
4. Не появляется ни одной новой safety-degraded сцены относительно DS
   там, где C1 не ухудшал safety. Число PDM-потерь и худшая потеря
   относительно DS не хуже C1. Все небольшие потери тоже публикуются.

Это строгий критерий перехода, а не сертификат безопасности. Если PDM-сигнал
есть, но пункт 4 не выполнен, фиксируем «полезный перенос с неприемлемыми
новыми ухудшениями», сохраняем primary=DS и не подбираем gate на outer-данных.
Если C2 лучше DS, но не C1/C3, пользу обучаемой коррекции можно признать,
а самостоятельную пользу памяти — нельзя. Если интервалы включают ноль,
результат неопределённый, а не доказательство отсутствия любого эффекта.

Эти 32 сессии уже исследовались. OOF и bootstrap здесь — проверка механизма
и устойчивости на training-когорте, не независимое подтверждение статьи.
Перекрывающиеся training folds также ограничивают статистическую трактовку.
Успех позволяет заморозить метод и отдельно спланировать проверку на новых
сессиях; не открываем существующий holdout автоматически после красивого числа.

## 10. Реализация и ресурсы следующего шага

После согласования плана подготовить отдельный CPU pipeline в `main`:

1. `check`: meaningful tests на исключение целой сессии, физическое
   соответствие labels/IDs, baseline=0, инвариантность перестановке,
   нечувствительность решений к подмене query labels и возобновление.
2. `inventory/plan`: обнаружить существующие Astra artifacts, проверить
   покрытие/hashes, сохранить protocol, split и ожидаемые 14 fits.
3. `smoke`: короткий полный цикл только на искусственных данных. Затем
   измерить время/память одного реального fit без просмотра outer-метрик.
4. `all`: последовательно выполнить готовые fits, memory controls и решения.
   Checkpoint каждого завершённого fit; lock, hash binding, fail-closed при
   несовместимых старых результатах. Новый протокол требует нового root.
5. `report`: полный OOF только после покрытия всех сцен; `status` показывает
   прогресс без запуска дополнительных jobs или открытия holdout.

Предлагаемое имя launcher: `run_drivemem_residual_memory.sh` (ещё не реализован).
Новый output root:
`/workspace/exp_v2/drivemem_memory/experiments/residual_memory_top64_v1`.
Сохранять inputs/labels manifests, split, fitted statistics, cross-fit
predictions/residuals, модели, donor traces, decisions до outcome join,
`per_scene.csv`, `per_session.csv`, paired comparisons и summary.

CPU runtime по умолчанию — 2 threads, float32 для MLP и float64 для расстояний,
весов и отчёта. Поиск блоками, без полного query×donor×feature tensor.
Время полного запуска оценить по pilot; заранее «за ночь» не обещать.
Нет BF16/FlashAttention/A100-зависимостей и новых image downloads.
GTX 1080 не требуется для этого этапа. A100 имеет смысл подключать позже
для нового представления/масштаба, если содержательная польза памяти отделена
от сильного обычного контроля; больший compute сам по себе не меняет вывод.

Порядок доставки по пожеланию пользователя: локальные изменения и проверки
в `main` → commit → push `origin/main` → пользователь делает `pull` на Astra
и запускает launcher в `egorov_drivesuprim`. Drex-ветку и её выполняющиеся
задания не меняем. Присутствующие незакоммиченные файлы других исследований
не включаем в DriveMem-коммит.
