# Разбор завершённого ночного table/image эксперимента

Это CPU-анализ ГОТОВЫХ решений и измеренных меток. Новых GPU-запросов,
scorer calls, обучения и чтения holdout нет. Исходный эксперимент не изменяется.
Отбор иллюстраций использует известные исходы и не является новым benchmark.

## Запуск на msu270

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
bash scripts/drex/run_table_case_audit.sh submit
```

Одна Slurm-джоба: сначала маленькие CPU-тесты, затем анализ 651 сцены, всех
11 718 запросов и 15 624 строк исходного CSV. Запрашиваются 2 CPU, 16G RAM,
`gres=none`, до одного часа. После постановки можно отключиться.
Для отдельных тестов без запуска анализа: `run_table_case_audit.sh check`.

Источник по умолчанию:
`/scratch/pr0201/drex_runtime/runs/table_topk_night_gpu8_v1`.
Выход: `/scratch/pr0201/drex_runtime/runs/table_cases_night_v1`.
Текущее `DREX_TABLE_NAME` (например, имя GPU binding-пробы) не влияет на выбор
источника. При необходимости явно задать `DREX_TABLE_AUDIT_SOURCE` и
`DREX_TABLE_AUDIT_NAME`; имена выходов должны начинаться с `table_cases_`.
Другой код/параметры для повторного исследования требуют нового имени аудита.

```bash
bash scripts/drex/run_table_case_audit.sh status
# ID напечатает sbatch:
tail -n 60 /scratch/pr0201/drex_runtime/logs/table-case-audit-JOBID.log
```

Вместо JOBID подставить число из `Submitted batch job ...`.

## Что проверяется

До чтения outcome-массивов проверяется полный decision commit, SHA всех worker
commit/environment/result файлов, отсутствие лишних/недостающих запросов и
нормировка распределений. Затем проверяются SHA источника меток, соответствие
request digest, полный top64 и совпадение с прежним top16. Замороженные решения
пересчитываются из вероятностей с исходным правилом выравнивания и tie fallback.

Исходный `per_scene.csv` не принимается на веру: проверяются все строки,
кандидаты, vocabulary IDs, PDM, дельты компонент и флаги. Итоговые макроприросты,
числа ухудшений/вмешательств и order flips сверяются с исходным report.json.
Для отобранных иллюстраций дополнительно восстанавливаются шесть исходных
запросов top64 и проверяются request hashes, включая исходные пиксели фотографий.
Для всего cohort request pixels повторно не регенерируются: проверяются уже
зафиксированные целые result files и первоначальный complete report/commit.

## Какие вопросы отвечает аудит

1. Где фото проиграло таблице и где было лучше. Различаются сохранение DS вместо
   плохой замены, уменьшение потери, дополнительный выигрыш, пропущенное улучшение
   и новый проигрыш относительно DS.
   Сохранение DS определяется по ID кандидата, а не по равенству PDM: другая
   траектория с тем же баллом относится к отдельной категории. Эти категории
   описывают наблюдаемые исходы, а не внутреннюю причину решения модели.
2. Из чего состоит эффект фото. Для каждой сцены `camera - table` точно
   раскладывается на уменьшение потерь относительно DS и изменение захваченного
   положительного выигрыша. Публикуются micro и macro, при том же полном cohort.
3. Какая польза top64 связана с выбором НОВОГО кандидата ранга >16/>32, а какая —
   со сменой выбора внутри прежнего пула. Вклады категорий считаются с нулями
   для остальных сцен и в сумме равны общему эффекту расширения.
4. Какие перестановки меняют только ID, какие дают равный PDM, какие меняют PDM
   минимум на 0.5 п.п. и какие ухудшают safety-компоненты относительно canonical.
   Сравнение перестановок не используется для выбора лучшего порядка постфактум.
5. Насколько выигрыш зависит от сессий. Есть исходные вклады, число вмешательств
   и потерь в каждой сессии, leave-best-one/two-out как анализ чувствительности.

`relative_safety_harm` относится к пяти компонентам NC/DAC/DDC/TLC/TTC и
сравнивается с DS. Нулевой harm не доказывает абсолютную безопасность. Отдельно
сохраняются все восемь компонент, включая lane keeping, progress и comfort.
Номинальная геометрия из словаря не подменяется исполнением контроллера.

## Результаты

- `report.json`: полные сводки, списки выбранных случаев и чувствительность.
- `image_pairs.csv`: все 651 сцена × три размера пула, выборы и парные различия.
- `order_effects.csv`: исходы canonical/reversed/permuted по измеренным метрикам.
- `all_scene_details.json`: измеренные компоненты и предсказанные признаки
  выбранных DS/table/camera/oracle для каждой сцены и размера пула.
- `index.md`: оглавление отобранных случаев с ссылками на PNG.
- `cases/NNN-TOKEN/summary.json`: подробности случая и причины его отбора.
- `cases/NNN-TOKEN/candidate_metrics.csv`: реальные метрики и предсказанные
  признаки всех 64 кандидатов, с исходным teacher rank.
- `cases/NNN-TOKEN/preview.png`: исходная доска камер и четыре НОМИНАЛЬНЫЕ
  траектории в общей метрической шкале. Это не карта, не проекция на дорогу и
  не симуляция. Oracle и метрики показаны только для постфактум-анализа.

По умолчанию до 64 иллюстраций, приоритет — image_worse, camera_pdm_losses,
table_safety_losses, camera_safety_losses, image_better, затем большие выигрыши.
Сводки и CSV всегда охватывают все сцены, а не только выбранные иллюстрации.

Для обсуждения прислать `report.json` и `index.md`; затем можно выбрать несколько
`summary.json`/PNG. По ним выбирается следующий контроль (matched blank image
или отдельная абляция DS score). Этот аудит сам не меняет prompts и не запускает
новый inference-протокол. Его изображения с oracle нельзя подавать модели.
