# DriveMem: план экспорта кандидатов и оракульного эксперимента

Дата: 26 октября 2026 года.
Статус: проект реализации, подготовленный после чтения локального кода; новые GPU-прогоны не выполнялись.
Исходный commit: `63ddb1eb3f97e0d899f426335fdc1c12768bbf7f`.

## 1. Цель и границы этапа

Определить, сколько качества теряется из-за окончательного выбора траектории DriveSuprim и какую часть резерва можно получить без ухудшения заданных компонентов безопасности.

Основной объект: опубликованный R34, teacher, NAVSIM v2, одна стадия refinement, три слоя, top-K 256. Настройки должны быть скопированы из фактически воспроизведённого запуска, а не восстановлены только по shell-скрипту. Зафиксированный результат v2: 83,0676746838 EPDMS; равенство округлённого балла само по себе не подтверждает идентичность всего протокола.

NAVSIM v1 остаётся отдельной задачей воспроизведения и не блокирует этот этап. Обучение памяти, FAISS и калибровка риска начинаются после проверки резерва. Наличие резерва необходимо, но ещё не доказывает, что его можно предсказывать по доступной в момент решения информации или извлекать из памяти.

## 2. Что установлено по коду

1. `navsim/agents/drivesuprim/drivesuprim_model.py`, `HydraTrajHead.forward`: оцениваются 8192 словарные траектории; по coarse score выбираются 256. Геометрия берётся из фактического `vocab` активной teacher-модели.
2. Там же, `RefineTrajHead.forward`: три decoder-слоя дают новые оценки тех же кандидатов. В проверенной реализации refinement не прибавляет геометрические смещения к траекториям. Окончательный выбор производится по `scores.argmax(1)` последнего слоя последней стадии.
3. `predictions['selected_indices']` относится к coarse-выбору среди 8192. Это не локальный индекс финального выбора среди 256.
4. В `predictions['refinement'][-1]` уже доступны `trajs`, `indices_absolute`, `layer_results`; финальные `scores` и локальный выбранный индекс сейчас явно не экспортируются.
5. `AgentLightningModuleSSL.predict_step_drivesuprim` сохраняет выбранную `final_traj`, но сопутствующие верхнеуровневые массивы метрик относятся к coarse-головам. Их нельзя использовать как финальные оценки 256 кандидатов.
6. `navsim/evaluate/pdm_score.py`, стандартный `pdm_score`: каждая предсказанная траектория оценивается в паре с опорной `metric_cache.trajectory` после LQR/bicycle-симуляции.
7. `PDMScorer._aggregate_pdm_scores` нормирует progress на максимум по переданным proposals. Замена пары [reference, candidate] пакетом [reference, 256 candidates] меняет метрику.
8. Готовая `pdm_score_full_v2` не является готовым решением: использует совместную нормировку, один вызов traffic policy для всех кандидатов и приводит выходные метрики к float16. Полная эквивалентность стандартной оценке не установлена.
9. Итоговый `score` в `run_pdm_score_one_stage_gpu_ssl.py` появляется после `SceneAggregator` и `compute_final_scores`. Он включает two-frame extended comfort между соседними ORIGINAL-кадрами одного лога. Поле `pdm_score` до агрегации не равно полному EPDMS.
10. `PDMScorer.score_proposals` обновляет переданный `observation`. Scorer, simulator и связанные объекты имеют изменяемое состояние: последовательность кандидатов и повторное использование кэша требуют проверки.

## 3. Основное архитектурное решение

Разделить процесс на четыре запуска: GPU-экспорт; CPU-оценка кандидатов; построение оракулов; отчёт. GPU не должен повторно исполнять модель при изменении анализа или метрик отчёта.

Первый рабочий вариант: один GPU, precision 32, batch size 1, последовательный экспорт. После подтверждения идентичности можно увеличить batch size и число GPU. CPU-работа распараллеливается по логам; внутри worker используются собственные объекты simulator/scorer. Полные данные не передаются через DDP `all_gather_object`.

Экспорт включается отдельной опцией и по умолчанию выключен. Изменения не добавляют параметры модели и ключи checkpoint. Формула выбора выполняется в том же месте и с теми же исходными тензорами; экспорт только считывает результат. Не сортировать и не переупорядочивать реальные кандидаты перед выбором.

### Точки изменений

| Файл | Предлагаемая роль |

## 4. Что сохранять

### Манифест запуска

`schema_version`, experiment id, дата, git commit и hash локального diff, SHA256 checkpoint, тип teacher/student, SHA256 фактического vocab, полная resolved Hydra config, версии runtime/CUDA/torch, precision, seeds, параметры refinement, sampling, traffic policy, scorer и human filter, идентификатор/manifest metric cache, упорядоченный список токенов и его hash, назначение split.

Точный checkpoint, vocab и scorer/cache должны относиться к одному запуску. Настройки выбора модели и веса итоговой метрики сохраняются отдельно: это разные формулы.

### Кандидаты

Общий `vocab.npy` активной модели, float32, ожидаемая форма [8192, 40, 3]. Проверить форму в runtime. Записывать один раз. Сравнить с `trajs` экспортируемой последней стадии; при несовпадении сохранить явную геометрию и остановить предположение об общем словаре.

Для каждого токена:

- `token`, `log_name`, timestamp, map id, frame type; неизвестные поля помечать явно;
- упорядоченные `candidate_absolute_ids`: [256];
- `selected_local_idx`, `selected_absolute_idx`, `coarse_selected_absolute_idx`;
- фактическая выбранная геометрия [40, 3] для независимой проверки;
- финальные selection scores [256] и raw logits девяти голов (включая imitation и history_comfort), имена и порядок голов;
- sampling, численная точность, validity и причина ошибки;
- coarse score для этих 256 кандидатов как дополнительная диагностика.

Внутренние embeddings, изображения и полные coarse logits [8192, 9] в обязательный экспорт не входят. Для будущей памяти можно добавить их отдельной версией схемы. Идентификатор кандидата имеет смысл только вместе с hash vocab и checkpoint.

### Результаты оценки

Для каждой пары token/candidate: все компоненты, возвращённые стандартной оценкой, векторы `weighted_metrics`, `weighted_metrics_array`, `multiplicative_metrics_prod`, локальный `pdm_score`, validity, время оценки. Скопировать массивы до следующего вызова stateful scorer. Не реконструировать результат только из отображаемых скалярных колонок.

Дополнительно сохранять raw progress и диагностические метрики до human filter, если извлечение проверено. Различать raw и benchmark-filtered показатели. Симуляционные состояния [41, StateIndex.size()] хранить в float64 на этапе проверки и построения двухкадрового комфорта; не округлять метки до float16.

Формат: NPZ/NPY-чанки плюс JSON manifests и CSV/Parquet для таблиц. Шарды ограниченного размера; запись временного файла и атомарное переименование. Состояние completed фиксируется после проверки содержимого. При возобновлении проверять совместимость manifest и hashes; существующие несовместимые результаты не смешивать. Дубликаты токенов разрешать только при полном совпадении данных, иначе ошибка.

## 5. Корректная оценка каждого кандидата

### Сначала эталонная реализация

Для каждого кандидата создать `Trajectory` с теми же 4 s / 0,1 s и выполнить стандартный `pdm_score` с той же опорной траекторией, кэшем и настройками, что при воспроизведении. В пилоте обеспечивать независимое исходное состояние observation/cache для каждого вызова (повторная загрузка или проверенная глубокая копия). Зафиксировать seed, если policy стохастическая.

Сохранить возвращённую строку и simulated states. Human penalty filter должен повторять базовый протокол, включая его работу с агрегированными полями. Если обнаружена ошибка согласования скалярных колонок и агрегатов, зарегистрировать её отдельно: не исправлять одновременно с проверкой идентичности. Исправленный протокол потребует повторной оценки baseline.

### Затем ускорение

В non-reactive log replay окружение не зависит от будущего ego-кандидата в прочитанной реализации. После тестов можно один раз преобразовать reference и кандидатов, пакетно выполнить симуляцию, затем считать metrics небольшими чанками. Но progress для каждого кандидата должен иметь ровно ту нормировку, которую дала бы пара [reference, candidate], с теми же multiplicative gates и порогом 5 m. Обычный вызов `score_proposals` на всём пакете это не обеспечивает.

Численные показатели human filter и reference можно кэшировать только после проверки независимости. Проверить chunks 1, 16, 64, полный пакет; перестановку кандидатов; baseline отдельно и внутри разных пакетов; повторный запуск. Использовать одинаковые исходные observation и policy.

Reactive policy потребует отдельного окружения для каждого кандидата; результаты policy одного кандидата не распространять на другие. Первый этап ограничить non-reactive настройкой воспроизведённого запуска.

Не использовать готовые обучающие scores словаря как эталон оракула без проверки их нормировки, human filter и точности: они могут быть сформированы по другой процедуре.

## 6. Три разных оракула

### A. Диагностический локальный оракул

Выбрать максимум по `pdm_score` без two-frame comfort отдельно в каждой сцене. Baseline для этого сравнения тоже пересчитывается без two-frame comfort. Это быстрый способ увидеть качество ранжирования. Название результата: «резерв локальной метрики без двухкадрового комфорта»; напрямую вычитать его из 83,0677 EPDMS нельзя.

Помимо unrestricted варианта посчитать constrained-вариант: candidate NC, DAC, DDC, TLC и TTC не ниже исходных в этой сцене. Для дискретных компонентов требовать отсутствие ухудшения, для непрерывных допускать только заранее заданный численный tolerance. Здесь «безопасность» означает эти измеренные компоненты; это не гарантия безопасности движения. Baseline входит в допустимое множество.

### B. Оракул одиночной замены при фиксированных остальных решениях

Полезен для первых примеров будущего вмешательства памяти. Заменить только выбор в сцене t, остальные решения оставить исходными. Пересчитать полный EPDMS с two-frame comfort. Изменение затронет строку t, а также комфорт следующей строки, если у неё предыдущим кадром является t. Учитывать оба изменения.

Такой анализ даёт эффект одной замены в фиксированном контексте. Сумма лучших эффектов отдельных замен не является выигрышем одновременного применения всех замен. Все выбранные одновременно решения затем прогоняются через общую агрегацию.

### C. Оракул полной метрики на цепочке соседних кадров

Для корректной верхней границы EPDMS оптимизировать последовательность выборов внутри каждого лога/связного временного сегмента, используя ровно adjacency mapping исходного evaluator. Не добавлять отсутствующие рёбра и не удалять рёбра при изменении набора кандидатов.

Пусть u_t(j) — итоговый вклад строки t без добавки двухкадрового комфорта, но с тем знаменателем, который положен этой строке. Для строки с predecessor знаменатель включает вес комфорта; для строки без predecessor применяется исходное правило NaN и исключения веса.

Для связанного кадра полная оценка строки:

`f_t(i,j) = gate_t(j) * (sum_non_TF_weights_t(j) + w_TF * comfort_t(i,j)) / denominator_t`.

`comfort_t(i,j)` берётся из исходной `ego_is_two_frame_extended_comfort` после такого же совмещения simulated states по временному сдвигу, как в `SceneAggregator`. При кэшировании производных сохранить порядок вычислений и проверить численную эквивалентность.

Динамическое программирование:

`V_1(j) = f_1(j)`;

`V_t(j) = max_i [V_(t-1)(i) + f_t(i,j)]`.

Восстановить путь по backpointers. Начинать новую цепочку при отсутствии ребра. Это точный максимум суммы строк для проверенного one-stage evaluator при фиксированных сценах, кандидатах, окружении и парной зависимости; это не closed-loop rollout и не оракул всей NAVSIM v2 со second-stage/pseudo-closed-loop агрегацией.

Считать unrestricted DP и DP с ограничениями NC/DAC/DDC/TLC/TTC относительно исходного выбора каждой сцены. Дополнительный строгий вариант запрещает ухудшение two-frame comfort относительно исходного ребра. Исходный путь должен оставаться допустимым. Разница constrained/unrestricted показывает цену ограничений.

После выбора пути обязательно повторно собрать обычный DataFrame и запустить исходные `SceneAggregator`/`compute_final_scores`. Совпадение с DP objective обязательно. Проверить DP против полного перебора на коротких цепочках с 2-3 кандидатами.

При одинаковом objective выбирать исходный вариант, если он даёт тот же оптимум; далее применять стабильный tie-break по абсолютному ID. Допуск равенства зафиксировать отдельно и не использовать для сокрытия ухудшения. Baseline сравнивается на точно том же множестве строк и с теми же правилами ошибок.

## 7. Выборки и порядок запусков

1. Проверка на 8-16 сценах, включая хотя бы две соседние цепочки из нескольких кадров. Выбор до просмотра результатов. Если берутся сцены из navtest, это только техническая проверка parity, без настройки исследовательских порогов.
2. Пилот порядка 256 целевых сцен из development-части navtrain с соседями; количество строк после добавления контекста явно сообщается. Логи для development, обучения модуля памяти и калибровки разделить до обучения этих модулей. Уточнить доступность train metric cache.
3. Расширение до порядка 1000-2000 сцен или большего числа логов, если pilot показывает широкий интервал. Для достоверной статистики важнее число независимых логов, чем число почти одинаковых кадров. Стараться иметь хотя бы 30 логов как практический ориентир; это не заменяет расчёт мощности.
4. Полный navtest используется после фиксации кандидатов, scorer и анализа как описательная проверка верхней границы. Его оракульные метки не идут в обучение/подбор порогов DriveMem. Поскольку navtest уже использовался для воспроизведения, точно описать историю его использования; новые параметры выбирать на development split.

Не формировать pilot только из ошибок baseline: это завысит средний резерв. Допустим отдельный error-enriched диагностический набор, но сообщать его результаты отдельно от случайной/групповой выборки. Соседние кадры не распределять по разным частям.

## 8. Проверки, без которых не масштабировать

- Export on/off: одинаковые выбранные absolute IDs и геометрия на одном устройстве и batch; проверить baseline raw scores и heads.
- Выбранная `final_traj` совпадает с `vocab[candidate_absolute_ids[selected_local_idx]]`; coarse и final indices различаются только по действительному выбору, не из-за ошибки индексации.
- Полное соответствие токенов; отсутствующие кэши и ошибки не скрываются пересечением множеств. Отсутствующий baseline не заменяется нулём.
- Baseline через новый путь совпадает со стандартным evaluator по каждой сцене и каждому компоненту; глобальный балл сравнивается на том же наборе строк и adjacency.
- Для subset baseline сначала пересчитывается на том же subset/контексте; полный 83,0677 не является эталоном среднего любой подвыборки.
- Для float64 метрик начальный допуск `atol=1e-8`, `rtol=1e-7`; для сохранённых float32 poses ожидается точное равенство на одном устройстве. Отличия категориальных метрик недопустимы. При другом GPU/батче расхождения исследовать отдельно, а не автоматически расширять tolerance.
- Повтор, перестановка и chunking не меняют оценки; human filter не оставляет состояние от предыдущего кандидата.
- No-op выбор всех исходных траекторий восстанавливает полный baseline с two-frame comfort; отсутствие соседей имеет исходную NaN-семантику. Пустой adjacency mapping обрабатывается явно.
- Проверить границу 0,55 s: mapping в текущем коде допускает <=0,55, а агрегатор требует <0,55. Если такие пары есть, остановиться и зафиксировать решение до новых сравнений.
- Локальный оракул не ниже локального baseline; DP не ниже baseline и любого проверенного допустимого пути в пределах численной точности.
- Повреждённый/прерванный shard не считается завершённым; resume не смешивает версии.
- Ошибка кандидата не должна незаметно повышать оракул за счёт изменения выборки. До основной таблицы устранить ошибки; оставшиеся incomplete scenes сообщать отдельно и не выдавать частичный максимум за точную верхнюю границу полного набора.

## 9. Отчёт и решение о продолжении

Главные таблицы: baseline; локальный oracle без TF (вместе с соответствующим baseline); одиночные замены; полный EPDMS DP; constrained EPDMS DP. Для каждого указывать число логов, сцен, кандидатов, ошибок и точное определение цели. Summary-строку `average_all_frames` исключать из выборки сцен.

Основные числа:

- абсолютный балл и прирост в процентных пунктах (100 * разность значений на шкале 0..1);
- NC/DAC/DDC/TLC/TTC, progress, lane keeping, history comfort, two-frame comfort;
- доля изменённых выборов, доля локально улучшенных сцен, величина и распределение выигрыша;
- доля сцен, где у исходно благополучного решения появляется опасная альтернатива среди тех же кандидатов; это лишь наличие альтернатив, а не отрицательный перенос памяти;
- ранг исходного выбора по фактической метрике, regret, дубли/разнообразие траекторий;
- разбивка по логам, типам манёвра и исходным ошибкам, если эти признаки доступны;
- paired cluster bootstrap по логам с пересчётом парной разности; не bootstrap соседние кадры как независимые;
- время GPU-экспорта, CPU-оценки, парного комфорта и DP, память worker, фактический объём диска.

Графики: распределение локального regret; резерв при ограничении доступных кандидатов top-8/32/64/256 по исходному финальному score с обязательным включением baseline; unrestricted/constrained выигрыш; несколько сцен с исходной и альтернативной траекторией. Любое top-K подмножество фиксируется по model score, а не по oracle labels.

Критерий достаточного резерва согласовать до расширенного development-прогона. Рабочий ориентир, который ещё не является утверждённым порогом: constrained прирост порядка 1 п.п. EPDMS с положительной нижней границей 95% cluster CI и эффектом в нескольких логах. Проверить чувствительность к ориентирам 0,5/1/2 п.п.; не выбирать удобный порог по navtest. При меньшем среднем резерве работа может быть оправдана важным выигрышем в заранее определённой сложной группе, но тогда нужно сузить основной тезис.

Даже большой oracle gap не доказывает перспективность памяти. Следующая веха после этого этапа: простой механизм переоценки с извлечённым эпизодом, контрольная модель без памяти и измерение реального отрицательного переноса при одинаковых кандидатах.

## 10. Ресурсы и срок первого этапа

На 12146 сценах и 256 кандидатах требуется 3 109 376 парных оценок. Наивное умножение времени обычного evaluator на 256 не учитывает повторную загрузку и кэширование; оценку длительности делать по измеренному pilot throughput, отдельно для scoring и парного комфорта.

Пример несжатого хранения при проверенных формах:

- общий vocab float32 [8192,40,3]: около 3,9 MB;
- IDs, девять финальных logits и selection score на 12146 сценах: около 0,14 GB, без метаданных;
- явные poses всех 256 кандидатов: около 1,49 GB; при общей неизменной геометрии достаточно vocab + IDs;
- simulated states float64 [256,41,11]: около 11,2 GB для 12146 сцен;
- bool-матрица comfort [256,256]: около 64 KiB на ребро; порядка 0,8 GB, если рёбер около 12 тысяч. Вычислять и сохранять по блокам/логам, без разворачивания всех парных состояний в RAM.

Это расчёт массивов, без overhead файлов, DataFrames и временных копий. Не хранить все логи одновременно в RAM. Полные 8192 кандидата оценивать только как отдельный необязательный диагностический опыт на малом наборе после основной проверки 256.

Оценка усилий при доступных данных и рабочем окружении:

1. 1-2 рабочих дня: экспорт, manifest и проверки выбора.
2. 1-2 дня: последовательный scorer и parity на малом наборе.
3. 1-2 дня: two-frame оракулы, DP, проверки полным перебором и повторной агрегацией.
4. 1-2 дня: development pilot, отчёт, оценка стоимости масштабирования.

Итого ориентировочно 4-8 рабочих дней разработки и проверки плюс время вычислений. Если отсутствует train metric cache, его подготовка является отдельной зависимостью. GPU, датасет, cache и checkpoint в локальном Windows-окружении этим анализом не проверялись; фактические запуски планируются в ранее использованном серверном Docker-окружении.

## 11. Отдельные замечания к текущим launch scripts

В локальном `scripts/drivesuprim/evaluation/eval_file_epdms.sh` обнаружено `file=$2z`: это добавляет `z` к имени checkpoint. В обычном `eval_file.sh` включены overrides scorer, отличающиеся от полного EPDMS. Поэтому оба файла нельзя считать достоверным описанием успешного v2-запуска без сверки с сохранённой resolved config.

Эти скрипты в рамках подготовки плана не изменялись. Перед реализацией восстановить точную команду и конфигурацию успешного запуска, затем создать отдельный launcher эксперимента с явной валидацией путей и без перезаписи результатов воспроизведения.
