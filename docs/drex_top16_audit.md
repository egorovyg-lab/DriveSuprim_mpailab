# Все top16 в шести диагностических сценах

Проверяем, есть ли в исходном top16 варианты с большим геометрическим запасом,
которые не попали в ранее рассмотренную пару. Используются все **96 кандидатов**
без исключения неудобных случаев. Сцены остаются прежними, выбранными по
известным исходам; это диагностический разбор, а не независимая валидация.

## Запуск на msu270

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
export DREX_TOP16_SOURCE=rollout_audit_pair6_v2
export DREX_TOP16_NAME=rollout_audit_top16_pair6_v1

bash scripts/drex/run_top16_audit.sh connect &&
bash scripts/drex/run_top16_audit.sh start
```

После `start` можно отключиться. Мост работает через `nohup`, вычисления —
на CPU Astra в прежнем контейнере. GPU и Slurm не нужны. Новые изображения,
веса и датасет не загружаются. На Astra checkout обновлять не требуется.

```bash
bash scripts/drex/run_top16_audit.sh status
```

Во время работы в журнале видны `TOP16 N/96`. В конце выводится компактная
таблица для шести сцен и путь к полным артефактам. Ожидаемые проверки:
`metric_parity_passed=96`, `known_pair_state_parity_passed=12`,
`geometry_interpretation_ready=true`.

## Выбор и воспроизведение

Проверяется источник: исходный успешный аудит, SHA файлов и пакета на Astra
и msu270, original cache hashes и scorer source hashes. Top16 определяются
только сохранёнными оценками DS, стабильной сортировкой по убыванию. Rank 1 —
исходный выбор DS. Весь список сохраняется в `selection.json` **до чтения
массивов исходов top16**. Сцены при этом уже outcome-selected, что явно указано.

Каждый кандидат заново проходит исходный одиночный `pdm_score` вместе с
эталонным PDM-предложением. Одновременное scoring всех 16 не используется:
оно могло бы изменить нормализацию прогресса. Для каждого вызова observation
создаётся из неизменённого cache, чтобы не переносить состояние между вызовами.
Raw human penalty filter выключен, как при сборе исходных raw labels.

Все девять метрик сравниваются с уже сохранённой строкой top16:
`atol=1e-8`, `rtol=1e-7`. У прежних 12 кандидатов дополнительно проверяется
совпадение исполненных states с аудитом пар. Несовпадения сохраняются и
помечают общий отчёт `parity_failed`; неудачные кандидаты не исключаются.

На исполненном пути считаются те же full-footprint дорожные запасы, площадь
вне области, LK и физические контакты, что в предыдущем clearance-аудите.
Геометрия углов/LK сверяется с текущим scorer. Буферы заранее фиксированы:
0 / 0,1 / 0,25 / 0,5 м. В eligibility входят cornerDAC, покрытие полного
габарита, LK, отсутствие контактов и запас до карты/объектов не меньше буфера.
Это не все метрики PDM и не гарантия безопасности между отсчётами 0,1 с.

## Прогресс и итоговая таблица

Для каждого буфера показываются:

- ранги всех прошедших геометрические условия кандидатов;
- ранги из того же набора с прогрессом не меньше DS;
- лучший raw PDM внутри набора, его ранг, выигрыш и прогресс в метрах;
- максимальный прогресс в метрах среди прошедших кандидатов.

`progress_m` — неотрицательное перемещение центра машины вдоль centerline,
вычисленное оригинальным scorer до нормализации. Для сравнения `>= DS`
используется только численная погрешность 1e-6 м. Набор без этого ограничения
также показывается, чтобы не скрывать полезные варианты с меньшим прогрессом.
Сохраняется и исходная нормализованная метрика `ego_progress`.

Выбор лучшего PDM по известным исходам — **oracle-диагностика**, не решение
Drex и не доступная онлайн-политика. Карта и записанный будущий traffic
используются для аудита. Эти данные модели не передаются.

## Артефакты и возобновление

`report.json` содержит все 96 строк и сводку. `candidates.csv` — плоская
таблица рангов, метрик, прогресса и запасов. В `candidates/caseNN-rankNN/`
сохраняются `summary.json`, покадровая геометрия, `rollout.npz` с исходным и
исполненным путями, states и габаритами, а также commit их SHA. Это позволит
использовать рассчитанные пути в следующих проверках без повторной симуляции;
будущий адаптер модели должен читать только allowlisted ego poses.

Повторный `start` после завершения предыдущего процесса проверяет готовые
кандидаты и не пересчитывает их. Новые код/входы требуют нового имени вывода.
Новых scoring-вызовов при полном первом запуске — 96; при возобновлении
счётчик `scorer_calls_this_invocation` показывает фактическое число.

Предыдущие аудиты и исходные данные сохраняются. Полный серверный запуск
нужно выполнить на Astra; локальные тесты не подменяют проверку nuPlan SDK.
