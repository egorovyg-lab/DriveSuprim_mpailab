# Несколько GPU и разбор первого реального пилота

## Что делает текущий запуск

`run_runtime.sh submit-real` запрашивает одну GPU, 4 CPU и 96G RAM узла.
Модель целиком загружается в BF16 на локальный `cuda:0`; CPU RAM не равна
памяти GPU. Изменение `--gres=gpu:1` на `gpu:2` само по себе не распределяет
Python-процесс или модель. Скрипт исходного пилота остаётся без изменений.

## Первое действие после отчёта: CPU-аудит

В real_train64_v1 основной метод дал +1.16 п.п., CI включает ноль; blank
контроль оказался выше. Повторять те же запросы на нескольких GPU для поиска
удачного ответа не требуется. Команда ниже анализирует уже зафиксированные
решения и метки, не запускает Drex и не меняет выбор кандидатов:

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
DREX_REAL_NAME=real_train64_v1 bash scripts/drex/run_real_parallel.sh audit
```

CPU-only Slurm job step на сохранённом setup-узле. Результат:
`$DREX_RUNTIME_ROOT/runs/real_train64_v1/audit_v1.json`.
Проверяются исходный пакет и полная фиксация решений. Отчёт содержит:

- парный контраст `drex_single - blank_single` по одним сценам и CI по сессиям;
- сравнение `drex_mean3 - blank_single`, отдельно отмеченное как сравнение
  разных правил агрегации, а не чистый эффект изображений;
- чувствительность среднего к исключению каждой одной сессии без изменения
  основного результата и без удаления сложных примеров;
- геометрическое расстояние и изменение PDM при перестановках кандидатов;
- крупнейшие потери/улучшения основного метода и изменения компонентов.

Это post-hoc диагностика, не новая независимая проверка или подбор правил.

## Для будущих больших серий: полная копия Drex на каждой GPU

Используется Slurm array. Каждый worker получает одну GPU и независимую полную
BF16-модель. 64 сцены распределяются без пересечений: две реплики — по 32,
четыре — по 16. Все четыре запроса одной сцены идут одному worker.
Состав сцен, кандидаты, текст/изображения и усреднение вероятностей остаются
такими же, как у последовательного пилота. Дополнительные GPU не улучшают
качество сами по себе и не складывают VRAM для одной модели.

Условия этого режима: отдельная A100 80 GB либо совместимая GPU >=70 GiB с
BF16 для каждой реплики. Около 50 GiB на модель по предыдущим замерам;
точный пик измеряется отдельно. Две одновременно работающие реплики запросят
суммарно 192G RAM узла и 8 CPU. Данные и веса читаются с общего диска,
загрузки могут конкурировать за I/O. Для 64 сцен выигрыш может быть небольшим;
время ожидания в очереди тоже может увеличиться. Начинать разумно с двух GPU.

Проверки на CPU в compute-node venv:

```bash
bash scripts/drex/run_real_parallel.sh check 2
```

Запуск отдельной серии на двух GPU — когда действительно нужна новая серия:

```bash
bash scripts/drex/run_real_parallel.sh submit 2
```

На четырёх:

```bash
bash scripts/drex/run_real_parallel.sh submit 4
```

Поддерживается 1..8 реплик. Эти команды НЕ запускают обе серии сразу: выбрать
одну. Старое имя `real_train64_v1` для parallel-запуска запрещено. По умолчанию
выходы: `real_train64_gpu2_v1` и `real_train64_gpu4_v1`. Не отправляйте новый
submit для того же выхода, пока старые workers ещё работают.

`submit` создаёт три задания:

1. CPU plan: проверяет пакет, фиксирует общий cohort и распределение.
2. Array workers `0..N-1%N`, зависимость `afterok` от plan, каждый с
   `--gres=gpu:1`, 96G RAM, 4 CPU и лимитом четыре часа.
3. CPU merge/report, зависимость `afterok` от ВСЕГО array.

Worker не читает outcome arrays. После завершения ВСЕХ workers координатор
проверяет их commitments, отсутствие пропусков/дублей и одинаковый runtime/GPU
profile, заново проверяет пиксели/запросы, формирует единую фиксацию всех 256
ответов. Только после этого читает raw PDM. При сбое или частичном результате
worker возвращает ненулевой exit code, поэтому оценка не запускается.

Все задачи закреплены на `setup_node.txt`, где проверена compute-node Python.
Они стоят в обычной очереди без эксклюзивного захвата узла, перезапуска чужих
задач или ручного изменения `CUDA_VISIBLE_DEVICES`. Slurm назначает каждой
реплике её GPU; локально она снова называется `cuda:0`.
См. [GRES scheduling](https://slurm.schedmd.com/gres.html) и
[job arrays / dependencies](https://slurm.schedmd.com/job_array.html).

После вывода трёх job IDs можно закрыть SSH. Номера текущих/чужих заданий
скрипт не отменяет. Логи: `parallel-plan-JOB.log`,
`parallel-worker-ARRAY_TASK.log`, `parallel-merge-JOB.log` в runtime/logs.

Повторный submit после разобранного прерывания использует готовые commitments
workers и сохранённые запросы; не перезапускает завершённую модель. Технические
ошибки в результатах, как и в исходном пилоте, не повторяются молча. При новом
протоколе требуется новое имя. Если worker завершился неудачно, старый merge
может остаться в очереди с невыполнимой зависимостью; после разбора его можно
отменить по напечатанному конкретному ID своего задания. Автоматической отмены
скрипт не делает.

Ограничение проверки: локальные тесты используют fake inference. Они проверяют
разбиение, совпадение решений/метрик с последовательным расчётом, возобновление,
зависимости и запрет раннего чтения меток. Фактическое ускорение и численное
совпадение на нескольких A100 ещё не измерены.
