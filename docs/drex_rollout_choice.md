# Согласование траекторий Drex с движением после контроллера

Инерция исходного NAVSIM сохраняется. Проверяем нашу передачу кандидатов Drex:
насколько выбор меняется, если вместо желаемого пути показать движение,
которое получилось после исходного контроллера и модели автомобиля.

Используются те же шесть заранее выбранных пар. Для каждой пары:

- исходный путь / движение после симулятора;
- центральная линия / линия с габаритами;
- текущая фотография / белый фон;
- исходный / обратный порядок вариантов.

Всего 96 запросов. Заранее указанный основной вариант —
`simulated/centerline/road`; в отчёте сохраняются все восемь сочетаний и
попарные изменения выбора. Эти известные случаи служат диагностикой
представления, а не независимой оценкой качества вождения.

## Запуск на msu270

```bash
cd ~/drivesuprim
git pull --ff-only

export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
export DREX_ROLLOUT_PAIR_SOURCE=pair_diag_gpu4_v1
export DREX_ROLLOUT_AUDIT_NAME=rollout_audit_pair6_v2
export DREX_ROLLOUT_CHOICE_NAME=rollout_choice_gpu4_v1

bash scripts/drex/run_rollout_choice.sh check 4 &&
bash scripts/drex/run_rollout_choice.sh submit 4
```

Поддерживаются `1`, `2`, `4`, `8` GPU. Одна полная BF16-модель на каждого
worker; запросы разделены без пересечений. Для другого числа worker выбери
соответствующее новое имя результата до первого планирования. Число worker
входит в frozen plan и не меняется при возобновлении.

`submit` создаёт CPU-план, GPU-массив с `afterok` и CPU-сборку после всех
worker. После сообщения о постановке задач можно выйти с сервера.
Ожидание ресурсов общей вершины обрабатывает Slurm. На worker запрашиваются
одна GPU, 96G CPU RAM и один час. План и сборка используют CPU, 8G и 20 минут.

Только построить план и посмотреть PNG:

```bash
bash scripts/drex/run_rollout_choice.sh submit-plan 4
```

После успешного плана `submit 4` проверит тот же план и продолжит работу.
Повторная команда `submit` допускается после завершения предыдущей задачи;
готовые ответы проверяются и не запрашиваются у модели заново.

```bash
bash scripts/drex/run_rollout_choice.sh status 4
```

Каталог результатов:

```text
/scratch/pr0201/drex_runtime/runs/rollout_choice_gpu4_v1/
```

Журналы Slurm: `logs/rollout-choice-plan-JOB.log`,
`logs/rollout-choice-worker-ARRAY_INDEX.log`, `logs/rollout-choice-merge-JOB.log`
внутри `DREX_RUNTIME_ROOT`.

## Проверки и артефакты

Нужны завершённая диагностика пар и CPU-аудит с совпадением метрик 12/12.
План проверяет SHA возвращённого архива, соответствие пакета, исходных пар,
ID кандидатов, commit файлов, период 0,1 с, начальную позу и 41 отсчёт.
Исходные poses из аудита должны совпадать с кандидатом из frozen vocabulary.
При несовпадении вычисления останавливаются, допуски scorer не меняются.

В `paths/caseNN.npz` записываются только два массива `nominal` и `simulated`,
каждый `[2, 40, 3]`: положения задней оси и heading двух кандидатов.
Это вычисленное движение самого автомобиля по кандидатам, а не будущие
наблюдения участников движения. Карта, centerline scorer, события нарушения,
метрики и диагностические PNG не используются для рисования входов Drex.
Инференс-worker читает только очищенные пути и обычные исходные входы.
Ожидаемые исходы читаются при планировании известных пар и при оценке уже
зафиксированных решений, но не при инференсе.

Подписи, текст запроса, имена кандидатов и перестановки одинаковы между
исходной и исполненной геометрией. Название геометрии не передаётся модели.
Во вставке используется единый масштаб для четырёх путей пары, включая
габариты; в дорожной проекции сохраняется исходная калибровка v2.
Обе геометрии заново проходят инференс с общим текстом: старые ответы из
другого представления не подставляются в новое сравнение.

- `tracking_error_report.json` — для каждого кандидата продольная,
  поперечная ошибка, ошибка heading и разность скоростей по соседним точкам.
  Отрицательная продольная ошибка означает отставание. Разность скоростей
  по точкам не отождествляется с профилем скорости внутри LQR.
- `preview-caseNN-GEOMETRY-REPRESENTATION-memberN.png` — новые анонимные
  картинки без диагностической карты или выделенных нарушений.
- `plan.json`, `requests.json`, `decision_commit.json` — SHA входов,
  распределение запросов и обязательство решений до оценки.
- `per_case.json`, `report.json` — выбор по двум порядкам, перестановочные
  изменения, выигрыши/потери по исходным raw PDM и попарные сравнения.

Аудит, предыдущие планы и исходные файлы scorer остаются сохранёнными.
Новое подключение к Astra, загрузка датасета, обучение, пересчёт метрик и
открытие holdout для этого опыта не требуются. Инференс на A100 остаётся
серверной проверкой: локальные тесты используют искусственные данные и
ответы и не измеряют качество Drex.
