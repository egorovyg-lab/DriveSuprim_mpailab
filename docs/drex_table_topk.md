# Drex: таблица против таблицы с фотографиями, top16/32/64

Новый протокол не меняет старые real/overlay/pair запуски. По умолчанию
используются ВСЕ 651 сцена / 32 сессии готового portable train-пакета, а не 64.
Это исследовательские train-сцены с ранее рассмотренными исходами; их нельзя
представлять как независимый тест. Fresh holdout не открывается.

## Что реализовано

- Вложенные top16/top32/top64 по сохранённому итоговому DS score среди 256;
  исходный выбор DS присутствует в каждом пуле. DS повторно не запускается.
- Таблица одинаковых численных признаков: восемь прогнозов голов DS,
  imitation log-probability среди 256, отступ DS score от максимума,
  положения через 1/2/4 секунды, конечный heading, длина пути, максимальные
  дискретные скорость/ускорение/кривизна. Таблица и правила используют одинаковое
  округление до четырёх знаков. Экстремальные значения не скрываются клиппингом.
- Текущие скорость и ускорение ego. Команда направления ещё не расшифрована;
  неизвестная семантика one-hot не подменяется догадкой о маршруте.
- Два условия: `table` и `table_camera`. State, question, таблица и варианты
  выбора совпадают; второе добавляет одну доску камер: front-left/front/front-right
  из двух последних доступных кадров. В `table` нет ни одной картинки, включая
  схемы траекторий. Траектории представлены численно.
- Три порядка вариантов: фиксированный случайный, обратный, циклический сдвиг.
  Анонимные ID стабильны между порядками и размерами пула. Основное решение
  каждого условия — среднее трёх распределений после выравнивания ID.
  Вероятности из разных пулов не усредняются. Primary: `table_camera/k64/mean3`.
- Контроли: исходный DS, `head_rule`, `head_veto_rule`. Первый использует
  произведение первых четырёх прогнозов × среднее остальных четырёх.
  Второй дополнительно запрещает ухудшение любого из пяти safety-прогнозов
  относительно DS. Это заранее заданные эвристики, а не PDM или гарантия безопасности.
- По одной полной BF16-копии Drex на выделенную GPU; 1/2/4/8 реплик,
  распределение по сценам, batch=1, 96G RAM на worker. Полный запуск: 18 запросов
  на сцену, **11 718 запросов** для 651 сцены. Короткий pilot: до 18 новых запросов
  на worker, то есть одна сцена на каждую реплику.
- Контекст ограничен 16 384 токенами. Upstream поддерживает до 255 вариантов;
  64 входят в этот предел. Переполнение контекста/неверное число изображений
  останавливает задачу, без обрезки таблицы или замены сцены.

Геометрия вычисляется по НОМИНАЛЬНЫМ словарным позам через 0.1 s. Это не rollout
контроллера. Ускорение включает переход от текущей измеренной скорости к первому
интервалу кандидата. Кривизна: изменение heading / пройденное расстояние, только
для интервалов >=0.05 m. Она не доказывает физическую исполнимость траектории.
HD-карта, её clearance, будущие акторы, measured PDM, результаты аудитов и radar
в запрос не входят. Вариант с картой/ego-rollout — отдельный будущий протокол.

## msu270: обновление, проверки и короткий GPU-пилот

Для единого ночного запуска с автоматическими мини-проверками используйте раздел
ниже. Этот раздел — если хочется вручную посмотреть pilot перед продолжением.

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
export DREX_TABLE_COHORT=all
export DREX_TABLE_NAME=table_topk_all_gpu8_v1

bash scripts/drex/run_table.sh check 8
bash scripts/drex/run_table.sh submit-pilot 8
```

Можно заменить 8 на 1, 2 или 4 и задать другое имя с соответствующим числом GPU.
Имя, cohort и число реплик замораживаются. Менять их в существующем запуске нельзя.
Новый output нужен также после изменения кода/признаков/формулировок.
Для отдельного исследования на прежних 64 сценах: `DREX_TABLE_COHORT=balanced64`
и другое имя. Эти сцены выбираются прежним input-only правилом real pilot.

`submit-pilot` ставит CPU plan и зависимый GPU array. Все задания sbatch продолжают
работу после отключения SSH. Данные камер нового raw-переноса ему не нужны:
готовый пакет 651 сцены уже содержит нужные снимки и прогнозы DS.

```bash
bash scripts/drex/run_table.sh status 8
squeue -u "$USER"
# Использовать ID array, который напечатал submit-pilot:
tail -n 60 /scratch/pr0201/drex_runtime/logs/table-worker-pilot-ARRAYID_0.log
```

В успешном pilot worker пишет `status: partial`, 18 завершённых запросов;
для некоторых совсем маленьких fixture-cohort возможен `choices_frozen`.
Это ожидаемое ограничение pilot, а не полная оценка.

После проверки всех pilot workers можно продолжить ТОТ ЖЕ запуск:

```bash
bash scripts/drex/run_table.sh submit 8
```

Готовые запросы повторно не вычисляются. После сбоя GPU/контекста записанная
ошибка сохраняется, автоматических повторов не делаем. При ограничении времени
частичные результаты сохраняются; повторить `submit` с тем же окружением.
CPU merge стартует только после успешного полного завершения всего array.

## Единый ночной запуск: мини-проверки, затем все 651 сцена

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
export DREX_TABLE_COHORT=all
export DREX_TABLE_NAME=table_topk_night_gpu8_v1

bash scripts/drex/run_table.sh submit-inventory 8
bash scripts/drex/run_table.sh submit-night 8

bash scripts/drex/run_transfer.sh connect
nohup python3 -u scripts/drex/table_labels.py \
  --root "$DREX_RUNTIME_ROOT" --table-run "$DREX_TABLE_NAME" \
  --wait-seconds 43200 --submit-report \
  > "$DREX_RUNTIME_ROOT/logs/${DREX_TABLE_NAME}-labels.log" 2>&1 < /dev/null &
```

`submit-night` ставит цепочку afterok: CPU tests → CPU plan → GPU mini-pilot
(18 новых запросов на worker) → GPU full → CPU merge. При отказе tests/plan/pilot
зависимые задачи отменяются (`kill-on-invalid-dep`); большой прогон не начинает
повторять неудачные запросы. Большой прогон продолжает тот же output после pilot.
По умолчанию GPU worker ограничен 8 h (можно заранее задать `DREX_TABLE_TIME`).
Задания могут ждать ресурсы в общей очереди; время ожидания не равно времени расчёта.

Параллельный login-процесс ждёт появления готового label request до 12 h, затем
запускает CPU scoring на Astra. После получения меток ждёт полный decision commit
и первичный отчёт. Если отчёт ещё ждёт top64 labels, ставит повторную CPU-задачу
отчёта. Если полный отчёт уже создан, повторную задачу не ставит.
При истечении ожидания/разрыве SSH результаты сохраняются: после восстановления
`connect` повторить команду labels. На msu270 login выполняются только ожидание,
передача и постановка задач; моделей и NAVSIM scorer на login нет.
После постановки sbatch и запуска nohup можно отключаться от сервера.

Для 1/2/4 GPU поменять число в обеих командах и использовать отдельное имя.
Полный объём для 651 сцены: 11 718 запросов, а не повторение синтетики. Данные
не дублируются для искусственного удлинения запуска; время окончания определяется
скоростью модели. CPU scoring дополнительно оценивает 41 664 кандидата на Astra.

## Дополнительные метки top64: CPU на Astra, без обновления её checkout

Старый пакет содержит измеренные raw PDM/компоненты только для top16. Без новых
меток отчёт явно пишет `awaiting_top64_labels` и оценивает только полный top16;
неполные top32/top64 не усредняются по удобным сценам.

После окончания CPU plan (появился `label_request.json`) можно параллельно
GPU-прогону запустить на msu270:

```bash
bash scripts/drex/run_transfer.sh connect
nohup python3 -u scripts/drex/table_labels.py \
  --root "$DREX_RUNTIME_ROOT" --table-run "$DREX_TABLE_NAME" \
  > "$DREX_RUNTIME_ROOT/logs/${DREX_TABLE_NAME}-labels.log" 2>&1 < /dev/null &
```

Login-bridge использует только stdlib. Он передаёт замороженный список кандидатов
и необходимые Python-инструменты в отдельный каталог контейнера Astra. Checkout
на Astra менять не нужно. Прежний перенос portable-пакета на Astra должен
сохраняться: `/workspace/exp_v2/drex_transfer/navsim_train_v1`.

Скоринг использует исходные связанные по SHA кеши и исходную конфигурацию,
восстановленную из provenance пакета. Никаких поисков подходящего кеша по всем
каталогам. Для каждого кандидата создаётся свежий объект кеша. Все 64 кандидата
оцениваются отдельно, 16 известных проверяются на raw metric parity. Есть resume
по полностью завершённым сценам; меняющиеся инструменты/кеши останавливают работу.
Это до 41 664 scorer calls для 651 сцены; GPU на Astra не требуются.

После успешного возврата меток автоматически создаётся `label_source.json`:

```bash
bash scripts/drex/run_table.sh report 8
```

Финальный отчёт: `$DREX_RUNTIME_ROOT/runs/$DREX_TABLE_NAME/report.json`,
таблица результатов: `per_scene.csv`. Публикуются micro/macro приросты,
cluster bootstrap по сессиям, ухудшения компонент, order flips, токены/задержки,
парная разница camera-minus-table и oracle каждого пула.
Все решения ВСЕХ условий и сцен фиксируются до первой загрузки outcome-массивов
в процесс отчёта. CPU scoring — отдельный процесс и не подаёт результаты модели.

## После окончания raw-переноса: сколько дополнительных сцен доступно

```bash
bash scripts/drex/run_table.sh submit-inventory 8
```

Это отдельная CPU-задача, GPU не запрашивает. Проверяет маркер завершения переноса,
читает только собственные доверенные OpenScene `.pkl`, проверяет наличие и
декодируемость камер. Подсчитывает окна с историей 4 и будущими 10 кадрами, с route,
различает 3 камеры × 2 кадра и 8 камер × 4 кадра. Сохраняет CSV, SHA логов,
дополнительные окна с разносом 10 s и распределение по сессиям.

```bash
cat "$DREX_RUNTIME_ROOT/data/astra_trainval_inventory_v1/report.json"
```

`existing_training`, `protected`, `unassigned` разделены. Последнее не означает
fresh или разрешённое обучение: нужно сверить прежние development-исследования.
Это аудит наличия, а не автоматическое расширение training split. Новые DS
экспорты, кеши и метки не создаются, новые архивы не скачиваются. Соседние окна
не считаются независимыми сценами. Новые сцены войдут в новый зафиксированный
пакет после проверки и отдельной подготовки.
