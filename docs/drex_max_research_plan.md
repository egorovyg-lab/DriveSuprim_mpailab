# Drex Max для выбора траектории DriveSuprim

План от 10 ноября 2026 года. Рабочая ветка: `codex/drex-max`.
Это план экспериментов, а не результат запуска Drex. Загрузка весов, платные
запросы, изменение окружения и обучение в рамках подготовки плана не выполнялись.

## 1. Вопрос и границы первого опыта

Проверяем, добавляет ли готовый мультимодальный Drex информацию, которая помогает
выбрать более качественную траекторию из неизменного top16 DriveSuprim.
Первый опыт — offline reranking без обучения Drex и без изменения DriveSuprim.
Выход — один из 16 существующих кандидатов. Baseline уже входит в эти 16:
отдельный дублирующий вариант «оставить baseline» не добавляем.

Основания: на 651 training-сцене из 32 поездок top16 имеет около 3.79 п.п.
среднего по сценам оракульного резерва local PDM. Наши обучаемые критики пока
не дали устойчивого выигрыша. Строгий teacher veto по пяти компонентам оставил
полезные альтернативы лишь в 19 сценах против 279 без ограничений. Поэтому
не переносим этот veto автоматически в новую основную политику.

Гипотеза о дополнительной пользе изображений проверяется отдельно от удобства
decision API, размера модели и замены алгоритма выбора. Уже имеющееся внимание
в малом селекторе само по себе эту гипотезу не проверяло.

## 2. Проверка ресурсов до загрузки модели

Снять инвентаризацию GPU/VRAM, драйвера, CUDA, CPU/RAM, свободного диска и mounts.
Проверить фактическую доступность GPU из предполагаемого окружения Drex.
Экспорт входных пакетов остаётся в старом Python 3.9; инференс Drex запускается
в отдельном окружении/контейнере, который получает только пакеты и веса.

Официальный Python-путь поддерживает изображения; документация требует
Python >=3.12. Проверенные авторами варианты: H100 80 GB / BF16 и L40S 48 GB /
8-bit. Загруженные веса занимают около 49 / 26 GB соответственно, дополнительно
нужна память для изображений и контекста. Это примеры, не обещание вместимости
любого нашего запроса. Начинать с batch_size=1 и измерять пик памяти.

Пользователь подтвердил: доступны только две GTX 1080 по 8 GB. Они не вмещают
эти штатные варианты даже суммарно. Этап подготовки и проверки пакетов выполняем
на имеющемся оборудовании, без загрузки весов. Сначала измеряем доступную RAM
и лимит памяти контейнера: свободная память хоста сама по себе не гарантирует
её доступность процессу. Также проверяем диск, драйвер и поддержку этих GPU
нужным стеком PyTorch/квантования/DeltaNet kernels в отдельном окружении.

Полученная инвентаризация: 31 GiB RAM, 27 GiB available, 2 GiB swap
(около 1.5 GiB свободно), 489 GiB свободного диска; cgroup `memory.max=max`.
Отдельной cgroup-квоты нет, но физическая RAM ограничена. Диска достаточно для
исходных весов; размещение файлов на диске не означает возможность исполнения.
Официальный CPU loader использует float32: только 27B весов потребуют порядка
100 GiB, поэтому этот путь в имеющуюся RAM не помещается. Swap не планируется
как способ разместить модель. Runtime/offload на диске — другой, непроверенный путь.

Проверка зависимостей уточнила ограничения. Bitsandbytes допускает NF4/FP4
на Pascal, но LLM.int8 требует Turing или новее. Triton официально поддерживает
NVIDIA CC >=8.0, поэтому на GTX 1080 нельзя рассчитывать на его быстрые ядра.
В исходниках Transformers v5.17.0 для Qwen3_5 есть torch fallback для DeltaNet;
это оставляет возможность исследовать медленный путь, а не доказывает полный
запуск Drex. Нужен ограниченный compatibility spike: FP32/FP16 вместо штатного
BF16, отключение недоступных ускорителей, NF4, проверка tensor/device mapping
и малыми тензорами подтверждённые fallback-операции. Всё это отдельно от старого
окружения и без загрузки 27B до прохождения проверок. Оценка 27B*0.5 byte
не включает неквантованные embedding/vision/head, scales, activations и
временные буферы, поэтому обещать вместимость по ней нельзя.

После инвентаризации допускается отдельный технический план экспериментального
4-bit multimodal / CPU-offload. Его работоспособность и скорость пока неизвестны;
не считать его штатно поддержанным режимом. Сначала проверить loader и kernels
на малых синтетических тензорах, затем только при достаточных ресурсах переходить
к весам и одному запросу. Сохранение vision encoder, non-causal attention и
readout обязательно: текстовый GGUF/MLX не заменяет этот опыт. Две GPU не
объединяются автоматически; device mapping тоже требует проверки.

Если запуск Max на имеющемся оборудовании непрактичен, подготовленные пакеты
сохраняются. Более компактная мультимодальная модель будет отдельным Drex-inspired
опытом с другим model ID, а не незаметной заменой Drex Max. Аренда GPU/внешний
платный API не предполагаются этой редакцией плана.

Зафиксировать commit upstream, HF revision, hashes файлов, зависимости,
точность, attention mode, image processor, размер контекста. Использовать
специальный Drex loader с non-causal full attention; обычный causal chat loader
не эквивалентен. Не обновлять библиотеки/драйверы основного DriveSuprim-контейнера.

## 3. Используемые данные

| Набор | Назначение |
|---|---|
| 40 уже просмотренных development-сцен / 7 поездок | Первая диагностическая серия, не независимый тест |
| 651 training-сцена / 32 поездки | Расширенная диагностика, при необходимости последующая настройка |
| 4 зарезервированные новые поездки, по manifest ожидается 64 сцены | Однократная оценка только после фиксации метода |

Проверить фактические counts, наличие изображений, кандидатов, timestamps,
метрик и пересечения поездок. Не считать исходные исторические C/T свежими
автоматически. Архивная выборка не репрезентативна, а независимость от pretraining
исходного DriveSuprim не установлена.

Прежние признаки, vocab, checkpoint и labels не пересоздавать ради Drex.
Проверять hashes, точный порядок candidate IDs, baseline и top16. Labels для
оценки берутся из прежних stored raw PDM / компонентов, не реконструируются
из filtered-полей. Отсутствующие labels исторического набора выявляются до
опыта; новые scorer calls не запускаются скрыто.

## 4. Вход модели и привязка траекторий

В v1 использовать те же наблюдения, которые использовал замороженный teacher.
В текущем коде r34 — panorama из cam_l0/cam_f0/cam_r0 и seq_len=2. Подтвердить
это по сохранённой конфигурации каждого источника. Отдельное расширение до
большего числа камер или более длинной истории будет другим опытом.

В пакет входят:

- Два past/current изображения с подписанными относительными временами,
  теми же camera crop/FOV и проверенной геометрией resize.
- Разрешённые ego velocity/acceleration/history и driving command.
- Точный top16 из vocabulary; полный массив траекторий сохраняется в sidecar.
- Краткая таблица каждого кандидата: положения в фиксированные моменты,
  heading, перемещение и вычисленные кинематические характеристики с единицами.
  Производные — только свойства предложения, не измеренный будущий прогресс.
- Прогнозы teacher явно помечены как прогнозы. Baseline отмечен одинаково
  для всех сравниваемых методов. Истинные DAC/TTC/PDM в пакет не входят.

Нейтральные локальные коды вариантов связаны с physical vocab ID только через
сохранённую mapping. Token, session, имя лога и известные ошибочные scene IDs
модели не показываются. Порядок вариантов задаётся воспроизводимой перестановкой,
а не сортировкой по известному качеству. Option codes, подписи карточек и
mapping меняются согласованно во всех permutation runs.

Подготовить небольшие одинаковые карточки кандидатов: ego-plane plot с метрами
и временем, габаритом автомобиля и выделенной собственной траекторией.
Не рисовать 16 перекрывающихся линий на одной фотографии. Точное число листов,
размеры и image-token budget зафиксировать после технического просмотра, до
просмотра новых Drex outcomes. Проверить, что уменьшение processor не уничтожило
подписи и различия между похожими траекториями; не обрезать контекст молча.

Дополнительно нужна корректная связь карточки с камерой. До включения проекции
проверить origin/оси trajectory frame, ego-to-lidar transform, высоту плоскости,
camera extrinsics/intrinsics, crop/resize и отсечение точек за камерой. XY нельзя
напрямую считать lidar XYZ. Проекция по плоской дороге — приближение; не выдавать
её за точную поверхность на уклонах. Если необходимые преобразования нельзя
подтвердить, сначала отдельно решается представление входа, а не запускается
массовое сравнение с заведомо неправильными overlays. Кандидаты вне видимости
не выбрасываются: отсутствие визуального подтверждения отмечается явно.

Синтетические тесты: проекция/обратная привязка, crop offsets, handedness,
временные интервалы, footprint, clipping и неизменность physical ID. В конфиге
DriveSuprim sampling 4 s / 0.1 s; не путать с NAVSIM camera interval 0.5 s.
Реальные timestamps и формы vocab проверяются, а не заменяются константами.

## 5. Сравнение, которое отвечает на вопрос об изображениях

| Метод | Вход и правило |
|---|---|
| DriveSuprim | Прежний выбранный baseline |
| Drex text | Таблица кандидатов, ego, teacher predictions; без изображений |
| Drex visual (primary v1) | Те же сведения + наблюдения и карточки; argmax по 16 вариантам |
| Drex visual без дорожных пикселей | Та же структура пакета и геометрия карточек, но дорожные фотографии замаскированы |

Последний контроль удаляет дорожное изображение везде, включая фон overlays;
оставляет линии, подписи и геометрию. Иначе дорожные пиксели утекут через карточки.
Это диагностическое вмешательство, не идеальное сохранение распределения входов.
Text и masked-image controls нужны вместе: один лишь выигрыш над text может
объясняться более удобной графической подачей геометрии, а не восприятием дороги.

Основной вариант заранее один: visual, канонический порядок, один фиксированный
prompt и argmax. Перестановки служат измерением устойчивости, а не способом
выбрать лучший ответ по outcomes. Слияние распределений, confidence gate,
binary veto или иерархический отбор будут отдельными протоколами после v1.

Baseline используется при техническом отказе: отсутствующий вход, неверная
mapping, невалидный ответ, превышение лимита или отказ runtime. Такой случай
остаётся в знаменателе. Низкая уверенность пока только логируется: её нельзя
объявить collision probability или подобрать threshold по development.

## 6. Очередность запусков

1. `inventory` и `prepare`: CPU, сбор входов и preview, без загрузки весов,
   инференса и scorer calls. Создать manifest всех наборов; свежий holdout
   оставлять в закрытой роли, не готовить его запросы в начальной стадии.
2. Техническая проверка на 8 заранее выбранных по metadata development-сценах,
   распределённых по поездкам. Не выбирать только две известные DAC ошибки.
   Проверить формы, визуализацию, VRAM, число tokens, latency и повторяемость
   на нескольких одинаковых запросах. Проверка представления — без outcomes.
3. После фиксации представления — все 40 исторических development-сцен:
   visual в трёх порядках (канонический, обратный, seeded permutation),
   text и masked-image по одному каноническому запросу. Около 200 уникальных
   запросов плюс технические повторы; кэшировать по полному содержимому.
4. При исправной привязке входов и достаточном времени — те же замороженные
   условия на 651 training-сцене. Полный набор из пяти запросов на сцену —
   3255 запросов. Время оценивать по фактическому пилоту; не обещать заранее
   ночь на имеющемся железе. Не исключать сложные сцены/ошибки исполнения.
5. Лишь при воспроизводимом полезном сигнале решать вопрос о calibration/gate
   или дообучении. Это новая версия метода; настройка только по training-поездкам.
6. После окончательного freeze — один запуск primary и заранее закреплённых
   controls на всех доступных сценах четырёх отложенных поездок. Evaluation
   запускается после фиксации всех решений. Любое изменение по их результатам
   лишает их статуса финального теста следующей версии.

Этапы 1–3 проверяют доступность и механизм. Результат первых 40 сцен нельзя
объявлять подтверждением эффекта. Промпт не улучшаем итеративно по их ошибкам
с последующим представлением той же серии как независимой проверки.

## 7. Отчёт и правила решения

Считать stored raw local PDM delta, micro по сценам и macro по целым поездкам,
число замен и поездок с заменами, ухудшения всех восьми компонентов, число
relative safety regressions по пяти компонентам, худшую потерю, oracle regret
того же top16. Показывать результаты по поездкам, городам и происхождению данных.
Bootstrap делать по целым поездкам; четыре финальные поездки дают слабую
оценку неопределённости, а не доказательство безопасности.

Отдельно сравнить visual с text/masked на тех же сценах, а не только с baseline.
Проверить зависимость от одной поездки (leave-one-session-out), flip rate при
перестановках, изменение распределений и фактического PDM между порядками,
повторы, отказы, latency p50/p95 и полное время подготовки/инференса. Скорость
из статьи не переносить на наш GPU или пакет с несколькими изображениями.

До новой версии настройки применять прежние минимальные критерии допуска
на исследовательских данных: positive uniform macro gain, zero observed
relative safety harm, худшая потеря не более 5 п.п., >=10 замен в >=3 поездках
и полезные улучшения >=0.5 п.п. в >=3 поездках. Это фильтр для дальнейшего
исследования, не сертификат safety и не основание выбрать лучшую из таблицы
абляций. При провале primary для следующего этапа остаётся DriveSuprim.

Остановки: неверная геометрия или нечитабельные входы; нет добавочной пользы
дорожных пикселей; выигрыш только в одной поездке; тяжёлые ошибки или чрезмерная
зависимость от порядка. В таком случае сначала разбираем механизм, а не
увеличиваем эпохи/датасет. Local PDM не называть full EPDMS или closed-loop
результатом. Для этих утверждений нужны отдельные последующие эксперименты.

## 8. Изоляция, артефакты и следующие файлы кода

Новый корень результатов: `/workspace/exp_v2/drex_max`. Старые эксперименты
читаются без изменения. Объект запроса содержит только allowlist входов.
Inference worker не получает labels, metric caches, будущие кадры/траектории
людей, GT actors/maps или annotations. Оценщик работает отдельным процессом.
Разрешённые ego/calibration fields не превращаются в доступ к целому Scene.

Сохранять protocol/inputs/model/runtime hashes, manifests, изображения и preview,
полные запросы/распределения, option mapping, реальные token counts, время,
ошибки и fallback. Все решения замораживаются перед оценкой. Кэш ключуется
полным содержимым запроса, моделью, processor и runtime; старый ответ нельзя
повторно использовать после изменения изображения или attention implementation.
Для повторов — явная отдельная роль, а не получение удачного ответа retries.

Планируемые новые компоненты:

- `scripts/drex/run_drex.sh`: check, inventory, prepare, preview, smoke, infer, evaluate, report.
- `scripts/drex/inventory.py`: ресурсы и наличие файлов; без модели.
- `navsim/planning/script/prepare_drex_requests.py`: старое окружение NAVSIM → пакеты.
- `drex_experiments/representation.py`: таблицы/геометрия/рендер и option mapping.
- `drex_experiments/inference.py`: адаптер официального loader, кэш, repeat/permutation runs.
- `drex_experiments/evaluate.py`: проверка frozen decisions и отдельное чтение outcomes.
- Тесты на candidate alignment, отсутствие future/label fields, геометрию,
  перестановку, fallback, сохранение отказов и корректное resume.

Эти имена задают структуру будущей реализации, файлы пока не реализованы.
Первая поставка кода — inventory + подготовка/preview + тесты и команды сервера.
Большая модель не должна требоваться для проверки этих компонентов.

## 9. Когда возвращаться к обучению

Если готовый Drex полезен, сначала сравнить с обычной VLM на том же входе,
чтобы отделить вклад визуального backbone от decision head. Затем выбирать
между LoRA самого Drex и дистилляцией его дополнительных сигналов в малый
селектор. Для дорожной настройки опираться на проверенные PDM/component labels,
не считать ответ Drex истиной и учитывать несколько равноценных траекторий.
651 сцена остаётся 32 поездками, а не тысячами независимых candidate rows.

Обучение 27B с нуля, новый масштабный image download, RLAF-судья и прямое
управление рулём не входят в первый опыт. Перспективный вопрос статьи:
«Даёт ли предобученная визуальная decision-модель дополнительную пользу
при выборе из фиксированных кандидатов и какова цена ошибок/задержки?»
