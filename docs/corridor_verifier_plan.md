# Новый подход: проверка пространственного коридора траектории

План от 10 ноября 2026 года. Первая реализация — диагностический положительный
контроль с текущей статической HD-картой. Он не считается улучшением camera-only
DriveSuprim. Новых весов, изображений, платных API и обучения для этого этапа нет.

## Почему меняем постановку

На 651 training-сцене из 32 поездок top16 имеет примерно 3,79 п.п. оракульного
резерва local PDM. Скалярные и компонентные критики не прошли критерии качества:
выдумывали выигрыш из-за неверной оценки baseline и допускали тяжёлые ошибки.
Возврат DAC+LK исправил два разобранных случая, но создал два других. Согласие
teacher/student оставило одну замену без выигрыша. Эти варианты зафиксированы
как отрицательный результат, их пороги больше не подбираем.

Новая гипотеза: проверяющему модулю нужна явная пространственная привязка
траектории к дороге. Начинаем с одного понятного вопроса: «Выходят ли углы
автомобиля за пределы доступной дороги при исполнении этой траектории?»
Это не обучение общего gain и не замена всего планировщика.

Важно: в текущем `DriveSuprimModel.forward` список camera_feature сводится к
последнему кадру. Наличие seq_len=2 при подготовке не означает использования
двух изображений самим backbone. В старом sidecar сохранялась глобально
усреднённая image embedding, а также decoder states. Из этого не следует,
что spatial information полностью отсутствует в decoder; мы проверяем пользу
её явного представления, а не объявляем причину прежней неудачи доказанной.

Пространственные и временные представления уже исследовались, например, в
[ST-P3](https://arxiv.org/abs/2207.07601). Сам по себе такой принцип не является
новизной будущей статьи. Наш вопрос — измеримая польза corridor verifier при
фиксированном наборе кандидатов и сильном исходном селекторе
[DriveSuprim](https://arxiv.org/abs/2506.06659).

## Этап 1 — привилегированный геометрический контроль, реализован

Используются прежние top16, vocabulary, teacher ordering и stored raw/filtered
labels. На вход проверке передаются только текущая статическая геометрия дороги,
начальное ego state и предложенные траектории. Другие участники движения,
будущая человеческая траектория, route centerline и измеренный PDM не нужны.

Два режима фиксированы до запуска:

1. `raw`: четыре угла автомобиля на интерполированной предложенной траектории.
2. `rollout`: те же углы после исполнения траектории штатным LQR/bicycle simulator.

Размеры и rear_axle_to_center берутся от автомобиля в начальном состоянии.
Sampling берётся из замороженной конфигурации предыдущих прогонов. Проверяются
все моменты sampling, включая начальный. Для DAC используются те же статические
типы полигонов и строгое `contains`, что в исходном scorer. Границы считаются
вне полигона. Это проверка четырёх углов в дискретные моменты, не доказательство
непрерывного swept-volume или отсутствия столкновений.

Политика сохраняет baseline, если он проходит проверку. Когда baseline
отклонён, выбирается первый прошедший кандидат в прежнем teacher ordering.
Если никто не проходит — сохраняется baseline с явной причиной отказа.
Новое ранжирование PDM не обучается, measured labels не определяют выбор.

Согласие `rollout` с stored raw DAC ожидается по конструкции: это воспроизведение
геометрии целевой метрики. Оно проверяет конвертер и постановку, а не доказывает
качество восприятия. Полезный результат этапа — сколько baseline-ошибок можно
исправить таким правилом и какие NC/TTC/DDC/TLC/качество оно ухудшает.

### Изоляция данных

Bundle loader проверяет training membership, protected sessions и hashes.
Из pinned cache_index выбираются только токены bundle; зарезервированные
поездки не конвертируются. Cache files и sampling обнаруживаются через
замороженные inputs bundle, включая цепочки старых `identity.json` с
относительными inputs от явно указанного `source` и группированные inputs
`expansion_protocol.json`. Hash каждого вложенного manifest проверяется до
чтения. Непривязанные соседние cache indexes и поиск по всему диску не используются.
Несколько cache options разрешаются лексикографически до просмотра геометрии
или outcomes; количество таких случаев показывается в plan вместе с покрытием
training-токенов и числом проверенных manifests/cache indexes.

Конвертер вынужден десериализовать существующий trusted local metric cache,
который содержит также будущие поля. Он обращается только к `ego_state` и
`drivable_area_map`. Чистый inference-модуль cache не получает: только allowlist
примитивных NumPy-массивов и WKB полигонов. Тест с запрещёнными cache attributes
проверяет эту границу. Это не sandbox для загрузки произвольных pickle.

Пакет содержит IDs, индексы, baseline, teacher scores, raw/rollout poses,
габариты, sampling и статические полигоны. Другие поля отклоняются. Все решения
замораживаются до оценки stored outcomes. Scorer и traffic policy не вызываются;
новые ego-rollouts учитываются отдельно. Исходные labels не переписываются.

### Запуск в существующем контейнере

После commit/push/pull:

```bash
cd /workspace/DriveSuprim
bash scripts/drivesuprim/evaluation/run_corridor_geometry.sh check &&
bash scripts/drivesuprim/evaluation/run_corridor_geometry.sh plan &&
bash scripts/drivesuprim/evaluation/run_corridor_geometry.sh pilot
```

Pilot выбирает до восьми training-сцен по metadata/seed с разнесением по
поездкам, без просмотра outcomes. Его каталог отдельный:
`/workspace/exp_v2/drivemem_memory/experiments/corridor_geometry_pilot_v2`.
JSON report и SVG preview появляются автоматически. Red=baseline,
blue=raw choice, green=rollout choice; прямоугольники — footprint в пяти моментах.
Превью показывает world XY относительно позиции ego, не изображение камеры.
При несовпадении rollout с raw DAC команда завершается с ненулевым кодом после
сохранения отчёта и preview. Это техническая несогласованность для разбора,
а не повод увеличивать допуск или переходить к полному запуску.

Полный прогон:

```bash
nohup bash scripts/drivesuprim/evaluation/run_corridor_geometry.sh all \
  > /workspace/exp_v2/corridor_geometry_v2.log 2>&1 &

tail -n 60 /workspace/exp_v2/corridor_geometry_v2.log
bash scripts/drivesuprim/evaluation/run_corridor_geometry.sh report
```

Основной каталог: `/workspace/exp_v2/drivemem_memory/experiments/corridor_geometry_v2`.
Ожидаются 651 сцена, 10416 проверяемых кандидатов в каждом режиме, 10416
ego-rollouts. GPU, новые scorer calls и image download не нужны. CPU-время
зависит от распаковки cache и симулятора. Пакеты коммитятся по одному, повторный
`all` продолжает подготовку, сверяет решения и не пересоздаёт готовые пакеты.
Системный lock запрещает параллельную запись в один каталог.

`identity.json` записывается один раз; при продолжении сравнивается содержимое,
а исходные байты сохраняются. Это важно для hashes: порядок ключей словаря
может различаться между Python-процессами. Тест запускает каждый этап pilot
отдельным процессом с другим `PYTHONHASHSEED` и проверяет неизменность identity
и пакетов. Старые каталоги `*_v1` сохраняются для диагностики ошибки повторной
сериализации identity; скрипт использует новые `*_v2` без изменения геометрической
политики и без переноса или перепривязки старых hashes.

Выходы: `plan.json`, `identity.json`, `packet_index.json`, `packets/*.npz`,
`decisions.json`, `per_scene.csv`, `candidate_geometry.csv`, `report.json`,
`preview/*.svg`. Partial решения не заменяются полным набором в том же корне:
для pilot/full используются отдельные каталоги. Для иных путей поддержаны
`--bundle`, `--out` и `CORRIDOR_ROOT`.

### Решение после этапа

- Если rollout не совпадает с raw DAC, разбираем coordinates, sampling,
  vehicle parameters и cache provenance. Не меняем допуски ради прохождения.
- Если точная геометрия не даёт полезных исправлений или переносит ущерб на
  другие компоненты, пересматриваем задачу до нового обучения.
- Если потенциал есть, он остаётся привилегированным положительным контролем.
  Не переносим его gain в таблицу camera-only результатов и не открываем fresh holdout.

## Этап 2 — road evidence из камер, следующий после геометрического контроля

Целевой проверяющий модуль должен получать доступные AgentInput-наблюдения,
camera calibration и candidate footprint. HD-map polygons используются только
для training labels; inference worker их не получает. Предположение о плоской
земле и переход между ego/lidar/camera должны быть проверены отдельными
проекционными тестами и overlay. Слепо считать эти системы координат одинаковыми
нельзя. Непроецируемые и ненаблюдаемые части коридора отмечаются как unknown.

Первый визуальный опыт: текущие три камеры, прежний замороженный R34 backbone,
лёгкая обучаемая дорожная/коридорная голова. Сохраняем пространственную сетку
признаков и привязку к footprint вместо одного усреднённого image vector.
Не требуется новый большой VLM или загрузка его весов. Ресурсный smoke batch=1
на GTX 1080 выполняется до полного экспорта; вместимость не обещается заранее.

Сначала проверяем способность детектора различать DAC failures, а не общий
PDM gain. Контроли: исходный teacher DAC; прежний decoder-only детектор;
тот же по мощности verifier с corridor/spatial input. Сравниваем на одинаковых
поездках, кандидатах, labels и бюджете обучения. Считать пиксели/кандидатов
независимыми примерами нельзя: остаются те же 32 поездки.

## Этап 3 — временная информация, только при пользе текущего изображения

Отдельно сравниваем current-only с current+past. Используются реально доступные
past frames и ego history, с проверенным выравниванием. Разница считается
изменением входной информации и вычислительного бюджета. Убедительный результат
пространственного модуля не предполагает автоматически пользу времени.

## Этап 4 — калибровка и одно независимое испытание

Порог detector/fallback выбирается только на внутренних training/calibration
поездках внутри внешнего fold. Ограничения на ошибочное отклонение исходной
траектории и на пропуск выезда задаются до опыта. Если достоверных случаев для
калибровки мало — отказ, не вымышленная оценка риска. Full PDM остаётся итоговым
критерием: хороший DAC detector сам по себе не доказывает улучшение выбора.

Перед независимым испытанием фиксируются checkpoint, sensor/input contract,
геометрия, пороги, fallback и критерии. Четыре свежие отложенные поездки
открываются один раз после этой фиксации. Уже просмотренные 651 сцена и
исторические development-когорты остаются диагностическими данными.

Новые изображения сначала ищутся среди уже скачанных. Дополнительные архивы,
крупные модели и платный инференс не входят в этот план автоматически.
Отдельный `drex_max_research_plan.md` и его ветка не изменяются этим опытом.
