# Overlay v2: исключение ложной линии через небо

В v1 аудит 64 сцен обнаружил подозрительные сегменты в 59 сценах, всего 755.
На присланном превью TC путь длиной 18,56 м содержал четыре таких сегмента;
они давали линию через дорогу и небо. Число пересечений с прямоугольником
изображения само по себе не проверяло допустимость дисторсии.

V2 — отдельный протокол `overlay_top4_v2`, новый каталог и новые запросы.
Старые файлы `overlay_data.py`, `overlay_pilot.py`, `run_overlay.sh`, аудит v1
и результаты `overlay_top4_gpu4_v1` не меняются.

## Исправление

Преобразование camera-to-ego, коэффициенты калибровки, плоскость `z=0` и
Brown–Conrady остаются прежними. Исключаем лучи вне консервативной центральной
области, где якобиан дисторсии положительно определён. Область вычисляется
из коэффициентов объектива, без подбора по PDM, ручной границы неба или
отключения дисторсии. Формула модели и требование биективности описаны в
[OpenCV](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html).

Для нормализованного радиуса `r` положим `q=r²`, `s=N(q)/D(q)`.
Собственные значения радиальной части якобиана — `s` и `s+2q ds/dq`.
Минимальное собственное значение тангенциальной части не меньше
`-6r sqrt(p1²+p2²)`. Начиная с оптической оси, обе радиальные величины должны
превышать эту границу, а знаменатель — оставаться положительным.
Первый положительный корень соответствующих полиномов/полюс ограничивает
диск. Внутри этого выпуклого диска якобиан положительно определён; ложная
внешняя ветвь, где он снова стал положительным, не принимается.

Используются фиксированный относительный отступ `1e-7` от границы и численный
порог `1e-8`. Близкие к камере/недопустимые лучи отбрасываются **до** вычисления
пикселей. Соединяются только соседние допустимые точки: линия не перескакивает
через отвергнутые участки. В допустимой области коэффициенты не изменяются.

Диск консервативен и может исключить физически допустимые периферийные лучи.
Это ограничение явно сообщается модели вместе с прежним объяснением вставки
полного пути. Все 64 сцены сохраняются, даже если проекция не видна. Не
восстанавливаются уклон дороги, высота её будущих участков и перекрытия.
Центральная линия не описывает габариты автомобиля. Исправление foldback не
доказывает точность калибровки или безопасность движения.

## Сначала CPU-план и реальные превью

```bash
cd ~/drivesuprim
git pull --ff-only
export DREX_RUNTIME_ROOT=/scratch/pr0201/drex_runtime
export DREX_OVERLAY_V2_NAME=overlay_v2_top4_gpu4_v1

bash scripts/drex/run_overlay_v2.sh submit-plan 4
```

`submit-plan` ставит только CPU-задачу через `sbatch`, можно отключаться.
Суффикс `4` фиксирует будущее распределение сцен по работникам, GPU на этом
этапе не выделяется. Лог: `logs/overlay-v2-plan-JOBID.log`.

После завершения:

```bash
cat "$DREX_RUNTIME_ROOT/runs/$DREX_OVERLAY_V2_NAME/projection_report.json"
```

Ожидаются `status=render_contract_passed` и
`retained_legacy_suspect_segments=0`. Это означает прохождение численных
проверок, а `visual_alignment_verified=false` напоминает о необходимости
просмотра реальных превью; код не может подтвердить её за пользователя.
`projection_diagnostics.json` содержит длины путей и число видимых сегментов
до/после исправления. `projection_commit.json` фиксирует SHA плана,
диагностики и первых 20 PNG. Изменённые превью не перезаписываются молча.

В VS Code открыть:

```text
/scratch/pr0201/drex_runtime/runs/overlay_v2_top4_gpu4_v1/preview-87db8b7a7deb5b53-1.png
/scratch/pr0201/drex_runtime/runs/overlay_v2_top4_gpu4_v1/preview-00d8048e68a35a1d-4.png
```

На первом изображении проверяется исчезновение ложной ветви и положение
оставшегося пути относительно дороги. Второе может по-прежнему содержать
только вставку, если весь путь вне допустимой видимой области. Не растягиваем
короткий путь и не дорисовываем отсутствующие участки ради наглядности.

## GPU-пилот и полная серия

После просмотра превью:

```bash
bash scripts/drex/run_overlay_v2.sh submit-pilot 4
bash scripts/drex/run_overlay_v2.sh status 4
```

Четыре независимых полных BF16-реплики, по одной GPU на работника, по 18 новых
запросов в коротком пилоте. При первом запуске это 8 сцен / 72 запроса.
`partial` ожидаем; пилот не отправляет merge и не читает метки PDM.
Пилотные ответы v1 не копировать: V2 меняет пиксели, заголовок и пояснение
исключённых частей. Проверка хэша запроса отклоняет такие старые ответы.

Затем полная серия в том же каталоге:

```bash
bash scripts/drex/run_overlay_v2.sh submit 4
```

CPU-план → GPU-массив → CPU merge после успешного завершения всего массива.
64 сцены / 576 запросов: top4, три представления, три порядка. Готовые ответы
**v2** проверяются и пропускаются. До фиксации всех ответов и решений метки
не десериализуются. Сравнения с DS, blank/separate и oracle top4/top16
сохраняются. Итог: `report.json` и `per_scene.json` в каталоге серии.

Поддерживаются 1, 2, 4, 8 работников. Без явного `DREX_OVERLAY_V2_NAME`
имя по умолчанию содержит число GPU, например `overlay_v2_top4_gpu8_v1`.
При смене числа работников с явно заданным именем выбрать новое имя.
`DREX_OVERLAY_NAME` относится только к v1. Обычная очередь Slurm, без
`--exclusive` и вмешательства в чужие задания; CPU/RAM/GPU могут ограничивать
фактическое число одновременных работников.

Результат остаётся исследованием ранее размеченных train/development-сцен:
без обучения, новых меток и открытия holdout; raw local PDM, не full EPDMS.
